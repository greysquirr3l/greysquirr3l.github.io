Architecture overview

Sparkle Pony is a Cargo workspace with two members: the sparklepony engine and CLI at the root, and the neon-echo Tauri desktop frontend under neon_echo/. The engine is a library crate with a thin binary on top, which is what lets the desktop app link the same code the CLI runs instead of shelling out to a binary.

The work-item model

Section titled “The work-item model”

The input layer’s job is to turn a path on disk into a list of work items, each of which is one logical PST that can be opened as a single Read + Seek stream.

A WorkItem holds one or more PartSegments. Each segment is one of three things:

Segment kind How it is read
Loose file Opened directly
Stored ZIP entry SubFileReader over the archive’s byte range — no copy, no decompression
Deflated ZIP entry Streamed into a tempfile that is deleted on drop

MultipartReader concatenates segments into one seekable stream, handling reads and seeks that cross a part boundary. This is what lets the PST parser work unchanged on a file that was split across three volumes.

scan_zip reads only the archive’s central directory — metadata, not payload — so indexing an archive with many entries is cheap.

Parallelism

Section titled “Parallelism”

Folder traversal and extraction run on a Rayon thread pool. Deduplication uses a DashMap, so the concurrent hash map does the locking rather than the extraction workers.

The worker count is a ceiling, not a target:

  • --workers 0 (the default) means auto — the pool sizes itself to the host
  • resource:: monitors CPU and memory live and the manager throttles the pool when a ceiling is approached
  • --min-free-memory sets a floor below which the run backs off rather than pushing the machine into swap

That is why --safe exists as a single flag: it turns on conservative resource behaviour without you having to work out which ceiling to lower.

Writing the CSV

Section titled “Writing the CSV”

The CSV writer is shared across worker threads, so it has to be safe under concurrent writes. Rather than buffering the whole list in memory, contacts are streamed to disk as they are found. The source column records the work item each contact came from, which is what makes a row traceable back to its archive after a ZIP or multi-part input.

Filtering

Section titled “Filtering”

Three filters run against each candidate address:

  1. Blacklist — the eight-tier rule set, evaluated in order
  2. TLD validation — the domain’s TLD is checked against the IANA registry, cached locally between runs
  3. Format validation — the address must be syntactically plausible

Each is independently switchable: --disable-tld-filter turns off TLD validation, and --max-username-length bounds the local part.

Resume support

Section titled “Resume support”

Progress is tracked in a .sparklepony_progress.json file so an interrupted run can pick up where it left off. It lives next to the input by default — co-located with the source data — but falls back to a per-user cache directory when the source volume is read-only, such as a write-protected USB stick or an NTFS volume mounted read-only on macOS.

Safe paths

Section titled “Safe paths”

The same read-only concern applies to output. A macOS .app bundle launched from Finder runs with / as its working directory — the sealed system snapshot, which is not writable. So:

  • default_output_path() returns contacts.csv in a normal shell, and an absolute path inside the user’s Documents folder when the working directory is not writable
  • safe_output_path() re-roots any relative output path at runtime
  • The CLI answers the same problem the obvious way: pass an explicit -o /path/to/contacts.csv

Build-time version metadata

Section titled “Build-time version metadata”

build.rs derives the commit hash, branch, commit date, rustc version, and target triple from git at build time and injects them into the binary. That is what sparklepony version prints — you can always tell exactly which commit a binary came from.

The desktop frontend

Section titled “The desktop frontend”

neon_echo/src-tauri is a Tauri v2 application that depends on the root crate as a path dependency:

It imports the engine’s modules directly. There is no subprocess, no shell-out, and no separate implementation of the extraction logic — the app and the CLI run the same code.

The frontend is SolidJS with TypeScript, built by Vite and bundled by Tauri. The backend lives in a single src-tauri/src/lib.rs file: the DTOs, the command handlers, and the tests are all in one place.

See the Neon Echo architecture guide for the desktop side in detail.
