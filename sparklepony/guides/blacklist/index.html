Blacklist rules

The blacklist is the mechanism that decides which extracted addresses are discarded. It is a RON file — the same format the Neon Echo desktop app writes when you edit rules in its Advanced drawer — so a list edited in the GUI is the same list the CLI reads.

Where the file lives

Section titled “Where the file lives”

The blacklist path is resolved in this order, and the first hit wins:

  1. Explicit — --blacklist <path> on the command line
  2. Working directory — config/blacklist.ron relative to the current directory. This is the convention when you run from a source checkout.
  3. Per-user config directory — <config dir>/sparklepony/blacklist.ron. On macOS that is ~/Library/Application Support/sparklepony/blacklist.ron. On Linux it is ~/.config/sparklepony/blacklist.ron. This is where the Neon Echo GUI saves its edits.
  4. Bundled defaults — the rules compiled into the binary

Step 3 exists for a specific reason: an .app bundle launched from Finder runs with / as its working directory, so without a per-user location the GUI’s edits would never be applied.

extract and exclude resolve the file identically, so the two commands can never disagree about which addresses are excluded.

The eight tiers

Section titled “The eight tiers”

Rules are evaluated in tier order. The first tier that matches an address excludes it, and the tier is recorded as the reason.

1. Hardcoded domain floor

Section titled “1. Hardcoded domain floor”

Three domains are excluded in the binary itself and cannot be configured away: arksf.com, smartofficesinc.com, and mysmarthomes.com. Everything else is yours to configure.

2. blacklisted_terms

Section titled “2. blacklisted_terms”

Case-insensitive substring match against the whole address. Only use terms that cannot occur inside a genuine personal address — unsubscribe, bounce, noreply, amazonses, mktoemail.com.

3. bad_patterns

Section titled “3. bad_patterns”

Also a substring match against the whole address, but for patterns rather than words. A pattern prefixed with ^ is anchored to the start of the address, which is what stops false positives on real names that happen to contain the pattern:

Pattern Matches Does not match
^user@ user@domain.com superuser@domain.com
^user@ — realuser@domain.com
@test. bob@test.com bob@testing.com
example.com a@example.com a@notexample.com

4. role_local_parts

Section titled “4. role_local_parts”

Exact match on the local part — the part before the @. Plus-addressing is ignored, so no-reply+abc@domain.com still matches no-reply. These are unambiguous automated mailboxes; no real prospect corresponds to one.

5. ambiguous_role_local_parts

Section titled “5. ambiguous_role_local_parts”

Shared mailboxes whose display name may still be a person. hello@ and info@ are common personal-name contacts in some organisations, so these are kept by default and excluded only when you opt in.

  • extract — opt in with --exclude-ambiguous
  • exclude — opt in with --include-ambiguous

6. local_part_prefixes

Section titled “6. local_part_prefixes”

Prefix match on the start of the local part. This is the tier for automated senders that look like a person but are not.

7. domain_suffixes

Section titled “7. domain_suffixes”

Matched as the exact domain or any subdomain of it. netsuite.com also excludes 8768677.email.netsuite.com.

8. domain_first_labels

Section titled “8. domain_first_labels”

Matched against the leftmost label of the domain only. This is how you catch a marketing subdomain without catching the domain itself: mkt excludes deals@mkt.flyfrontier.com but leaves marketing@nowcfo.com alone.

File format

Section titled “File format”

The file is a RON document with a single BlacklistConfig(...) call. Comments use // syntax and are preserved by editors.

A copy of the bundled defaults lives at config/blacklist.ron in the repository.

Keeping the two modes in sync

Section titled “Keeping the two modes in sync”

extract and exclude evaluate the same tier set, so the same address is never kept by one and dropped by the other. The one asymmetry is deliberate: ambiguous shared mailboxes are kept by default in both modes, and excluded only when you ask for it (--exclude-ambiguous for extract, --include-ambiguous for exclude).
