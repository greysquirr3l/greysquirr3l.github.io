Architecture

Neon Echo is three layers. Nothing in the middle layer duplicates logic from the bottom one.

The app links the library, it does not shell out

Section titled “The app links the library, it does not shell out”

This is the single most important architectural fact.

src-tauri/Cargo.toml declares:

The Rust backend imports the library’s modules directly:

There is no Command::new, no std::process::Command, no sidecar declaration in tauri.conf.json, and no tauri-plugin-shell dependency. The sparklepony binary is a separate CLI; the app uses the library.

The consequence: the extraction logic is the same code either way. A bug fixed in the library fixes both surfaces.

Frontend: SolidJS, not React

Section titled “Frontend: SolidJS, not React”

The files are named .tsx, but they contain Solid JSX — createSignal, <Show>, <For> — and tsconfig.json sets "jsxImportSource": "solid-js". The package is solid-js 1.9, wired up through vite-plugin-solid.

State is a handful of signals in src/App.tsx: the selected input path, the preview result, the extraction progress, the live system stats, and the version string. There is no state library and no routing — the app is one screen with a drawer.

The backend: one file, eleven commands

Section titled “The backend: one file, eleven commands”

src-tauri/src/lib.rs holds the entire backend. It declares no submodules — DTOs, helpers, commands, the build() and run() entry points, and an inline #[cfg(test)] mod tests block all live in that one file.

src-tauri/src/main.rs is thirteen lines: it calls neon_echo_lib::run() and sets windows_subsystem = "windows" in release so no console window appears.

off_main — the reason the UI never freezes

Section titled “off_main — the reason the UI never freezes”

Tauri runs synchronous commands on the thread that pumps the window event loop and the webview. Blocking there freezes the UI, and macOS flags the app as unresponsive.

Every heavy command goes through this helper instead:

preview_input, extract, all three cleanup commands, load_blacklist, save_blacklist, and system_info are async and route through it. Only version, default_blacklist, and default_paths are synchronous — they return in-memory data with no work to do.

The regression test at lib.rs:708 builds the real app over the mock runtime and asserts that dispatch returns in under 250 ms while the work itself takes over 400 ms.

The extraction path

Section titled “The extraction path”

extract → off_main → run_extraction:

  1. Validate that req.input exists.
  2. Map the request DTO onto a sparklepony::config::Config via build_config — output path through config::safe_output_path, blacklist path through resolve_blacklist_path, and no_progress: true so the CLI progress bar stays off (the app has its own).
  3. Build an Arc<ProgressCallback> that emits extract://progress. If an emit fails, it logs to stderr and continues — a dropped progress tick must never abort an extraction that is otherwise succeeding.
  4. Run Processor::new(cfg)?.with_progress_callback(callback).process()?.
  5. Return the contact count and output path.

Window sizing

Section titled “Window sizing”

fit_window_to_monitor runs at startup and shrinks the window to the monitor’s work area, so the footer controls stay reachable on short displays instead of falling off the bottom of the screen.
