The workflow

The whole app is four steps. Each one is a decision you make, and nothing starts until you ask it to.

1. Pick

Section titled “1. Pick”

Three ways in, all native:

  • Open folder of zipped PSTs — the common case. A folder of .zip files, each containing PSTs.
  • Select PST or ZIP files — individual files, multiple at once.
  • Drag and drop — drop a file or folder onto the window.

Everything goes through Tauri’s native dialog and drag-drop APIs, so the app receives real filesystem paths. This is not a browser <input type="file">, which would give you an opaque handle and no way to read sibling files in a folder.

Mixed inputs are fine

A folder can contain PSTs, ZIPs of PSTs, and split-part archives side by side. The pre-flight scan works out what each file actually is.

2. Review

Section titled “2. Review”

As soon as a path is set, the app runs a pre-flight scan and reports:

  • how many mailboxes were found
  • the total size of the input

This is the preview_input command. It walks the input tree with collect_work_items and returns counts — it does not open a single mailbox. You find out the size of the job before committing to it.

3. Extract

Section titled “3. Extract”

The Extract Contacts button starts the run. Two things happen:

  • A live progress bar shows which mailbox is being processed and how far along the whole job is.
  • The CSV is written incrementally, so contacts are on disk as the run progresses rather than all at the end.

The output lands in your Documents folder by default. The 📁 button next to the output path picks somewhere else.

The window stays responsive

Every heavy command runs on Tauri’s blocking thread pool via the off_main helper, never on the thread that pumps the window event loop. This was a real bug — the first version blocked the UI during extraction and macOS flagged the app as unresponsive. It is now regression-tested at the Rust level.

4. Done

Section titled “4. Done”

The result card shows the total contact count and the output path, with a button to reveal the CSV in the file manager.

The advanced drawer

Section titled “The advanced drawer”

Behind the drawer toggle sits everything that is not part of the main path:

Section What it does
Resources & workers CPU ceiling, memory ceiling, minimum free memory, worker thread count
Filtering TLD filter toggle, ambiguous-role exclusion, sender/recipient extraction toggles
Blacklist manager Edit the blacklist rules the conversion applies
List cleanup Validate email syntax, validate MX domains, exclude blacklisted addresses

Each of those maps onto a sparklepony library call — see the command reference.

The blacklist applies to the conversion

Section titled “The blacklist applies to the conversion”

The blacklist lives in the per-user config directory:

The conversion reads that same file. There is no separate load step, and no risk of the app and the CLI disagreeing about which rules are in force — they resolve the path the same way.

One source of truth, two surfaces

If you edit the blacklist in the app’s manager, the app writes to the per-user config file. The CLI, run from a different working directory, will find the same file through its fallback chain. Run the CLI with an explicit --blacklist if you need it to use a different one for a single invocation.
