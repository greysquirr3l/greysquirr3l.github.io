Trails and review

A trail groups the changes (one branch per repository) that make up a piece of work. The Trails view lists them, and six commands review them from the editor, and more create, update and watch them and work their discussions and findings. Entirely calls the CLI for each action, and reads the result back before it says anything landed.

The Trails view

Section titled “The Trails view”

The view lists the trails of the project the open repository belongs to, filtered to this repository. The project comes from entire repo view. It needs a signed-in login that can see that project.

A trail row shows #number title and its status. entire trail list does not carry a trail’s changes, so the row says changes not loaded until you expand it (or select it). Expanding reads entire trail show <n> once and lists the changes underneath, each with the state of its merge gate; the row then says how many changes it has and how many are awaiting approval. Expanding it again, or selecting it, inside entirely.selectionCacheSeconds (default 30) reads nothing. If the read fails, a line under the trail says why, and expanding it again tries again. A change row shows the repository and number and the gate:

Gate text Icon Meaning
ready to merge · N approvals check The CLI says the change can merge.
awaiting approval bell The CLI’s blockers include an approval requirement.
blocked · reason error The CLI reports a blocker that is not an approval.
merged question The change has been merged, so there is no gate left to read. The merge check is skipped.
trail closed question The trail is closed, so its changes are not checked.
gate unknown question The CLI did not answer. The tooltip says why.

The gate comes from entire trail merge --dry-run, which is the one place the CLI reports its merge conditions. Entirely reads the blockers, not an approval count. A gate can require more than one approval, a named reviewer, or none, and only the CLI knows which. The approval count on a ready change is for display only. Hover a blocked change to see the CLI’s blockers.

The approvals badge

Section titled “The approvals badge”

Changes awaiting approval are counted in the Trails view’s badge. The list carries no changes, so the count comes from reads, and the tooltip says what it covers: for example “2 changes not yet approved, counted from 10 of 12 open trails; 2 open trails not read, expand one to read it”. When you refresh the view, or after an approve, merge, link or unlink, Entirely reads up to entirely.trailBadgeLimit open trails (default 10, 0 shows no count), three at a time, once. Closed trails are not read. A trail you expand adds to the count. The badge clears when none of the trails read are waiting, and there is no badge before anything has been read.

The view re-reads its list on the entirely.refreshInterval timer (default 30 seconds) and drops a tick that arrives while the previous read is still running. That background refresh reads only the list and keeps the changes already read, so the badge is the count as of your last refresh; refresh the view to read again.

An empty view reads “No trails to show”, or gives the reason it couldn’t list them, such as the CLI’s refusal.

Note

Access to a project is per login, not just per repository. On a personal account, a login that can see the repository may still be unable to see its project, and then it can’t list or review the project’s trails. Entirely says so and names entirely.cliContext instead of showing an empty list. See Accounts and contexts.

The detail panel

Section titled “The detail panel”

Select a trail or a change, by click or by keyboard, and its detail opens in the detail panel beside your code, without taking focus. It is one panel for every selection: the next row you select replaces what it shows.

A change shows the change’s title, repository/number, branch (or “no branch”), status, whether it carries code, and the gate with its approval count and blockers. One entire trail show <n> --json of its parent trail adds the trail’s number, title, status, type, priority, page, whether it has a description, and the other changes on it. The gate is the one the Trails view read, so it is as fresh as the last read of that trail.

A project trail shows its own fields and its changes, from the same single entire trail show <n>. The panel and the Trails view share that read: expanding a trail and then selecting it reads it once.

What it does not show, because each needs a read of its own or is not in the data: base branch and head commit, who approved, comment and finding counts, and linked items. A description appears only as “Has a description”; Open as text writes it to a read-only document, and it is never written to the output channel.

  • Merged or deleted. If trail show fails with the CLI’s not-found wording, or the answer leaves the change out of the trail’s change list, the panel says “… is no longer available. It may have been merged or deleted.” with a Refresh link.
  • Failed read. The panel names the item and the CLI’s reason, with a Retry link. No popup.
  • CLI missing, or without trail show. You keep the listing’s fields and one line, “Trail details need a newer Entire CLI”, which links to Set Up Entire. Sessions and Activity are not affected.
  • Cache. The answer is kept for entirely.selectionCacheSeconds (default 30). Approving, merging, linking or unlinking drops it for that change and its trail and refreshes the Trails view. Each trail show read uses entirely.trailActionTimeout.

A change’s panel has the review actions as links: Approve, Comment, Merge, Check out, Link branch and Unlink branch. They are the commands below, acting on the change shown instead of asking you to pick. Each keeps its own confirmation, and Approve gains one here: picking the change in the palette was its confirmation, so from the panel or a Trails row it first asks “Approve change as login?” in a modal, and does nothing if you cancel. Link and Unlink act on its parent trail. Each command checks that it was given the item the panel shows, and asks which one you mean if it was not.

The panel, its reveal behaviour and the click handling were tested only against stand-ins for the editor, so check them by hand in a real window (open the panel, hide it behind another tab, click the same row again, try a light and a high-contrast theme, and Tab to a link). The reads were checked against a fake CLI that mirrors the shapes of the real one (trail list without changes, trail show with them and with an empty branch for a merged change). trail show for a change that has since been deleted was not seen against a live server, so the not-found wording is read from the CLI’s error text and may need adjusting.

Review commands

Section titled “Review commands”

Run from the palette, each command lists the trails of this repository from the CLI, in the CLI’s order, and asks you to pick one. Run from the detail panel or with a row from the Trails view, it acts on that row and does not ask which change. The CLI’s list carries no changes, so before you pick a change Entirely reads the changes of the open trails that have none (at most 50, three at a time, with a cancellable progress notification; closed trails are skipped). This read does not depend on entirely.trailBadgeLimit. Changes are picked for approve, comment, merge and check out. Trails are picked for link and unlink. If there are none, you’re told so.

Command Picks Asks What you see after
Entirely: Approve a Change on a Trail a change Nothing further when you pick it in the palette. From the panel or a Trails row, a modal “Approve change as login?” first. The approval is read back. “Approved … as author” if it is under the login Entirely acts as. A warning if the CLI recorded it under someone else, or didn’t record one.
Entirely: Comment on a Change on a Trail a change The comment text. “Commented … as author” once the comment is read back under the acting login. A warning if it isn’t there.
Entirely: Merge a Change on a Trail a change A modal naming the branch, its base and the head commit: “Merging branch into base at sha … Merge it?” “Merged …” on success.
Entirely: Check Out a Change on a Trail a change “Check out …? This moves the working tree to that branch.” “Checked out …”.
Entirely: Link a Branch to a Trail a trail The branch, then “Link branch to trail #n?” “Linked …”.
Entirely: Unlink a Branch from a Trail a trail The branch, then “Unlink … ? The branch and its code are kept.” “Unlinked …”.

Details that matter:

  • Approve and comment act as the login Entirely is using. The status bar and Account view say which. Pinning a different login is covered in Accounts and contexts.
  • Merge first runs the CLI’s dry run. If the change isn’t mergeable, nothing is asked. You get “Entirely did not merge the trail:” followed by the CLI’s own reasons. Each change of a trail merges on its own.
  • Check out is refused while any workspace file has unsaved changes. The message names the files: “Save the files, or stash them, and try again.” Untitled buffers and files outside the workspace don’t count.
  • Comment from an agent session. The CLI refuses discussion comments from inside an agent session and points at its finding command. When that happens, Entirely posts the note as a finding instead, and tells you: “The CLI refuses discussions from an agent session, so the note was posted as a finding instead.”
  • A failure of any command shows “Entirely could not … : the CLI’s reason”. Comment bodies and titles are redacted from the logged command line.

Write actions are tested against a fake CLI. They are not verified against a live Entire server in every case, so check the result on the trail itself the first time you use them. See Coverage.

Create, update and watch

Section titled “Create, update and watch”

These were tested against a fake CLI only: no trail was created, updated or watched on the real service while they were built, and the CLI’s output for several of them was not observed. Check the result on the trail itself the first time you use them.

  • Entirely: Create a Trail (the + in the Trails view title, or the palette) asks for a title, an optional description and whether the trail is for the current branch or intent only, then asks in a modal naming the title, the login and “on Entire”. For a branch, the CLI publishes your current branch to the remote first; it does not commit your changes or change your checkout. The trail is reported only when a fresh trail list holds exactly one new trail with that title. If the CLI succeeds but no such trail is listed you are told so (“check the web UI”). If the CLI fails after the trail exists, Entirely says to link the branch with Link a Branch to a Trail and not to create it again. Type and priority are offered only when the CLI’s help names a list.
  • Entirely: Update a Trail (the pencil on a trail row, or the palette) changes one field: title, description, type, priority, status, or the assignees (add, remove, replace the list, clear it). It shows the current value, changes it once and reads the trail again before reporting. Closing a trail and replacing or clearing the assignee list ask first, naming the trail, the login and “on Entire”, with the old and new value. Other edits and adding or removing one assignee do not ask.
  • Entirely: Watch a Change on a Trail (the eye on a change row) starts one entire trail watch process for that change. The CLI reconnects by itself and Entirely never polls. When the stream reports an event, the change’s Comments and Findings rows are read again once, after entirely.trailWatchRefreshDelay seconds so a burst of events costs one read. The change row says “watching” and how many updates have arrived; event contents are never shown or logged. Stop Watching (the closed eye, or Stop Watching All Changes) ends the process, and so do the end of the stream, a revoked access, a project the login cannot see, and closing the editor. A watch that ends on its own says why and is not restarted. entirely.trailWatchLimit caps how many run at once.

Comments and Findings under a change

Section titled “Comments and Findings under a change”

A change row expands into Comments and Findings. Nothing is read until you expand a group; the rows are then kept until you refresh the view, write something, retry, or a watch reports an event, so the view’s refresh timer does not read them again. A group with nothing shows “No discussions” or “No findings”; a read that fails shows the reason with a retry button.

Discussions show their title, resolved or open, message count and last author. Findings show severity, status and file and line, with an icon by severity, and resolved and dismissed findings stay in the list so they can be reopened.

Row Inline actions In the context menu
Change Watch or Stop Watching, Start a Discussion
Discussion Reply, Resolve or Reopen, Show Edit a Discussion Message, Delete a Discussion Message
Finding Apply, Resolve, Dismiss (open); Reopen (resolved or dismissed) Update a Finding, Show a Finding
Action Asks first? Read back before it is reported
Start a discussion, reply No (the text is the consent) The discussion shows it under the acting handle. A message recorded under another handle is reported as theirs.
Edit a message No; your own messages are offered, and any message the listing gives no author for (the CLI then decides) The fresh discussion holds the new text.
Delete a message Yes, the strictest wording, naming the message (author and the start of its text) when there are several: it cannot be recovered from the editor The fresh discussion no longer holds the message.
Resolve or reopen a discussion No The fresh flag.
Resolve or reopen a finding, update a finding No The fresh listing of every status.
Dismiss a finding Only a high-severity one The fresh listing.
Apply a finding’s suggestion Yes See below.

Typed text (titles, bodies, messages, reasons) is sent to the CLI as arguments of their own, left out of the logged command line, and what the CLI prints is withheld. Show a Discussion and Show a Finding open read-only documents on request; their text is review text and is never logged. If the CLI’s answer for a discussion is in a form Entirely does not read, you are told so and offered the command to copy.

The CLI allows discussion writes only to people. If this editor session is an agent session, a reply, edit, delete or resolve is refused with a message saying so; nothing is retried or redirected. (A new comment from Comment on a Change on a Trail still falls back to a finding, as above.)

Applying a finding’s suggestion

Section titled “Applying a finding’s suggestion”

Apply changes your working tree, so it is refused while any workspace file has unsaved changes, naming the files, and the CLI is not run. Otherwise Entirely asks the CLI whether the patch applies (its check flag); if not, your files are untouched and the CLI’s reason is shown. If it does, a modal names the finding, the login and the folder, and offers Apply or Apply and Resolve. The CLI applies it once and Entirely says “The CLI reported the suggestion applied. Review it in Source Control.” It reads no diff, so it cannot list the files that changed. With Apply and Resolve the finding’s status is read back, and “unconfirmed” is reported if it still shows open.

When the project is not visible

Section titled “When the project is not visible”

A GitHub collaborator on a repository can see the repository but not the personal project that holds its trails, and every trail command then fails with “project not found”. For every command above Entirely says that the acting login has no access to the project, that this is how the CLI and the forge behave, and that you can review in Entire’s web UI or move the repository to a GitHub organisation both people belong to. See Accounts and contexts.

Limits

Section titled “Limits”
  • trail resume is not offered. It is interactive in the CLI. Resuming a session on a branch is covered by Entirely: Resume Session in Sessions and checkpoints.
  • The view lists only this repository’s changes within the project. Other repositories’ changes on the same trail are dropped.

Settings

Section titled “Settings”
Setting Default Effect
entirely.trailActionTimeout 60 Seconds a review action may run before Entirely stops waiting. A check out that has to fetch can take longer than a read.
entirely.trailWatchLimit 3 How many changes may be watched at once (1 to 10).
entirely.trailWatchRefreshDelay 2 Seconds a watch gathers events before reading a change’s discussions and findings again (1 to 30).
entirely.refreshInterval 30 Seconds between Trails view refreshes. 0 refreshes only on command.
entirely.cliContext empty The saved login to act as. Machine scope.
