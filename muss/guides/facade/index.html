The muss-teams facade

An application depends on muss-teams alone and writes ordinary async functions. The facade is the only supported entry point: transport clients, storage adapters and protocol types stay internal, so an application never assembles an OAuth client, an activity adapter, a storage trait and a dispatcher just to answer a message.

That is examples/hello.rs. A test keeps it under 25 lines and checks that it imports only from muss_teams.

The three types

Section titled “The three types”
Type What it is Starts anything?
TeamsApp A configured bot with handlers registered. No. Dropping it has no effect.
BuiltApp The authenticated pipeline, running, with no listener. Its worker pool, on build.
TeamsClient Sends messages with the bot’s credentials. No. It binds nothing and spawns nothing.

TeamsApp is a builder. Nothing listens, connects or spawns until build or run is called, so a value of this type can be passed around, tested and dropped without side effects.

BuiltApp is the pipeline running: authenticator, intake, bounded dispatcher and handlers, with no listener. It is what you embed in a host you control.

TeamsClient only sends. It binds nothing and spawns nothing, and it keeps working after the app it came from is shut down.

Configuration

Section titled “Configuration”

TeamsApp::from_env() reads:

Variable Required Meaning
TEAMS_APP_ID yes The application (client) id of the bot’s Entra registration, a GUID. Also the audience of inbound tokens.
TEAMS_TENANT_ID yes The id of the directory the registration lives in, a GUID. Not its domain name.
TEAMS_CLIENT_SECRET yes A client secret of the registration.
TEAMS_CREDENTIAL no client-secret (the default). certificate and managed-identity are refused with a pointer to TeamsApp::with_credentials.
TEAMS_BIND_ADDR no host:port for run. Defaults to 127.0.0.1:3978.

The default address is the loopback interface on purpose: a bot is reached through an HTTPS front end or tunnel, and listening on every interface by default would publish a plain-HTTP endpoint nobody asked for.

The credential is a choice, not a guess. A missing secret is an error that names TEAMS_CLIENT_SECRET; it never turns into a managed identity. For a certificate, a managed identity or a provider you write, use TeamsApp::with_credentials(app_id, tenant_id, credentials) with a Credentials::ClientSecret, a Credentials::Certificate or a Credentials::ManagedIdentity.

A configuration error names the setting, says what to do, and never prints the value:

A variable that holds bytes that are not text is reported as not usable, not as not set.

Starting and stopping

Section titled “Starting and stopping”
Call What it does
TeamsApp::run Builds the app, binds the configured address and serves until Ctrl-C (or SIGTERM on Unix). Then shuts the app down.
TeamsApp::run_until(stop) The same, stopping when the future you pass completes. Use it for your own signal, or from a test. Returns a ShutdownReport.
TeamsApp::build Builds the app and returns a BuiltApp, with no listener.
BuiltApp::serve(listener, stop) Serves on a listener you bound, then shuts the app down.
BuiltApp::shutdown(grace) Stops admitting, lets admitted handlers finish for up to grace, aborts the rest, joins every worker, returns a ShutdownReport.
BuiltApp::shutdown_gracefully shutdown with the configured grace period.

run and run_until are behind the http-host feature, which is on by default.

A request that fails authentication is answered with the refusal’s status code and nothing else happens: it is not parsed into an activity, recorded or queued.

BuiltApp::client() returns a TeamsClient that sends through the same credentials and keeps working after the app is shut down.

Shutdown and ownership

Section titled “Shutdown and ownership”

The app owns its worker pool. shutdown(grace) stops admitting, lets admitted handlers finish for up to grace, aborts what is left, joins every worker and returns a ShutdownReport of handled, unhandled, failed, panicked and aborted counts.

If you mounted router() in your own server, stop that server and drop the router before calling shutdown; otherwise it returns Error::StillInUse rather than hang, and the workers stop when the last holder lets go.

The app starts no task of its own other than the worker pool it joins: no timer, no cache refresher, no detached spawn. The HTTP client library keeps its own connection tasks, which it owns.

Handlers

Section titled “Handlers”

Every kind of activity has one registration method on TeamsApp: on_message, on_message_update, on_message_delete, on_conversation_update, on_installation_update, on_reaction, on_invoke, on_meeting (with on_meeting_start, on_meeting_end, on_meeting_participants_joined and on_meeting_participants_left) and on_unknown. A handler is any Fn(Context) -> impl Future<Output = Result<(), E>> where E is an error type, so a plain function, a closure that captures an Arc, and a handler that returns std::io::Error all work. It may be called many times and from several tasks at once. A context is Clone and can move into a spawned task.

An activity with no handler is counted in the shutdown report and dropped. An activity this version does not route goes to on_unknown with its raw body, and never to another kind’s handler.

Handler failures are counted. To see them as they happen, register on_handler_failure, which is called with a Failure: Failure::Handler, Failure::Panicked or Failure::TimedOut.

Bounds

Section titled “Bounds”

concurrency(queue, workers) bounds the work in flight; the defaults are 256 waiting and 16 running. A full queue answers 503 with Retry-After: 1 and forgets the delivery, so Teams’s retry is handled once there is room. Bodies over 1 MiB are refused before they are authenticated.

State

Section titled “State”

State defaults to a bounded in-memory store that is lost on restart. With the sqlite feature, sqlite_state(path) keeps conversation references and repeat marks in a SQLite file, so a delivery handled before a restart is not handled again after it. memory_limits(MemoryLimits) bounds the in-memory store (rows, bytes and the share one tenant may hold). See state and performance.

Features

Section titled “Features”
Feature Default Adds
http-host yes TeamsApp::run, run_until, BuiltApp::router and serve.
sqlite no TeamsApp::sqlite_state.
test-utils no muss_teams::testing: supply your own signing keys, clock and Connector destination in a test.

--no-default-features is the lean combination for an application that only sends, or that hosts the bot on another framework through handle. It has no web server dependency.

muss_teams::testing::SimulatedTeams is the public stand-in for Teams: it generates a signing key, publishes the public half to the bot, and signs the bearer tokens the bot is asked to accept. SimulatedTeams::components takes the address of a server you run on the loopback interface and refuses any other address, so a simulation cannot be pointed at a real service. examples/offline.rs is built on it.

test-utils replaces where the signing keys come from, the clock, and where the Connector writes. The token is still parsed, its signature checked and its claims judged by the production policy, so a token signed by another key is refused. No build enables it by default, and there is no switch that turns authentication off.

What the production wiring trusts

Section titled “What the production wiring trusts”
Decision Value
Signing keys https://login.botframework.com/v1/.well-known/keys, refetched at most once an hour, with a bounded negative cache
Issuer https://api.botframework.com
Audience TEAMS_APP_ID
Algorithm RS256
Channel msteams only
Tenant the configured tenant only (single-tenant registration)
Reply destinations smba.trafficmanager.net, https, port 443, public addresses; allow_service_host adds a host

Multi-tenant registrations, managed-identity bots receiving activities, sovereign clouds and other channels are refused at configuration time rather than accepted on trust. They are unverified, not unsupported forever.

What the facade deliberately does not do

Section titled “What the facade deliberately does not do”
  • No live tenant has been involved. Every test signs its own tokens and writes to a loopback server. That the facade works against Teams is not proven.
  • It does not register your app. The registration, the Teams channel, a public HTTPS endpoint, the manifest and the installation are real prerequisites that no library does for you; the muss-teams tool walks through them.
  • It does not answer every invoke. Card actions and dynamic choice sets are answered (see card actions); dialog and message extension invokes are answered too. Other invoke names run their on_invoke handler and write no response.
  • It does not look a user up by name. Proactive notifications use typed targets and need the conversation state of a built app; a client built on its own can still send to a ConversationReference you recorded.
  • Windows has not run any of this. The pipeline is platform-neutral and has been run on macOS only.

The locked list of public names is in the public API.
