Tenant-scoped state

muss-teams keeps conversation references, subscriptions, deduplication markers, outbox entries and idempotent results in a store behind a few narrow ports. Two stores ship: an in-memory one for development and an optional SQLite one. A custom store implements the same ports.

Port Methods Purpose
RecordStore get, put, delete references, subscriptions, deduplication markers, with compare-and-set
OutboxProducer enqueue add work outside a unit of work
OutboxWorker claim, complete, release lease and finish queued work
IdempotencyStore execute check, run, persist the result, atomically
Retention purge_tenant, sweep_expired erase a tenant, release expired rows

The ports live in muss_teams::application::state, one module per intent. The domain (muss_teams::domain::state) holds only values: keys, payloads, versions, fingerprints, the retention policy. It has no storage trait and no clock. Time is an argument (StateTime).

Run cargo run -p muss-teams --example state for a worked example.

Tenant isolation

Section titled “Tenant isolation”

Every port method takes an AuthContext, and every row is keyed by its tenant. A RecordKey names a thing inside a tenant, so no call can name another tenant’s row. Two tenants that use the same conversation id, outbox id or idempotency key each get their own row; the contract suite checks this for records, the outbox and idempotent results, and checks that purging one tenant leaves the other alone.

Compare-and-set

Section titled “Compare-and-set”

put takes an Expectation: Absent, At(version) or Any. A write whose expectation does not hold fails with Conflict and changes nothing. Versions start at 1 and rise on every write. An expired row reads as absent, but a rewrite still takes the next version, so a stale At(v) cannot succeed against a recreated row. Do not hold a version across the row’s lifetime: once a sweep removes an expired row, its version history is gone.

Running a command once

Section titled “Running a command once”

execute_once takes an IdempotencyKey (a UUID v4) and a CommandFingerprint (an operation name plus the ids it acts on), and runs a closure with a UnitOfWork. In one atomic step the store checks for a committed result, runs the closure, and commits the closure’s writes together with the result it returned.

  • A repeat returns Outcome::Replayed with the committed result and does not run the closure.
  • A repeat under a different fingerprint is KeyReused.
  • A closure that returns an error is rolled back completely (records, overwrites and outbox entries) and reports WorkFailed. The key stays free.
  • A store that cannot fit the result rolls the work back and reports the limit. Partial state is never reported as success.

The closure runs while the store holds its lock or transaction. Keep it short and do not call other systems from it.

An IdempotencyKey wraps a version 4 UUID. IdempotencyKey::new() draws a fresh value from the operating system’s random source, and that is the path most callers take. A key that arrived as text goes through IdempotencyKey::parse or FromStr, and both accept exactly one shape: a canonical hyphenated version 4 UUID. Any other UUID version, any other notation and any malformed text is rejected, so a key cannot be assembled from an arbitrary string.

The outbox, and what it does not promise

Section titled “The outbox, and what it does not promise”

Write the business change and an outbox entry in one unit of work. A worker then leases the entry, performs the effect and completes it. If the worker dies after the effect and before complete, the lease expires and the entry is delivered again. Delivery is at least once. An external system with no idempotency support cannot be made exactly-once from this side: the window between “effect performed” and “entry completed” is real, so the receiver must tolerate a repeat (send a stable id with the effect and let the receiver deduplicate). SDK replay handling does not make an external business operation atomic.

An entry that has been leased max_attempts times stays in the store and is no longer handed out, for an operator to inspect. Leases run from one second to one hour, and a claim returns at most 100 entries.

Deduplication

Section titled “Deduplication”

first_delivery records a delivery id with Expectation::Absent and returns true for the first caller only. Bot activities and Graph notifications carry different ids; a Graph change without a stable delivery id cannot be deduplicated, and the caller must not invent one. This is deduplication, not exactly-once processing: if the worker records the delivery and then crashes, the delivery is lost. Put the marker in the same unit of work as the handling when that matters.

Retention and deletion

Section titled “Retention and deletion”

Nothing is kept forever by default. RetentionPolicy sets a default lifetime (24 hours), a maximum (30 days, longer requests are shortened) and how long an idempotent result is replayable (7 days). Expired rows are invisible to reads; sweep_expired releases the space.

  • Uninstall or a privacy request: Retention::purge_tenant deletes every row held for the tenant (records, outbox entries, results) and returns the count.
  • What is kept: only data needed to operate for a tenant, such as a conversation reference. Payloads are stored in the clear. Never store tokens, client secrets or keys here; they need a secret store.

The in-memory store

Section titled “The in-memory store”

MemoryState is lost when the process ends. It is bounded by entry count (10,000), bytes (16 MiB) and time, and by a per-tenant share of the first two. A full store refuses a new row with LimitExceeded rather than evicting a live one, because the rows are deduplication markers, references and queued work.

One tenant may hold 90 per cent of the rows and of the bytes by default (MemoryLimits::tenant_share_percent, 1 to 100). A tenant at its share is refused (tenant entry count or tenant byte size) while the other tenants still write, so a flood by one cannot starve the rest. Records, queued outbox entries and idempotent results all count, a replacement does not, and a delete, an expiry or a purge gives the share back. The bounds are a MemoryLimits: MemoryLimits::default().entries(50_000).tenant_share_percent(100). A bot built with TeamsApp passes them to TeamsApp::memory_limits, which checks the range (rows 16 to 1,000,000, bytes 64 KiB to 1 GiB) when the app is built. Expired rows are released first, and a write releases every expired row at most once a minute, so the memory a quiet bot holds follows what is live rather than the busiest hour it ever had. MemoryState::stored_rows reports the row count, expired rows included. Keys hash with the standard library’s randomly keyed hasher.

The SQLite store

Section titled “The SQLite store”

Enable the sqlite feature of muss-teams. SQLite is compiled in (rusqlite with bundled), so a build needs a C compiler and no system library.

  • Atomicity: each write, and each unit of work with its result, runs in one immediate transaction. An error or a crash before the commit leaves nothing behind.
  • Durability: WAL mode with synchronous = FULL. A committed result survives a restart and replays once.
  • Workers: writers serialise on SQLite’s write lock, across threads and across processes sharing the file, waiting up to five seconds.
  • Migrations: the schema version is recorded in the file, and each migration runs in a transaction that records its version. A database written by a newer library is refused with SchemaTooNew. Never edit a shipped migration; append one.
  • Async code: the ports are synchronous and block on disk. Call them from tokio::task::spawn_blocking.
  • Not bounded by count: SQLite rows are bounded by expiry and SqliteState::sweep_all_expired, not by a row cap. Run the sweep on a schedule. A flood of unexpired writes can grow the file.
  • Permissions: the file is as private as its directory. Restrict it.

Platform notes

Section titled “Platform notes”

Paths use std::path::Path, so spaces and Unicode work (tested). A store closes its handles when dropped, which lets a Windows process delete the file afterwards (the test removes it). The Windows MSVC build compiles the bundled SQLite with the system C compiler; it has not yet run on a Windows runner, as the CI workflows have not run anywhere.

Verification

Section titled “Verification”

One contract suite (tests/contract/mod.rs) runs against both stores: compare-and-set, expiry, tenant isolation, purge, sweep, deduplication, idempotent replay, rollback of failed work, eight racing threads, outbox ordering, lease expiry, wrong-owner completion, attempt limits and claim bounds. The memory store adds limit tests. The SQLite store adds restart recovery, a failed command before restart, two connections on one file, migration from version 1, refusal of a newer schema, and Unicode paths.

Records the notifier keeps

Section titled “Records the notifier keeps”

Proactive notifications (see the notifications guide) add two record kinds beside the conversation reference. notification holds the attempt under an idempotency key - started, delivered or ambiguous - and user-conversation remembers the one-to-one chat opened for a person. Both are tenant-scoped like every record, expire with the store’s default retention, and hold identifiers and a digest, never message content. The outbox entry of a queued notification does hold the message, because it has to be sent later; treat the outbox as application state.
