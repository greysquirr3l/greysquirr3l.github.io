Microsoft Graph

The graph feature adds two clients, one for each kind of authority Graph accepts. It is off by default and adds no dependency.

Which client

Section titled “Which client”
ApplicationGraph DelegatedGraph
Acts as the app one signed-in user
Token minted from the registration’s credential for the Graph audience handed in by your DelegatedTokenProvider
Permissions application permissions an administrator granted delegated permissions the user consented to
me() not available available

A method that only makes sense for one of them exists only on that one. A program that calls me() on an ApplicationGraph, or builds a DelegatedGraph from the app’s credentials, does not compile. Neither client requests consent, installs anything or widens a grant: a missing permission is a 403 that names what the operation needs.

Reading users

Section titled “Reading users”

from_env reads TEAMS_APP_ID, TEAMS_TENANT_ID and TEAMS_CLIENT_SECRET, as TeamsClient::from_env does. Building a client sends nothing.

Each typed operation is recorded in the compatibility matrix with its endpoint, version, the permission each client needs, the cloud, the account type and the page it was read from. A test keeps that table and the code in step.

Activity-feed notifications

Section titled “Activity-feed notifications”

A feed notification appears in the recipient’s activity feed. It is not a chat message, and it does not deliver a bot reply.

The manifest is what makes the send safe to attempt. An activity type the manifest does not declare is refused before any request goes out, as is a template parameter set that does not match the template that activity type declares. The actor parameter is never asked of the caller: the service fills it in with the caller’s name.

A topic either names a Graph resource, which is the form the service expects when the notification is about a team, a chat or an installation, or carries text with a Teams deep link behind it:

A deep link is refused unless it is an HTTPS address on teams.microsoft.com and has one of the shapes Teams publishes.

Each of the three targets has its own permission, and the SDK never widens it: an application client needs TeamsActivity.Send.Group, .Chat or .User according to the target, and a delegated client needs TeamsActivity.Send. A 403 names the one the operation needs.

The SDK does not install the app, does not request consent, and does not check whether the app is installed for the recipient. That is the service’s answer to give, not the SDK’s to guess.

Change-notification subscriptions

Section titled “Change-notification subscriptions”

A subscription is a standing request: “post to this URL when this resource changes”. The service holds it until it expires, so the app has to renew it before then, or create a new one.

The SDK watches two resources: the messages of one channel and the messages of one chat. Others are added only after their contract has been read.

Describe what to watch with a SubscriptionRequest, then hand it to SubscriptionKeeper::watch. watch creates the subscription and records it in the tenant’s state, so it is renewed and survives a restart. graph.subscriptions().create(..) alone only sends the request: it stores nothing, so nothing renews that subscription and a restart forgets it. Use it only if you keep your own records.

A request is checked before anything is sent. It is refused when the resource path is not one of the two, a change type is missing or repeated, the notification or lifecycle URL is not an https address without a fragment or user name, the client state is over 128 characters, the lifetime is over the resource’s 4,320 minutes or under the 45 the service rounds up to, or the lifetime is over an hour and there is no lifecycle URL. Exactly an hour needs none. The lifecycle URL cannot be added later, so a subscription made without one is renewed an hour at a time.

get, renew and delete take the subscription’s identifier and resource kind (renew takes the Subscription itself). renew sends one PATCH with only the new expiry; a 404 means the subscription is gone and a new one has to be created.

Keeping them alive

Section titled “Keeping them alive”

SubscriptionOwner stores each subscription, and the plan for it, under the tenant. SubscriptionKeeper creates and records subscriptions with watch, and renews what is due with sweep:

If watch fails with WatchError::NotRemembered, the service did create the subscription but the state store refused the record. The error names the subscription and carries it.

Behaviour, all of it driven by the clock you pass, so a test needs no sleep. A sweep reads the clock once per subscription, so a renewal that waits on the network does not leave the next one with a stale lease:

  • A renewal is planned 12 hours before expiry, brought forward by up to 25 percent jitter, and persisted with the subscription. A restart reads the plan back; nothing is renewed twice and nothing is forgotten.
  • Before acting, a worker claims a two-minute lease with a version-checked write. Of two workers, one wins and the other skips; a worker that crashed loses its lease when it ends. Give each worker its own name.
  • 429 waits for the Retry-After (up to an hour). 401 and transient failures back off from 30 seconds, doubling to 15 minutes, with jitter. Five failures stop the schedule and tell the hook. 403 stops it at once (a person has to grant the permission), and 404 marks the subscription lapsed, because it cannot be renewed. Each retry fetches a fresh token.
  • The SDK starts no background task. sweep is a call you make on your timer, so there is nothing the SDK owns that would need a cancellation token or a joined shutdown.

SubscriptionOwner::recovery is the quick restart check: which subscriptions are due for renewal and which have lapsed.

The state store holds a secret. A subscription’s client state is the value the service echoes to prove a notification is genuine, and the keeper has to compare it, so the record stores it in the clear. Protect the store the way you protect a credential. The SDK keeps the value out of every Debug output, log line and error text, but it cannot protect the store for you.

Lifecycle notifications

Section titled “Lifecycle notifications”

The service posts reauthorizationRequired, subscriptionRemoved and missed to the lifecycle URL. Parsing and answering the request belong to the webhook ingress; once you hold an authenticated body, hand it to the keeper:

The keeper checks the tenant and the echoed client state first; a notification that fails either does nothing.

  • reauthorizationRequired renews with one PATCH, which also reauthorizes.
  • subscriptionRemoved tells the hook, then marks the subscription removed. The SDK does not recreate it.
  • missed tells the hook. The SDK does not replay or resync what was missed: no delta query is documented for these resources, so re-reading the resource is the application’s job.

Permissions come from the resource, not the endpoint, so a 403 names the one that resource’s contract lists. Chat and channel messages differ.

Receiving change notifications

Section titled “Receiving change notifications”

Register a handler and the app answers Graph for you:

With a handler registered, router() serves two more URLs next to /api/messages:

URL For
/api/graph/notifications (GRAPH_NOTIFICATION_PATH) the subscription’s notificationUrl
/api/graph/lifecycle (GRAPH_LIFECYCLE_PATH) the subscription’s lifecycleNotificationUrl

Both do the same thing, so either may carry either kind of notification. On another framework, call BuiltApp::handle_graph_webhook(query, body). Without a handler neither URL exists. Create the subscription with BuiltApp::graph_webhooks().watch(request): it records the subscription for this app, and picks a random client state when you give none. A subscription made any other way is not recognised, and its notifications are dropped.

The handshake

Section titled “The handshake”

When a subscription is created, Graph sends POST {url}?validationToken=.... The app answers 200, text/plain; charset=utf-8, with the decoded token as the body, inline: no storage and no network. The token is never HTML-escaped or wrapped in JSON, because Learn says an encoded token fails validation. The answer carries X-Content-Type-Options: nosniff and Cache-Control: no-store.

What happens to a notification

Section titled “What happens to a notification”

Graph does not sign these requests. What replaces authentication is that every item must match a subscription this application created, before anything is written:

  1. the item parses (bounded body of 256 KiB, 128 items, each item read alone);
  2. its tenant is the app’s tenant;
  3. the subscription is in this app’s state, under this tenant, and was recorded by this application id;
  4. the subscription has a client state, and the item echoes it (compared in constant time);
  5. the change type is one the subscription asked for;
  6. the item’s resource is a message of the watched channel or chat, and resourceData.id agrees with it.

An item that fails any step is dropped and counted, and the application hears about it through on_graph_fault as GraphFault::Refused. The sender is not told which step failed: the request is still answered 202, so a stranger cannot probe for subscriptions or client states. A body that is not a collection is 400, one over the limit 413.

The believable items are written to a bounded durable queue (the state store, in its own lane, so the proactive-notification outbox never sees them), and only then is the request answered 202. If the write fails, stalls past the acceptance deadline (2.5 s by default; Graph waits 3 s), or the queue is full, the answer is 503 with Retry-After, and Graph retries for up to 4 hours.

A worker owned by the app then claims entries and runs your handler: at most workers at once, each under handler_timeout, each in its own task so a panic is contained. A handler that returns an error, panics or runs over time is tried again when its lease ends, up to attempts times. After the last, the notification is poison: a record is kept for poison_retention (7 days), the entry leaves the queue so it cannot block the rest, and GraphFault::Poisoned is raised. WebhookLimits sets every bound; each is clamped into a range.

Rich notifications

Section titled “Rich notifications”

A rich notification carries the changed resource, encrypted for your app. Turn it on with three things: a certificate, its private key, and a handler.

Paging

Section titled “Paging”

users().list(..) returns a Pager. next_page() fetches one page; collect_all() fetches the rest. Every walk is bounded (20 pages and 2,000 items by default, changed with with_page_limits), and a walk that would pass a bound stops with a PageLimit error: a shortened list is never returned as if it were the whole one.

The link to the next page is followed only if it points at the Graph root’s own scheme, host and port, under the same API version, with no user name or fragment. Anything else ends the walk with an error and no request is sent, so the bearer token never goes anywhere else. Dropping the pager, or the future of a call in flight, stops the walk.

Errors

Section titled “Errors”

Every failure is a GraphError:

  • a service answer carries the HTTP status, the OData code, a clipped message with credentials removed, the request id Graph reported and the client-request-id the SDK sent, so the failure can be matched to Microsoft’s logs;
  • a 403 on a typed operation names the permission its contract requires;
  • a throttle is waited out for as long as the service asked, up to a bound, and a longer wait is returned to you as RateLimited with the delay;
  • applied_state() says whether a failed call may have changed anything. A refusal, a throttle and a request the SDK would not build did not. A write that met a server error or lost its answer is Unknown: it is never repeated for you, and you reconcile it yourself.

The escape hatch

Section titled “The escape hatch”

request(&GraphRequest) sends a request for an endpoint the SDK has no typed operation for. A GraphRequest has a method, a version, a path and a query, and nothing else, so it cannot name another host:

It carries no permission contract: the SDK does not know what the endpoint needs, and a 403 says so. Read the endpoint’s own page before relying on it. A path is plain segments from a small character set, with no .., no %, no ? or #; a query name that looks like a credential is refused.

A write to an installedApps path, or to $batch (which can carry one in its body), is refused here with an error that points at app_installs(): installing or removing an app needs an InstallApproval made for that exact request, and the escape hatch must not be a way round it. Reads of installedApps still work.

beta needs allow_beta() on the client. Microsoft documents beta APIs as subject to breaking change and unsupported in production, and no typed operation uses them.

Not covered

Section titled “Not covered”
  • Sovereign clouds. Only the public cloud’s graph.microsoft.com is used; asking for another is an error.
  • Anything not in the compatibility matrix. A live Graph answer has not been seen: every body in the tests and the example is a sample from the Learn pages, served by a loopback server.
  • Signing a user in is the sso feature. UserSession::graph() returns a DelegatedGraph fed by the person’s sealed session. You can still hand in your own DelegatedTokenProvider.
  • A live rich notification. The payload vector comes from OpenSSL and the tokens are minted locally; no real tenant, certificate registration or validation token was used. Only Teams chatMessage on the two watched paths and a single user’s presence are typed.
  • Meeting subscriptions, bulk presence subscriptions, tenant-wide getAllMessages paths, and beta resource-specific consent for chats.
  • A live Graph call. Every subscription answer in the tests is a sample from the Learn pages; no subscription has been created against a real tenant.

Run cargo run -p muss-teams --example graph --features graph,test-utils to see it against a loopback server. It is labelled a simulation, as are examples/graph_rich.rs and examples/graph_webhook.rs.

The full list of types, errors and settings is in the public API.
