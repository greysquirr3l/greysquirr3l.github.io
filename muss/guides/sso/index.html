Teams sign-in and delegated Graph

Sometimes a bot has to act as the person it is talking to: read their profile, their calendar, their files. That needs a token for that person, not the bot’s own. muss-teams gets one in the way Teams documents: Teams already holds a Microsoft Entra token for the person and offers it to the bot, and the bot exchanges it for a delegated token with the on-behalf-of flow. When that silent route is not available, the bot sends a sign-in card and runs an authorization code flow with PKCE.

Sign-in is opt-in and denies by default. Nothing is exchanged until the application registers an authorization hook that says the person may sign in, and the SDK asks for the scopes you name, never a broad default.

Turn it on with the sso feature. The delegated Graph client it feeds (UserSession::graph) needs graph as well.

Three identities that stay apart

Section titled “Three identities that stay apart”
Identity What proves it What it is used for
The application The bot’s client secret or certificate Asking the identity platform for a delegated token
The channel The signed Bot Framework token on every activity Saying who is chatting, in which tenant
The person The SSO token, then the delegated tokens issued for it Acting as that person, and only that person

The SDK never mixes them. The SSO token is verified and then exchanged; it is never sent to Microsoft Graph. The bot’s Connector token is never used for a person. A decoded token is not proof: its signature is checked against the tenant’s published keys before any claim is read.

Set it up once

Section titled “Set it up once”

This part is configuration in your tenant. The SDK does none of it for you, and nothing here has been run against a live tenant (see Not verified).

  1. Register an app in Microsoft Entra ID. It is the same registration as the bot, or a separate one if the bot runs on a managed identity. The application ID URI is api://botid-<bot id>.

  2. Add the delegated permission your Graph calls need, and grant admin consent where the scope needs it.

  3. Expose an API on the registration with the application ID URI as its scope, and allow the delegated permission for that scope.

  4. Give the bot a credential: a client secret, or a certificate (ClientAuth::certificate). A secret read from the environment is ClientAuth::secret_from_env("NAME"). It is never written in source.

  5. For the fallback, register a redirect URI of type Web for a page your application serves over HTTPS.

  6. Update the app manifest. Add webApplicationInfo with id set to the registration’s client id and resource set to the application ID URI, and add the host of your redirect page to validDomains:

    webApplicationInfo needs manifest version 1.5 or later. SSO for a bot works in personal and group chat, not in a channel.

The bot pages Microsoft publishes describe a setup that also creates an OAuth connection on the Azure Bot resource and lets the Bot Framework Token Service do the exchange. muss-teams does not use the Token Service: the bot exchanges the token itself with the identity platform, so the Azure Bot OAuth connection and https://token.botframework.com in validDomains are not needed. The tradeoff is that the bot holds a client secret and you own token storage.

The shortest program

Section titled “The shortest program”

examples/sso.rs is a complete, compiled program, and tests/example_sso.rs runs it against a simulated Teams, a token endpoint and Graph on the loopback interface.

What happens, silently

Section titled “What happens, silently”

  1. The person messages the bot. sign_in finds no session, checks the authorization hook, and sends an OAuth card. The card names a connectionName and a tokenExchangeResource whose uri is your application ID URI.

  2. Teams sees the resource, gets an Entra token for the person with audience your application, and sends signin/tokenExchange:

  3. The SDK reads the invoke, finds the person from the signed activity (not from the invoke), and checks, in this order, and stops at the first that fails:

    1. the authorization hook says yes (no hook, no);
    2. the connection name is the one on the card;
    3. the token is a well-formed RS256 JWT whose kid names a key the tenant publishes, and the signature verifies against that key;
    4. it is a version 2.0 token, issued by https://login.microsoftonline.com/<tid>/v2.0 where <tid> is the configured tenant, and tid is the configured tenant;
    5. aud is this application’s client id or its application ID URI;
    6. it has not expired and is not yet valid (60 seconds of clock skew);
    7. scp carries access_as_user (or the scope you set);
    8. its tenant and oid are the activity’s tenant and sender. A genuine token for somebody else is not exchanged.

  4. One on-behalf-of request goes to the fixed authority of the configured tenant (https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token) with the application’s own credential, asking for the scopes you named. The token is the request’s assertion. Redirects are refused: a token request carries the secret in its body.

  5. The delegated tokens are sealed and stored. Teams is answered 200:

    On any failure the answer is 412 with the same body and a failureDetail that is a fixed sentence chosen by the SDK. Teams then shows the card’s sign-in button. The sentence never holds the identity platform’s text.

What happens, with the fallback

Section titled “What happens, with the fallback”

When the silent route does not answer 200 (the person has not consented, or a step-up is needed), Teams shows the card’s Sign in button. This is the flow Microsoft calls “Authentication flow for bots”:

  1. sign_in made a state (256 random bits, kept server side, good for ten minutes, usable once), a nonce (256 more, also kept server side) and a PKCE verifier (kept server side), and put the authorize address in the card’s button. The request asks for openid profile as well as your scopes, so the token endpoint returns an id token that says who signed in. With keep_refresh_tokens() it asks for offline_access too, so the session outlives its access token.
  2. The person signs in at the identity platform. It returns the browser to your redirect page with code and state.
  3. Your page calls Sso::complete_callback(code, state). The SDK consumes the state, redeems the code with the verifier, and checks who signed in before it keeps anything (next section). Then it holds the token as provisional: tied to the person who started the sign-in, and unusable. You get a verification code.
  4. Your page calls notifySuccess(<verification code>). Teams closes the window and sends signin/verifyState with { "state": "<code>" }.
  5. The SDK compares the code with the one stored for this person. A match turns the provisional token into a session. Anything else deletes the provisional token. Either way the code works once, and it times out after five minutes.

The account that signs in must be the person who is chatting

Section titled “The account that signs in must be the person who is chatting”

A browser may be signed in to a different account from the one in the Teams chat (a shared machine, a second profile). Without a check, that account’s code would be redeemed and its delegated token stored for the person who asked for the card. So the id token that comes back with the code is verified, and each of these must hold, or nothing is stored:

  • its signature verifies (RS256) against the tenant’s published keys, by kid;
  • it is a version 2.0 token issued by https://login.microsoftonline.com/<tid>/v2.0, where <tid> is its own tid and is the configured tenant;
  • aud is this application’s client id (in an id token the audience is the app’s Application ID);
  • it has not expired and is not yet valid (60 seconds of clock skew);
  • nonce is the one this sign-in sent. Each sign-in has its own, so a token minted for another sign-in is refused;
  • oid and tid are the person who started the sign-in: the sender of the Teams activity that asked for the card.

Every failure (another account, another tenant, a missing, forged, expired or replayed token) gives the same typed answer, SsoError::Callback(CallbackRefusal::WrongAccount), and the same sentence for your page to show: “the account that signed in is not the account chatting in Teams; sign out of the other account in the browser and start again”. It names no account and no check. The one exception is a key set that cannot be read, which is the identity platform’s trouble and is Unavailable. The authorization code has been spent by then and nothing waits for Teams.

azp is not read. For a version 2.0 id token it names the client that asked for the token, and Entra only issues a code to the client id in the request and only redeems it for the same client with its credential, so the application’s own redemption is already the proof.

Your page is small. The Rust side is one call:

If the page cannot finish, call authentication.notifyFailure("reason").

Without redirect_uri the fallback is off: the card has no button, and only silent SSO works.

Consent and step-up are typed outcomes

Section titled “Consent and step-up are typed outcomes”

A refused sign-in is never a silent fallback. The person is told a fixed sentence; your application hears the reason as a typed value through on_sign_in_refused:

SsoError The identity platform said What to do
ConsentRequired(need) AADSTS65001, consent_required The person signs in with the card’s button and accepts. For scopes only an administrator can approve, need.admin_consent_url() is the address an administrator uses. It grants those permissions to the whole tenant, so the SDK shows it to you and never sends anyone there.
InteractionRequired interaction_required, AADSTS50076, 50079, 50158 A step such as multifactor authentication is needed. Send the card again.
SessionEnded AADSTS50173, 70008, 700082, 500133 The refresh token is revoked or lapsed. Send the card again.
ApplicationCredential invalid_client, AADSTS7000215, 7000222, 7000218 A deployment problem: the client secret or certificate is wrong or expired. It is also reported to the failure observer.
InvalidScope AADSTS70011 The scopes do not match the registration. Reported to the failure observer.
Refused(_) (the SSO token itself) The token’s audience, tenant, signature, lifetime, scope or user was wrong. The reason names the check.
Callback(_) (the fallback) The state was unknown, used or expired; there was no code; the verification code did not match; nothing was waiting; or the account that signed in is not the person chatting (WrongAccount).
Denied (your hook) The authorization hook said no, failed or ran out of time. When it says no for a session that exists, the session is deleted.
TooManyAttempts (the SDK) See below.

None of these carries a token, a code or the identity platform’s error_description, which holds trace identifiers.

Where tokens live

Section titled “Where tokens live”
  • Sealed first. Every session is sealed with AES-256-GCM before it goes to the store, with a fresh random nonce each time and the tenant, application, person and scopes as authenticated data. A record copied into another person’s slot, another application’s or another scope set does not open.
  • Memory by default. The default vault is in memory, bounded to 10,000 sessions, and forgets everything on restart. A restart signs everyone out. That is deliberate: a refresh token is a long-lived secret, and an in-memory store leaves none on disk.
  • A vault of your own. For sessions that survive a restart, implement SessionVault (put, get, delete; every call carries the AuthContext and must be scoped to its tenant) and give it to SsoConfig::vault. The vault holds ciphertext only. What it must protect is availability and integrity, and it must forget at ttl. Give SsoConfig::seal_with a SealingKey from your secret store (SealingKey::from_env("NAME") reads 32 bytes of base64), or after a restart the sessions will not open. Persistent secrets belong in an OS keyring or a secret manager, not a generic JSON column.
  • Rotating the sealing key. Each sealed record starts with a version and the id of the key that sealed it (the first four bytes of a SHA-256 over a label and the key, which reveals nothing usable). To rotate without signing anyone out, give the new key to seal_with and keep the old one with SsoConfig::previous_seal_key: records under either key open, and new ones (and renewed ones) are sealed under the new key. Drop the previous key once a session’s longest life, 24 hours, has passed. Without the previous key a record under the old key fails to open, is removed and the person signs in again, which is the safe failure. previous_seal_key without seal_with is a configuration error.
  • Refresh tokens are opt-in. keep_refresh_tokens() adds offline_access to both routes: the silent exchange and the sign-in fallback. Without it a session lasts as long as its access token (about an hour), and an expired session ends.
  • No token reaches you. UserSession holds no token and has no accessor for one; DelegatedToken can be built by you but only the SDK can read it. The delegated Graph client asks for a fresh token before each call, and the SDK renews a token with less than 60 seconds left, once for any number of concurrent callers.
  • Nothing prints one. Debug and Display of every type here show placeholders. A test formats the whole flow and looks for each secret.
  • Plaintext copies. The decrypted record and its buffers are wiped when they are dropped, as is the sealing key. The token strings the rest of the flow holds are muss-core’s Redacted<String> and the Graph client’s token value, which do not zeroize on drop, and a token also passes through the HTTP client’s request buffers. The SDK keeps these copies short lived but does not wipe them; a core dump or swap file of the process can hold a token that was in use. Treat the host as holding live tokens.
  • sign_out deletes the session. Revoking the tokens at the identity platform is the administrator’s tool (revoke sessions), not this SDK’s.

Withdrawing access

Section titled “Withdrawing access”

A session is only as good as the authorization behind it, so the hook is asked again every time a session is used or renewed, not just when it is created. The hook gets AccessPurpose::Use and the same SsoAccess (the authenticated activity, the person, the scopes) it gets at sign-in.

Use The hook is asked
Sso::sign_in finds an existing session once, before the session is returned
Sso::session once, before the session is returned
UserSession::ready once per call
UserSession::graph (every Graph call it makes) once per call, before the token is fetched
A renewal (a refresh token redeemed) before it, as part of the use that needs it

Nothing is cached between calls: the hook is the source of truth, and a person removed from your directory or your allow list stops working on their next use. The price is one hook call per use, bounded by the sign-in timeout (SsoConfig::timeout, 10 seconds by default). Keep the hook cheap, or cache inside the hook, where you can judge how stale an answer may be.

  • If the hook says no, the use fails with SsoError::Denied and the person’s sealed session (with its refresh token) is deleted. Allowing the person again does not bring it back; they sign in again. A denied person has no refresh token redeemed.
  • If the hook fails or times out, the use fails with SsoError::Denied but the session is kept: an outage in your directory is not a revocation.
  • A session that nobody uses is never asked about. It sits sealed in the vault until its time to live (24 hours with refresh tokens, otherwise the access token’s life), and nothing can read it without a signed activity from that person, whose first use asks the hook.
  • The SDK does not call the identity platform to revoke refresh tokens; an administrator does that when a person leaves.

Limits and protections

Section titled “Limits and protections”
What Bound Why
Concurrent sign-in invokes 16 (1 to 1,024); more get 503 Backpressure, not buffering
Time for one invoke 10 seconds (1 to 60); late work is cancelled and its slot freed Teams waits on the answer
Exchanges in flight per person 1 A duplicate waits and then gets the first answer
A finished exchange id Remembered 10 minutes (2,048 ids) A duplicate costs no second exchange; a remembered 200 is repeated only while the session exists
Failures per person 3 in 10 minutes per route (signin/tokenExchange and signin/verifyState each have their own count), then 412 with no call to the identity platform or your hook Loop protection. Routine consent failures on the silent route must not lock out the fallback that exists to fix them, and wrong verification codes must not lock out the silent route
A timed-out exchange 412 with the { id, connectionName, failureDetail } body and the sentence “Sign-in took too long. Try again.” The documented body; verifyState has none
Authorization hook Bounded by the invoke timeout on every call A hook that hangs must not hang a Graph call
Fallback sign-ins in progress 1,024; 4 per person; 10 minutes each Bounded table
Waiting verification 5 minutes, one per person
Sessions in the default vault 10,000
Token size 16 KiB in, 32 KiB out
Scopes 1 to 16, named; .default is refused No broad request by default

Teams can send the same signin/tokenExchange more than once, for example from a second client of the same person. The Microsoft pages do not describe the behaviour, so the SDK’s rule is the one in the table: the first one runs, the others get its answer.

Testing without a tenant

Section titled “Testing without a tenant”

With the test-utils feature, SsoConfig::test_keys supplies the keys SSO tokens are checked against and SsoConfig::test_authority points the token endpoint at a loopback server. Verification still runs in full; only where keys and the endpoint come from changes. tests/sso/ is the suite: every invoke, every refusal above, replay, cross-person reuse, tampering and leaks.

Not verified

Section titled “Not verified”

No tenant, registration, bot or Teams client was used. Everything is checked against Microsoft’s published payloads and against loopback stand-ins, which prove the SDK’s behaviour, not Microsoft’s. In particular nothing confirms:

  • that Teams offers its token to a bot whose OAuth card does not come from the Bot Framework Token Service, and that the client then treats 200 as signed in;
  • the signin/verifyState payload beyond state as a string (Microsoft’s pages name the invoke and the code; the field name is from the Teams SDK reference), and that Teams answers a 412 to it as the SDK expects;
  • the exact aud of the token Teams sends (the application’s client id for a version 2.0 token, or the application ID URI; the SDK accepts both);
  • what the identity platform answers for each consent case in a real tenant;
  • that the id token returned by the token endpoint for a plain response_type=code request carries the nonce sent to /authorize. Microsoft requires nonce for the hybrid flow and says the claim “matches the parameter included in the original authorize request”, and OpenID Connect Core says the nonce is echoed whenever it was sent; no page states it for the token endpoint’s id token. If it is absent in a real tenant the SDK fails closed (every fallback sign-in is refused as WrongAccount), which would show on the first live run;
  • that profile is what makes oid appear in the id token (the claims reference says so; the SDK asks for openid profile);
  • that the id token is signed RS256 with a key of the tenant’s key set when redeemed at the token endpoint. Microsoft’s refresh-token example shows an unsigned (alg: none) id token and calls it “unsigned”, which the SDK refuses; the code-redemption page shows a signed one’s claims.

Live acceptance is blocked: no configured nonproduction tenant exists.

Not covered

Section titled “Not covered”
  • Message extension sign-in. A search extension that answers composeExtension: { type: "auth" }, and the config response, are not built. The sign-in here is for the bot conversation. An extension can still read a session with Sso::session(ctx.activity()).
  • 401 sign-in responses to Action.Execute. The card action pipeline does not answer with a login response; a handler can send the sign-in card with Sso::sign_in from a message.
  • Tab SSO (getAuthToken in a tab). That is a browser flow with a different token audience; this feature is for the bot.
  • Several tenants, personal accounts and sovereign clouds. Refused.
  • Channel scope. Microsoft’s pages say SSO for a bot is not supported there.
  • Revoking tokens at the identity platform on sign-out.
