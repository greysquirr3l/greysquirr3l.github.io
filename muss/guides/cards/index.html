Adaptive Cards

muss-teams builds Adaptive Cards with a fluent builder, reads them from JSON without losing anything, and checks both the same way. Handling the button presses is in card actions.

examples/card.rs is this program. It prints the JSON and sends nothing.

Sending a card

Section titled “Sending a card”

A card is a message. In a handler, ctx.reply(card).await? sends it as a reply. To send without a bot, client.send(&to, &OutgoingMessage::from(&card)) does the same, and OutgoingMessage::new().text("Approval needed").attach(&card) adds a line of text above it. TeamsClient::update replaces a card you sent with another.

The card goes out as an attachment with the content type application/vnd.microsoft.card.adaptive. A message that holds only a card carries no text.

What the builder covers

Section titled “What the builder covers”
Method Element Schema version
text, heading TextBlock (heading style is 1.5) 1.0, 1.5
facts FactSet 1.0
image(url, alt_text) Image 1.0
media(alt_text, sources) Media 1.1
container, columns Container, ColumnSet 1.0
actions ActionSet 1.2
input_text, input_number, input_date, input_time, input_toggle, input_choice Input.* 1.0
open_url, submit, execute, show_card, toggle_visibility actions 1.0, 1.0, 1.4, 1.0, 1.2
refresh the card’s refresh section 1.4
raw, raw_property anything else, kept as written n/a

Modifiers apply to the element added just before them: id, hidden, separator, subtle, bold, and for inputs label, placeholder, required, default_value, multiline, max_length, multi_select, expanded. For actions, tooltip, secondary, fallback_submit and fallback_drop. A modifier that does not fit the element before it is not silently ignored: build() names it.

The version column comes from the published schema; see compatibility.

The version is worked out for you

Section titled “The version is worked out for you”

Without .version(..), the builder declares the lowest version that carries everything in the card. A text-only card is 1.0; adding a label makes it 1.3; an execute button makes it 1.4. The highest version Teams renders for a bot card is 1.6, and a card that declares more is refused.

To keep an older Teams client working, declare a lower version and give the newer features a fallback, as Microsoft documents:

The fallback is an Action.Submit that sends the same data, so the bot has to handle both forms. Microsoft recommends wrapping Action.Execute in an ActionSet for this, as above.

Errors name the field

Section titled “Errors name the field”

CardError::path() returns the JSON path (body[1].id) and CardError::problem() says what is wrong. An empty path means the card as a whole.

What build() and Card::from_json refuse:

  • an input with no id, or an id used twice anywhere in the card, including in different containers, columns, table cells or Action.ShowCard elements (the second use is reported). A fallback element may reuse its own element’s id, and no other;
  • a fallback that is not text, an element or an action;
  • an input id that is also a field of an action’s hidden data, because the two are merged when the user submits;
  • a link that is not https, or that has surrounding whitespace or a control character (an image or background may also be an inline data:image/png|jpeg|gif;base64,... URI, and an action icon may be icon:Name). Links are checked everywhere the schema puts one: images, ImageSet images, Table cells, RichTextBlock runs, every action and selectAction, iconUrl, media sources, every backgroundImage (a link or an object with a url, on the card, a container, a column, a table cell or a ShowCard) and fallback bodies;
  • a choice list with no choices, a column width that is not auto, stretch, 48px or a weight, an Action.Execute with an empty verb;
  • a refresh that names more than 60 users;
  • action data that is not an object or text, or cannot be serialized;
  • a feature newer than the declared version, a version below 1.0 or above what Teams renders, nesting deeper than 32 levels, and a card larger than 100 KB measured as UTF-16.

There is no separate count of elements: text is read up to 1 MiB and a card over 100 KB is refused before it is walked, and the smallest element takes a dozen bytes, so those caps already bound the walk.

Notices: what was kept but not vouched for

Section titled “Notices: what was kept but not vouched for”

A card can be fine and still deserve a note. Card::notices() lists them, each with a path:

  • an element or action type the SDK does not know. It is kept exactly as written; the SDK does not claim Teams renders it;
  • isEnabled on Action.Submit and positive or destructive action styles, which Microsoft documents Teams as ignoring;
  • more than six primary actions (the rest go to an overflow menu);
  • an input with no label, and an image with no altText, which hurt assistive technology;
  • Media, whose Teams rendering the Microsoft pages do not state;
  • a card within 20 KB of the size limit.

Reading JSON

Section titled “Reading JSON”

Card::from_json is the escape hatch. It checks the card, then keeps every property it was given, including ones this SDK has never heard of, so a property added to the schema next year survives a round trip. It reads text of at most 1 MiB. Key order in the output is alphabetical, not the order of the input; the content is the same.

A card must declare its version. Microsoft’s own pages show samples without one, and the SDK refuses them with the line to add.

The checks walk into ImageSet, RichTextBlock, Table rows and cells, background images and fallback bodies (on elements, columns, table rows and table cells). They do not look inside a Table’s column definitions, which hold no links, ids or actions, or inside an element type the SDK does not know (that one is kept and gets a notice).

The builder reproduces Microsoft’s published samples except for three deliberate differences: it always sets wrap, it writes a refresh action without the title the sample gives it, and it writes an Action.Execute fallback as an object where the Universal Action Model sample writes a string. The tests say so where they compare.

What the SDK cannot tell you

Section titled “What the SDK cannot tell you”

It does not render. It cannot say how a card looks on desktop, web or mobile, whether text truncates, or whether an image address returns a supported image (Teams wants PNG, JPEG or GIF up to 1024 by 1024 pixels and 1 MB, with no redirect). Test the cards you ship on the clients you support. The card checks are structural.

No card has been shown by a real Teams client in this project. Every card in the test suite was checked against the SDK’s own rules and Microsoft’s published payloads, which prove the SDK’s behaviour, not Teams’.

Hidden data is not a permission

Section titled “Hidden data is not a permission”

execute and submit take data. It is invisible to the user, but it travels through the client, so a user, a script or another app can change it. A handler must authorize the person pressing the button and re-check the object the data names. The card cannot do that for you.
