Meetings and presence

muss-teams turns the four Teams meeting events into typed async handlers, reads a meeting’s details and one participant through the Bot Connector, reads a user’s presence through Microsoft Graph, and keeps a presence subscription alive with the same keeper that renews the Teams message subscriptions.

Nothing here has been run against a real tenant. The example and the tests use the shapes the Microsoft Learn pages publish, served by a loopback server.

Meeting events

Section titled “Meeting events”
Method Event Payload
on_meeting_start application/vnd.microsoft.meetingStart MeetingSummary: title, type, join link, actual start
on_meeting_end application/vnd.microsoft.meetingEnd MeetingSummary: the actual end
on_meeting_participants_joined application/vnd.microsoft.meetingParticipantJoin MeetingParticipants: members with role and presence
on_meeting_participants_left application/vnd.microsoft.meetingParticipantLeave MeetingParticipants
on_meeting any of the four with no handler of its own MeetingEvent

What the SDK checks before a handler sees an event:

  • the activity is authenticated, and the tenant it names is the one the app’s trust model approved for; an event from another tenant never reaches a handler.
  • a join or leave event names at least one member, at most 256, and each has a Teams user id. Anything else is refused with a 400, not delivered empty.
  • a title, join link or time that does not parse is left out of the typed value and stays in the raw activity. A join link must be https.

What the manifest needs

Section titled “What the manifest needs”

Teams sends the events only to an app whose manifest asks for them. The exact permissions are data you can check:

Events Resource-specific consent permission (Application) Also
start, end OnlineMeeting.ReadBasic.Chat or ChannelMeeting.ReadBasic.Group webApplicationInfo in the manifest
join, leave OnlineMeetingParticipant.Read.Chat A subscription made in Developer Portal; scheduled meetings only; the bot must be in the meeting first

The SDK cannot see the Developer Portal subscription, so a missing one looks like events that never arrive.

Reading a meeting

Section titled “Reading a meeting”

A read starts from the activity, never from loose strings:

  • ctx.meeting_target() reads channelData.meeting.id. The conversation id and the Id inside a start or end event are not meeting ids, and a target is refused (MeetingIdMissing) rather than built from them. The target carries the activity’s tenant and service URL, so a read cannot be pointed at another tenant.
  • client.meetings() exists on the client of a built app (app.client()), not on a client built on its own: the hook lives with the app.
  • details is GET /v1/meetings/{meetingId}; participant is GET /v1/meetings/{meetingId}/participants/{participantId}?tenantId=... and takes the person’s directory object id. Do not cache a role: the organizer can change it.
  • The hook sees the operation, the tenant and the meeting. It runs under a five-second deadline in its own task. No hook, a refusal, an error, a panic and a timeout all refuse the read.
  • Errors are specific: Forbidden (403: not installed in the meeting, or blocked), NotFound (404), Throttled with the delay (429, not repeated), Unauthorized, Service, and Decode for an answer without usable details. A read never returns an empty object.

Presence

Section titled “Presence”
Read Client Permission
presence().get(user) application Presence.Read.All
presence().get(user) delegated Presence.Read.All (another user)
presence().me() delegated only Presence.Read

An answer without an id, availability or activity is a Decode error. Availability and activity values the SDK does not name are kept as Other.

Presence subscriptions and change notifications

Section titled “Presence subscriptions and change notifications”

A presence subscription is a different surface with different rules: delegated only, Presence.Read.All, at most 60 minutes, one user per subscription (communications/presences/{id}), change type updated, and resource data: Microsoft Learn advises always specifying the encryptionCertificate “to avoid failure”. The SDK follows the advice conservatively: it always creates a rich subscription and refuses a request without a certificate before anything is sent. That refusal is the SDK’s choice, not a stated service rule. The webhook creates it with the user’s token, keeps it renewed, and delivers its changes to on_presence_change.

What the app has to set, and what happens when it does not:

Missing Result
on_presence_change watch returns WatchError::PresenceHandlerNotConfigured; nothing is created
graph_decryption_keys (with on_presence_change) build fails: “on_presence_change needs graph_decryption_keys”
graph_delegated_tokens watch returns WatchError::DelegatedClientNotConfigured; a lifecycle notification for a presence subscription reaches on_subscription_recovery as blocked
A certificate on the request SubscriptionError::ResourceDataRequired, before anything is sent
The private key of the request’s certificate WatchError::CertificateNotHeld

Delivery goes through the same ingress as every Graph notification: the client state, the tenant, the application and the resource are matched with a subscription this app created before the item is written to the durable queue, and the answer is 202 only after the write.

  • A rich notification waits in the quarantine lane. It reaches the handler only after its validation tokens, certificate and data signature checked out and the decrypted presence was shown to be the watched user’s: the plaintext id must equal the user in the resource path and in resourceData. Another user’s correctly signed presence, a tampered ciphertext and a token for another application are dropped, reported to on_graph_fault with a fixed reason, and never reach the handler. Ordinary items are never held up by the quarantine lane.
  • A basic notification names the user and carries no state; the handler sees availability() and activity() as None. The SDK never creates a basic subscription, but the page documents the payload, so one is delivered.
  • Repeats. The documented presence payloads have no notification identifier, so a repeat cannot be recognised and is delivered again; a notification that does carry an id is skipped as a repeat. Presence also changes often and arrives out of order: read presence().get(user) and compare sequence_number() when order matters.
  • Lifecycle. With a lifecycle URL, reauthorizationRequired renews the subscription with the user’s token; call GraphWebhooks::sweep on your own timer for the half-hour renewals.

The renewal needs the user’s token every time one is due, so a delegated token provider that can refresh is part of running this. Without the facade, the same subscription can be kept by a SubscriptionKeeper over a DelegatedGraph.

What is not here

Section titled “What is not here”
  • Transcripts and recordings. Reading them needs an application access policy and tenant administrator settings that the SDK can neither check nor grant, and a live tenant to prove them. No operation is offered.
  • Application-hosted real-time audio and video. It needs Microsoft’s .NET media library on Windows. It is out of scope for a Rust SDK, not a small missing endpoint.
  • In-meeting notifications, real-time captions, share to stage, bulk presence, the presence writes, sovereign clouds and beta endpoints.

Not verified

Section titled “Not verified”

No meeting event, meeting read or presence read has been seen from a real tenant. Every answer in the tests and the example is a sample from the Learn pages, served by a loopback server. The rows of the compatibility matrix that still need a live run are listed in the compatibility reference.

cargo run -p muss-teams --example meetings --features graph,test-utils plays Teams, the Connector and Graph in one process (it says so) and shows a start event leading to a details read, a join event leading to a roster read the hook refuses, an event naming another tenant refused, a presence subscription renewed by the keeper, and presence changes delivered to on_presence_change. tests/example_meetings.rs runs it.

The full list of types, errors and settings is in the public API.
