Routing bot activities

muss-teams turns an authenticated request into a typed activity, drops repeats, remembers how to reach the conversation, and runs the handler for that kind of activity on a bounded set of workers.

An application does not assemble these pieces. TeamsApp builds the whole pipeline from environment configuration and a few handlers; see the facade. This page describes what is inside it. The pieces stay public for a host that needs to compose them differently.

The pipeline

Section titled “The pipeline”

BotEndpoint::handle(authorization, body, now_epoch_seconds) runs the first three steps and returns a status code (and a Retry-After when the bot is busy). It does not depend on a web framework: pass it the header value and the body bytes. BuiltApp::handle(authorization, body) is the same call with the time taken from the app’s own clock.

A request refused at any step before admission reaches nothing after it. The tests in tests/router/rejection.rs check this for eight kinds of refusal: the store is never called, nothing is queued, and no handler or reply runs.

Status codes

Section titled “Status codes”
Outcome Status
Authenticated, admitted or recognised as a repeat 200
Missing, malformed or untrusted credentials 401
Authenticated but not allowed (tenant, channel, endorsement, destination) 403
Body too large 413
Body is not an activity 400
Queue full 503 with Retry-After: 1
Dispatcher stopped 503
State store full 503 with Retry-After: 30
State store failed 500

The split between 401 and 403 is the one the Bot Connector service expects: a request that could not be authenticated is 401, and a request that was authenticated but is not allowed is 403. A body over 1 MiB is refused with 413 before it is authenticated.

Handlers

Section titled “Handlers”

A handler is an ordinary async function or closure that takes a typed context and returns HandlerResult:

The router holds at most one handler per kind. Each context carries the activity (its provenance and its raw body) and the payload for that kind.

Registration Context payload
on_message MessageBody: text, mentions, how it reached the bot
on_message_update MessageChange: Edited or Undeleted
on_message_delete none
on_conversation_update ConversationChange: members, channel or team change
on_installation_update InstallAction: Add, Remove, AddUpgrade, RemoveUpgrade
on_reaction Reactions: what was added and removed
on_invoke InvokeName
on_meeting MeetingEvent: the four meeting events, typed. on_meeting_start, on_meeting_end, on_meeting_participants_joined and on_meeting_participants_left take their own payloads and win over on_meeting
on_unknown UnknownActivity: the type, and the body is on the activity

Context::reply takes text, a Card, or any OutgoingMessage. Without a reply channel it fails with ReplyError::NotConfigured. A failed reply reaches the handler as ReplyError::Connector, which carries the typed cause, including an outcome the SDK cannot know (AmbiguousWrite) that the handler must not blindly send again.

Which messages a handler gets

Section titled “Which messages a handler gets”

A message handler gets every message in a one-to-one chat. In a channel or group chat it gets a message when it mentions the bot, and it also gets messages that do not when the app holds ChannelMessage.Read.Group or ChatMessage.Read.Chat. MessageBody::delivery() says which case it is:

  • Direct: a one-to-one chat.
  • BotMentioned: a shared conversation and the message mentions the bot.
  • AllHumanMessages: any other message. In a known shared conversation the bot got it only through the resource-specific consent permissions. It was not addressed to the bot, so a bot that replies to every message would be answering a conversation it was not part of.

Teams never delivers messages written by other bots, whichever permissions the app holds. A conversation that does not say what it is (some documented payloads omit conversationType) is never classed Direct.

Unknown activities

Section titled “Unknown activities”

A new activity type, an event type the SDK does not know, or an installationUpdate with an unfamiliar action goes to the handler registered with on_unknown. It is never given to the handler of a similar kind. Without an on_unknown handler the dispatcher counts it as unhandled and runs nothing. The whole body is kept: read an extension property from activity.raw().get("/some/pointer").

Invoke activities are routed and their handlers run. The response an invoke expects is written for two names when the bot registers card action hooks: adaptiveCard/action and application/search are answered in the HTTP response of the request that carried them, and a form submission (a message with an object value and no text) is run through the same hooks. See card actions. Every other invoke name still runs the on_invoke handler and writes no response.

Repeat handling

Section titled “Repeat handling”

Teams redelivers an activity when it does not get a timely answer, so the same delivery can arrive twice. A repeat is acknowledged with 200 and not handled again.

The key is Activity::replay_key(). It answers “have I already handled exactly this?” and must not answer “have I seen this message?”. An edit, an undelete, a delete and a reaction carry the identifier of the message they refer to, so the identifier alone would let the first edit hide every later one. For those kinds the key includes the kind and the timestamp.

An activity that has no usable key is never deduplicated, and neither is an invoke: an invoke expects a response every time, so a repeat is answered again and the handler’s own idempotency decides what it does.

If an activity cannot be admitted (the queue is full, or a state call fails), the mark is removed, so Teams’s retry is accepted. This is deduplication, not exactly-once processing: see state for the outbox pattern when a handler’s side effects must not repeat.

Conversation references

Section titled “Conversation references”

When the bot is installed, receives a message, or is added to a conversation, Ingest stores a ConversationReference (service URL, channel, conversation, scope and the bot’s own id) under the activity’s tenant. An uninstall or the bot being removed deletes it.

References are written only for an activity that passed authentication and the tenant policy, and a tenant cannot read another tenant’s reference. Decode one with decode_reference.

The bounded dispatcher

Section titled “The bounded dispatcher”

The dispatcher has two bounds, set when it is built: how many activities may wait (default 256, at most 65,536) and how many handlers run at once (default 16, at most 1,024). A full queue refuses at once; it never makes the request wait.

A handler that returns an error, or panics, is counted and reported to the optional FailureObserver; the panic is contained to its own task and the next activity runs. shutdown(grace) stops admitting, lets admitted work finish for up to grace, aborts what is left, joins every task and returns a ShutdownReport of handled, unhandled, failed, panicked and aborted counts. Dropping a dispatcher without shutdown aborts running handlers.

Not covered here

Section titled “Not covered here”
  • Typed answers to invoke activities other than card actions and searches.
  • Graph change notifications, which are a different source with different identifiers and are never routed through this pipeline.
  • Windows: the pipeline is platform-neutral and has been run on macOS only; no Windows MSVC runner has executed it.

The protocol facts behind each step, with the Microsoft Learn page each came from, are in compatibility.
