Card actions

A card is a question, and the button a person presses is the answer. This page covers how the bot receives those answers and how it replies. Building the card is in Adaptive Cards.

The walkthrough runs with no cloud account:

It is a simulation and says so. A person messages the bot, the bot replies with an approval card, the person presses Approve and the bot answers with a replacement card. A second press is a replay and approves nothing twice. A press by somebody who does not own the request is denied before any handler runs. A request signed by another key is refused with 401.

The example is the smallest form: the bot part is 60 nonblank lines or fewer, and a test measures it. A second example adds a per-user view (see Refresh and per-user views):

The three things a card sends back

Section titled “The three things a card sends back”
Card element What the bot receives How it answers
Action.Execute An adaptiveCard/action invoke In the HTTP response of the same request: a replacement card, a message or an error
Action.Submit A message with an object value and no text A new message (the response has nowhere to go)
Input.ChoiceSet with choices.data An application/search invoke The choices, in the HTTP response

A message that has text and a value (what a messageBack button sends) is an ordinary message and goes to on_message. Invokes the card hooks do not answer, such as task/fetch, still go to on_invoke, which runs and writes no response.

The bot denies by default

Section titled “The bot denies by default”

Everything in a press except the person’s identity comes from the client. The verb, the id, and every value in data were composed by whoever pressed the button, or by a program pretending to be them. A hidden request_id can say anything. The person comes from the signed activity.

So the SDK runs nothing until your hook says the person may:

  • A bot that registers card handlers and no hook answers every action 403. The handler never runs. The same holds for searches (authorize_card_search).
  • A hook that returns an error answers 500 and runs no handler: it fails closed.
  • The hook runs before the verb is looked up, so an unknown verb is also checked first.
  • ctx.actor() holds the person’s Teams id, their Microsoft Entra object id when Teams sent one, the tenant and the conversation, all from the authenticated activity. Putting user_id in the card’s data changes nothing; a test sends exactly that.

The SDK cannot make this decision. It does not know who owns an approval, which rows a person may read, or whether a data set is theirs.

Handlers and responses

Section titled “Handlers and responses”

A handler is an ordinary async function: Fn(CardActionContext) returning Result<CardResponse, E>. ctx.data_as::<T>() deserializes the data into your type. Return its error with ? and the client gets a 400; any other error becomes a 500 that says nothing about the cause, and the error goes to the failure observer (on_handler_failure).

Constructor statusCode type
CardResponse::replace(&card) 200 application/vnd.microsoft.card.adaptive
CardResponse::message(text) 200 application/vnd.microsoft.activity.message
CardResponse::bad_request(..) 400 application/vnd.microsoft.error
CardResponse::forbidden(..) 403 application/vnd.microsoft.error
CardResponse::conflict(..) 409 application/vnd.microsoft.error
CardResponse::internal(..) 500 application/vnd.microsoft.error

The HTTP status is 200 whenever the bot’s code ran. The result is the statusCode in the body, which is how Microsoft documents the envelope.

A verb names its handler. An Action.Execute has a verb property; an Action.Submit has none, so the verb is a verb property the card author puts in data. An action with an unknown verb, or none, goes to the fallback if you registered one and is answered 400 otherwise. It never goes to another verb’s handler.

Doing something once

Section titled “Doing something once”

A button can be pressed twice: Teams retries, a person double-clicks, a card stays on screen after it was acted on. ctx.once runs your work once per decision and says so on every later press:

  • The first argument identifies the decision. Use the id of the object the button acts on. It is combined with the verb and hashed into the idempotency key, scoped to the tenant by the store, so two tenants never share a decision.
  • Two presses racing run the work once. A press repeating the decision with different data fails with StateError::KeyReused, which ? turns into a 409: a client that changes the amount on a replay is not approved twice.
  • Authorize before calling it. The identifying string usually comes from the client.

What this does not do. It makes the store’s own writes atomic with the recorded result. It cannot make a call to another system atomic. If the work writes to your own database, the write and the record are two commits, and a crash between them runs the work again after a restart. So:

  • Write work that is safe to run twice (setting a status is; adding to a balance is not), or
  • Put the intent in the store’s outbox from inside the work (UnitOfWork::enqueue) and send it from a worker. A crash then repeats the send and never loses it, and the receiver must tolerate a repeat. See state.

The work runs while the store holds its lock: keep it short and do not call out from it.

How long “once” lasts. The guard is a record, and records do not last forever or travel between processes:

  • Seven days. A committed result is replayable for 7 days (the store’s result_ttl). After that the same decision is new again and work runs again. A decision that must never repeat needs a record in your own database as well.
  • Memory by default. TeamsApp keeps decisions in memory unless you call sqlite_state(path) (the sqlite feature). In memory they are gone when the process restarts and are not shared between instances, so a second instance, or a restarted one, will run the same decision again. Use SQLite on one host, or your own store, if a repeat after a restart matters.
  • Not per person. The key is the verb and your string, not the actor. A second authorized person pressing the same decision gets the first person’s result back with is_replay() true, and work does not run for them. That is usually what an approval wants. If each person should decide separately, put the person in the string, for example format!("approve:{request_id}:{}", ctx.actor().user_id()).

Time and capacity

Section titled “Time and capacity”

A card action runs in its own task under a deadline, 10 seconds by default (card_action_timeout). One that outlives it is cancelled and answered with a 500 whose code is Timeout. One that panics is contained, answered 500 and reported. At most 16 run at once (card_action_concurrency); the rest get a 503 with Retry-After: 1, which is how the bot says “busy” without queuing unbounded work.

Cancellation. The hook and the handler run together in one task. That task is cancelled in two cases: it outlives the deadline, or the request is dropped because the client went away or Teams stopped waiting. A dropped request cancels the handler, so it cannot go on to do its work after nobody is waiting, and it keeps its place in the concurrency limit until it is gone: the limit is at most 16 handlers running, not 16 requests waiting. A late press is answered 503 while the cancelled one is still being torn down.

Cancellation is cooperative. A task stops at an .await, so an async handler can be cut off between two effects that are not atomic: after it called one service and before it called the next. Work that must not be split belongs in ctx.once (atomic with the record) or in the outbox. A task the handler spawned, or a blocking call it made (spawn_blocking, a thread), is not cancelled with it and keeps running.

The 10 seconds is the SDK’s choice, not a Microsoft figure. The pages read do not state a time budget for an adaptiveCard/action response. Work that takes longer should answer at once (“Working on it”) and finish later, then update the message through the Connector. This is separate from Graph webhook deadlines, which are a different delivery with different rules and never go through this pipeline.

Searches

Section titled “Searches”

ctx.request() holds the typed query: the text, the data set name, skip and top. Teams shows at most 15 choices, so top is clamped to 15 and SearchResults keeps the first 15. skip is clamped to 10,000. The data set is the client’s claim, so the hook decides whether this person may read it.

Refresh and per-user views

Section titled “Refresh and per-user views”

The per_user_view example uses them; it is the approval example with a refresh added, kept separate so that the approval stays within 60 lines. A card sent with Card::builder().refresh("view", data, [sender]) asks Teams to refresh it for the people in userIds (60 at most) with an adaptiveCard/action whose trigger is automatic. ctx.trigger() tells a refresh from a press, and ctx.actor() says whose view to build, so one handler answers the owner with an Approve button and everybody else with “wait”. The base card, the one sent to the conversation, is what everyone sees until their refresh arrives, so keep anything private out of it.

What this does and does not give you:

  • A view is a card, not a permission. The refresh goes through the same authorization hook as a press. Deciding that anyone may look and only the owner may approve is the hook’s job (the example does it with the verb); the SDK does not infer it.
  • Only the listed people refresh by themselves. Anyone else gets Teams’s Refresh menu item, which sends trigger manual. The example shows the difference between the two.
  • Teams, not the SDK, decides when. The Microsoft pages say the client refreshes only if the last invoke is older than a minute and keeps the latest 50 cards per user. The SDK neither enforces nor works around either.
  • Not seen on a client. The requests are the documented shape, signed by a generated key. No Teams client has refreshed a card from this SDK.

Not done and not verified

Section titled “Not done and not verified”
  • No press has come from a real Teams client. Every request in the tests is the shape Microsoft documents, signed by a generated key.
  • How each Teams client shows a 403, 409 or Timeout error is not verified. Only 400, 401, 412 and 500 are in Microsoft’s table.
  • The msteams variants of Action.Submit (imBack, messageBack, invoke, signin) are not routed specially. A messageBack is a message; an invoke variant arrives as an invoke the card hooks do not answer.
  • 401 login and 412 SSO responses belong to the SSO work; see sign-in.
  • Nothing has run on Windows.
