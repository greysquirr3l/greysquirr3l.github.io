Directory and app installs

The graph feature adds a narrow set of Graph reads, and one explicit pair of writes, hanging off the two clients:

DelegatedGraph has the same two methods. Every operation, its endpoint, its permission for each kind of client and the page it comes from is in the compatibility matrix. Everything is v1.0. Nothing asks for consent, and nothing here lists a whole tenant.

What it will not do

Section titled “What it will not do”
  • It never lists every user, team or chat. Each list is of one named user, team, channel, chat or scope, and each walk stops at the client’s PageLimits with an error.
  • It never installs on its own. The notifier, the Connector client and muss-teams doctor hold no Graph client. A proactive message to someone who has not installed the app is an AppNotInstalled-style error; the SDK does not try to fix it.
  • It never grants consent. The install body is teamsApp@odata.bind and nothing else, so an app that needs resource-specific consent fails with the service’s refusal.

Naming users, teams and chats

Section titled “Naming users, teams and chats”

The identifiers are separate types, and none converts into another.

What Type
Entra application id (the registration) AppId
Teams manifest app id (externalId) ManifestId
Catalog app id (teamsApp.id) TeamsAppCatalogId
Installation id TeamsAppInstallationId
Graph chat id 19:...@thread.v2 ChatThreadId
Graph channel id 19:...@thread.tacv2 ChannelThreadId
Team id (a GUID) TeamId
Bot Framework conversation id ConnectorConversationId

A user is named with UserRef::object_id(..) or UserRef::principal_name(..), or with MailAddress. The SDK does not guess which a string is. A guest’s principal name holds #EXT#, so look a guest up by object id or by the mail address they were invited with.

user_by_mail reports AmbiguousMail when two users share the address and never picks one. A soft-deleted user is not found by user; deleted_user reads it from the directory’s deleted items by object id.

Members that change while you read them

Section titled “Members that change while you read them”

A member who moves from a later page to an earlier one while the walk runs is returned once. The result is a snapshot read over several requests. Keep two snapshots and call diff_memberships(&before, &after) to see who was added, removed or had a role change.

Is the app installed?

Section titled “Is the app installed?”

None means not installed there. require_installation turns that into a NotInstalled error. The catalog id an install needs comes from catalog_apps(&manifest_id), or from your own records.

Installing, when someone asked for it

Section titled “Installing, when someone asked for it”

An install changes what a team, a chat or a person can see, so it takes an approval made from the exact request.

  • The approval covers only that app in that scope. Another app, another scope or an uninstall is ApprovalMismatch, and nothing is sent.
  • It says who approved. An agent has to get that from a person.
  • It carries the write’s idempotency key and is spent by the call. The same key after a success returns Replayed without a second request; after a lost answer, or when the call was dropped (cancelled, timed out by the caller) before it finished, it is refused (EarlierWriteAmbiguous) and the SDK does not repeat it; after a refusal it may be used again. Once you have looked at the installed apps and know what happened, reconcile(key) frees an ambiguous key; at 1,024 unreconciled keys a new write is refused with TooManyOpenWrites.
  • Finding an installed app (installation_of) walks the scope’s list within the page limits and matches the manifest id by externalId or, for a Teams store app whose externalId is empty, by teamsApp.id.
  • A match is a claim by the app, not proof of who published it. externalId is chosen by the app author, so a sideloaded or organisational app can declare another app’s manifest id and installation_of will report it as that app. The SDK does not check distributionMethod on an installation, and the manifest id does not identify the publisher. Before trusting a match, an operator should confirm the app’s distributionMethod (store for a Teams store app, organization or sideloaded otherwise), its catalog id and its publisher in the Teams admin center or on the teamsApp object, and compare the catalog id with the one they approved.
  • Every write to an installedApps path, or to $batch, is refused in the one function all Graph calls share, including through request() and the application client; only app_installs() can send one, and only with an InstallApproval.
  • The client remembers up to 1,024 keys, in one process. That is replay handling, not exactly-once. If the install must be atomic with your own state, record the key and the result in your store in the same transaction as your change, and send the install from an outbox.
  • The caller’s real permission decides. The write permissions are the Self ones the pages list as least privileged; a 403 names the permission the contract says was needed.

Not verified

Section titled “Not verified”

No directory read and no app install has been run against a live Graph. Every answer in the tests and the example is a sample served by a loopback server. The rows of the compatibility matrix that still need a live run are listed in the compatibility reference.

Run the whole flow against a simulated Graph with cargo run -p muss-teams --example directory --features graph,test-utils.

The full list of types, errors and settings is in the public API.
