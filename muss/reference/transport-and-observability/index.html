Transport and observability

How the SDK talks to Microsoft 365, and what it tells you about its own work. This is the contract for muss-core’s transport layer.

The shape

Section titled “The shape”

The policy is pure and the adapter owns no policy. That split is what makes the retry behaviour testable without a network, and it is why the two live in different layers.

The adapter’s public face is HttpClient. A use case holds one, calls get/post_json on it, and receives a HttpResponse or a MussError - never a reqwest type. HttpClient is what applies the bounds below, so a use case cannot forget to apply them. The raw reqwest::Client is reachable through build_client, but that is the adapter’s own escape hatch: it is a foot-gun with a doc comment saying so, and nothing in the use-case layer uses it.

The bounds

Section titled “The bounds”

Every outbound request is bounded. A client that is not bounded is a client that can exhaust a worker slot, a socket pool or the heap.

Bound Default Why it exists
Connect timeout 10s A dead host must not hold a worker slot.
Request timeout 60s A slow endpoint must not hold a worker slot.
Response size 1 MiB A hostile or broken endpoint must not exhaust memory.
Redirects 3 A redirect chain must not be infinite.
Attempts 3 A failing endpoint must not spin forever.

The response limit is enforced while the body is read, not after. A limit applied after the read has already let the whole body into memory, which is the thing the limit exists to prevent. HttpClient is what enforces it: a body that arrives over the limit is a transport failure, not a response with a long body.

One fetch carries its own limit. The Bot Connector service publishes its signing keys as a JWKS document that was 872,896 bytes on 2026-11-04, which does not leave much room under a 1 MiB limit, so the key-set fetch in muss-teams reads up to 4 MiB. The wider limit belongs to that fetch alone: it is a client of its own, and every other call the SDK makes keeps the 1 MiB bound above.

Retries

Section titled “Retries”

Three questions, answered by muss_core::application::request:

Is this failure retryable? A 429 is. A 500 is. A 403 is not - the permission will not appear by waiting. A transport error on a read is.

May this request be repeated? A read has no side effect, so it always may. A write may be repeated only if the caller says so, and there is exactly one way to say so:

There is deliberately no “best effort” option. A caller who believes a write is safe to repeat has to state it in a variant that can be grepped for.

When should the next attempt happen? The server’s Retry-After wins when it is longer than the local backoff, because the server knows when it will be ready. It is still clamped to the 30s ceiling, because the caller’s own deadline is the outer bound. A server asking for an hour does not get an hour.

The local backoff is capped exponential with jitter: the delay lands somewhere between half the backoff and the whole of it, so a fleet of clients does not retry at the same instant. The jitter comes from a seed the policy carries, so it is reproducible - a test asserts an exact number of milliseconds - and it can never undercut the server, because the delay is never shorter than the backoff the policy chose.

The ambiguous outcome

Section titled “The ambiguous outcome”

A timeout during a POST is not a failure. It is an unknown: the request may have been applied on the server before the failure was observed.

This distinction matters more than any other in this document. Treating an unknown as a failure invites a duplicate; treating it as a success hides a real failure. The SDK reports it as its own outcome, and is_ambiguous_write exists so a caller can act on it.

Two send methods keep the distinction. HttpClient::send reports a failed request as a transport failure, which is right for a read. HttpClient::send_write is for writes: when the request may have reached the service and no complete answer came back (a dropped connection, a timeout after the request was sent, an unreadable body) it returns MussError::AmbiguousWrite, and only a failure to connect is a plain transport failure with no status, because then the request was never sent. never_reached_service is true only for a failed connection: reqwest also files a connection that dropped mid-exchange as a request error, and a write that failed that way may have been applied. An earlier version of is_ambiguous_write called a transport failure with no status ambiguous, contradicting its own comment; it now agrees with it.

Credentials and redirects

Section titled “Credentials and redirects”

An Authorization header is presented only to the origin it was minted for. The origin is the scheme, the host and the port together.

Redirect to Credential
https://graph.microsoft.com/v1.0/other kept - same origin
https://graph.microsoft.com:443/v1.0/other kept - the default port is the same port
https://GRAPH.MICROSOFT.COM/v1.0/other kept - host names are case-insensitive
https://graph.microsoft.com:8443/v1.0/other stripped - a different port
http://graph.microsoft.com/v1.0/other stripped - a plaintext downgrade
https://attacker.example/collect stripped - a different host

A redirect target is attacker-controlled input. This rule is the reason the credential is compared against an origin rather than a host: https:// to http:// on the same host is still a leak.

Clear text

Section titled “Clear text”

A request is sent over clear text only where the traffic provably cannot leave the machine. Everywhere else the transport requires https and refuses the request before it is built, so nothing reaches the wire.

Destination Clear text
https://graph.microsoft.com/v1.0/users always allowed
http://127.0.0.1:8080/v3 allowed - the loopback interface
http://localhost:8080/v3 allowed - the loopback interface by name
http://[::1]:8080/v3 allowed - the loopback interface
http://169.254.169.254/metadata/identity/oauth2/token allowed - the instance metadata service is link-local and speaks clear text by design
http://192.0.2.1:81/v3 refused - the traffic would leave the machine
http://localhost.example.com/v3 refused - the name only looks local

A host the client was pinned to is judged by the addresses the pin names, not by the name in the URL: the bytes go to those addresses whatever the name resolves to. A pin whose addresses are all loopback is a local destination; a pin that names any other address is not.

The rule covers redirects too. A redirect is attacker-controlled input, so a destination that would move the traffic into clear text is refused rather than followed, and the refusal keeps the same identity as any other refused request.

The refusal names the scheme, the host and the port. A path can carry an identifier and a query can carry a token, so neither is part of the message.

What gets logged

Section titled “What gets logged”

The default is the safe set. The identifiers are opt-in.

Always reported:

  • the operation name, a low-cardinality constant such as graph.send_message
  • the latency
  • the number of attempts
  • the outcome
  • the queue depth at the time
  • the failure classification

Never reported by default:

  • tenant identifiers
  • resource identifiers
  • request or response payloads

A tenant identifier names an organisation. A resource identifier can name a person. A payload can contain anything a user typed. Logging them by default would make the SDK a data-mining tool for its users’ traffic, and the opt-in would be discovered only after the data had already been collected.

So identifiers are off unless a caller opts in:

Payload logging is a separate and louder decision, and it is not implemented. The tracing adapter has no access to a payload, which is deliberate: a payload switch would have to live somewhere with the payload, and the safe default is that no such place exists yet.

Backpressure

Section titled “Backpressure”

The tempting way to handle an incoming event is to spawn a task for it. That is unbounded: a burst of activity spawns one task per event, each holding a connection, each waiting on a rate-limited API. The process does not fail loudly; it grows until the machine runs out of memory or the tenant’s quota is gone.

The queue is the alternative. It has a fixed capacity, and when it is full a producer is rejected rather than made to wait - because a bot that cannot acknowledge an activity in time has to fail the request the platform can see, rather than accept it and lose it quietly.

One tenant must not starve another, so the scheduler round-robins over tenants. A tenant that submits a thousand items does not delay a tenant that submits one.

The clock

Section titled “The clock”

There is no clock port in muss-core. Time enters the transport in one explicit place and nowhere else.

parse_retry_after_at(value, now) resolves a server’s Retry-After against an instant the caller supplies. The adapter passes the system clock; a test passes a fixed instant and gets an exact duration back.

The retry policy reads no clock at all. It answers how long to wait, not when it is, so its answer is a pure function of the policy, the attempt number and the failure - and a test asserts the exact number of milliseconds without sleeping for them.

A use case that needs the current time owns a narrow port for it in muss-teams, where the use case lives, and passes the time down. A clock trait in muss-core would have had no user: nothing in the crate asks for the time.

What is not covered

Section titled “What is not covered”
  • No live-tenant verification. The transport has been proved against a loopback HTTP server, not against Microsoft 365. The wire behaviours that the tests assert - the 429 handling, the redirect stripping, the size limit, the timeout - are properties of HTTP, and the fixture reproduces them exactly. The parts that are not covered are the authentication handshake and the service-specific payload shapes.
  • No token acquisition. This layer authenticates with a credential it is given. Where that credential comes from is a different task.
