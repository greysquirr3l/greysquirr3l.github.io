The muss-teams command-line tool

The tool is optional. An application depends on the muss-teams crate only; the tool scaffolds a project, checks and packages an app manifest, sets the bot up in Microsoft Entra ID and diagnoses a configuration.

Install it from the workspace:

Commands

Section titled “Commands”
Command Writes Touches the cloud
init files in the output directory no
manifest validate nothing no
package one ZIP archive no
setup the manifest and .env file locally; Entra objects only with --apply only with --apply, after confirmation
doctor nothing read-only calls

An unknown subcommand or option is an error that names it, and the exit code is non-zero. init and package never replace an existing file unless --force is given; init reports each file it left alone, and with --force it lists what it replaced, line by line, and which files already held the scaffold. init --force never writes through a symbolic link: a link where a scaffold file belongs is an error that says to remove it.

init does not draw icons. package stops with an error naming the icon it could not read. It writes the archive to a temporary file beside the destination and renames it into place when it is complete, so a failure leaves no partial archive and, with --force, leaves a good existing archive exactly as it was.

The package holds the manifest and the icons the manifest names, at the archive root, so the same inputs give a byte-identical archive: every entry carries the ZIP epoch (1980-01-01 00:00:00) and the entries are sorted by name. A .env file or any other neighbour is never included.

Registering the bot

Section titled “Registering the bot”

setup prints its plan first: every step, the reason for it and the exact az command. Nothing changes until --apply is given and the operator confirms.

The generated SETUP.md walks through the same steps by hand, in both shells: Entra registration, credential, identifiers, manifest, icons, HTTPS endpoint, packaging and side-loading.

doctor

Section titled “doctor”

doctor is read-only by construction. It reads the configuration, mints a Bot Connector token and reports what it verified. Minting the token is a read of the identity platform, not a write to the tenant, but it does send the client secret (or a signed assertion, for a certificate) to the Microsoft token endpoint, as the bot itself does, so run doctor only on a machine you would run the bot from. Its Azure CLI driver is read-only: it refuses, before starting a process, any command other than version, account show, ad app show and ad sp show, so a probe that tried to write would be refused and show up in the output. A test runs doctor against a stand-in az that logs every call and fails if any call is not one of those reads.

It also lists what no read it makes can establish, as not verified rather than leaving the gap to look like a pass: whether the app is installed anywhere, and what the tenant’s app permission and setup policies allow. Both live in the Teams admin center. doctor sends no message, installs nothing and grants no consent, and it never prints a secret; a test plants a secret in the environment and checks it does not appear.

It does not repeat what the Azure CLI writes to standard error, because that text can carry identifiers and tokens. It reads the text to tell what kind of failure it was and prints a fixed description. It says not installed only when the operating system reports the program missing; a program that was found and failed is reported as such. It says a registration has no service principal only when the CLI answers that the object does not exist; any other failure is could not find out, and the fix it names for a missing service principal says that it changes the tenant. The Certificate check says both variables are set; that they belong together is shown only by the Token check, which signs with them.

Offline simulation

Section titled “Offline simulation”

One command runs a message and card round trip with no cloud account:

It is a simulation, and it says so on its first line. Nothing leaves the process. A person messages the bot, the bot replies with an approval card, the person presses Approve and the bot answers with a replacement card. A second press is a replay and approves nothing twice, a press by somebody who does not own the request is denied, and a request signed by a different key is refused with HTTP 401. The bot is a real TeamsApp that authenticates every request with the production trust policy, and the Connector is a loopback server that records what the bot sends. Authentication is not bypassed. The only things replaced are where the signing key comes from, the clock and where the Connector writes, and those replacements live behind the test-utils feature that no production build enables. A test runs the example and checks its output. See card-actions.md.

The message-only version, offline, and the per-user refresh, per_user_view, run the same way:

Why this is an example and not a muss-teams simulate subcommand. The simulation needs the test-utils feature of the muss-teams library. The command-line tool is an optional program people install and run against real tenants, and it shares nothing with the library beyond its documented public API. A simulate subcommand would compile the test seam, a replaceable signing key and a replaceable clock, into that shipped binary. Keeping the simulation as a cargo example keeps those seams out of every binary anyone installs.

Errors and help

Section titled “Errors and help”

A mistyped command names the nearest real one, and an unknown command lists the commands:

Help text and every argument error are compared against golden files in crates/muss-teams-cli/tests/golden/, so a wording change shows up as a diff.

The argument rules are the same for every command:

  • --name value and --name=value mean the same. The second is how to pass a value that starts with a dash.
  • A value is never taken from the next option: --output --force is an error.
  • An empty value, an option given twice, a switch given a value and a stray word where only options go are errors.
  • -h and --help work after any command and print the help text.
  • An argument that is not valid text is an error, not a crash. The tool reads its arguments as text.

The parser is hand-written and not clap; see ADR 0004.

Package rules

Section titled “Package rules”

A package holds the manifest and the icons it names, flat at the archive root. Nothing else is ever added: a .env or a key beside the manifest is not packaged, and a manifest that names one as an icon is refused.

The manifest names the files; the packager checks each one before it goes in.

  • Name. Refused, on every host, before any file is read, when it contains a path separator, starts with a dot (a hidden file such as .env), starts with .., is absolute, contains : (a drive letter or an NTFS data stream) or <, >, ", |, ?, * or a control character, is a reserved Windows device name with or without an extension (CON, PRN, AUX, NUL, CONIN$, CONOUT$, CLOCK$, COM0 to COM9, LPT0 to LPT9), starts or ends with a space, or ends with a dot.
  • Characters. ASCII letters, digits, space, ., - and _ only. A name with other characters can be written two ways (é as one character or as e and a combining accent) and two such names would be one file on some file systems, which the standard library cannot detect. This is a narrowing the SDK chooses; the schema accepts any relative path.
  • Collisions. Two names that differ only in case, the manifest included, are refused.
  • Kind. The file must be a .png whose header is a PNG header, at the size the schema asks for: icons.color 192x192, icons.outline, icons.color32x32 and each activities.activityIcons[].iconFile 32x32. Only the header is read; the image data is not decoded.
  • Size. An icon over 1 MiB, a manifest over 1 MiB, or entries that add up to more than 4 MiB are refused. These are the SDK’s own bounds, not Microsoft’s.
  • Links. A symbolic link is refused, and so is anything that is not a regular file. The link check and the open are two steps; the opened handle is checked again, but a process that can swap a link in between could still race it. Such a process can already edit the manifest.
  • Activity icons. The files named by activities.activityIcons go into the package and are checked like the other icons. The model keeps their paths only; it does not read the ids.

Windows

Section titled “Windows”

Windows is a first-class host for this tool, and the following is not yet verified on a Windows machine or CI runner: the PowerShell snippets above, and the Azure CLI launcher lookup. The Windows-name and path rules run on every host, so they are tested here. The Azure CLI installs az.cmd on Windows, and the tool resolves it by walking PATH and PATHEXT itself, skipping the current directory. That lookup is tested on every host with a supplied file system, but no Windows run has confirmed that the resolved az.cmd starts. The stand-in az tests of doctor are Unix-only.
