The error taxonomies

Every failure the workspace reports is a variant of one of two enums. The shared enum, MussError, lives in muss-core and names the failures any Microsoft 365 surface can report. The Teams enum, TeamsError, lives in muss-teams and names the failures that only a Teams surface can report. The Teams enum extends the shared one rather than repeating it, so a caller that only cares about the shared taxonomy unwraps one layer and matches on MussError.

Both enums are #[non_exhaustive]. Adding a variant is not a breaking change for a downstream crate that matches with a wildcard arm.

The shared taxonomy

Section titled “The shared taxonomy”
Variant Meaning Worth retrying
Config The application is not configured correctly. no
Unauthorized The credential was not accepted. no
Forbidden The credential was accepted but the operation is not permitted. no
MissingPermission The credential lacks a permission the operation requires. no
AppNotInstalled The app is not installed where the operation was attempted. no
UnsupportedCapability The requested capability is not supported. no
RateLimited The service throttled the request. yes
DeadlineExceeded The operation did not finish within its deadline. yes
AmbiguousWrite The outcome of a write is not known. no
Transport The request did not reach the service. yes
Credential The credential could not be obtained or presented. no
InvalidRequest The request was rejected because it could not be understood. no
Cancelled The request was cancelled before it completed. no

MussError::is_retryable answers the retry question, MussError::retry_after returns the delay the service asked for, MussError::status returns the HTTP status when there was one, and MussError::correlation_id returns the correlation identifier the service supplied.

AmbiguousWrite is deliberately not retryable. A write that may or may not have been applied must be reconciled with its idempotency key before it is attempted again; retrying it blindly can duplicate the effect.

The Teams taxonomy

Section titled “The Teams taxonomy”
Variant Meaning
Core(MussError) A failure the shared taxonomy already names.
AppNotInstalled The app is not installed in the tenant the operation targeted.
ConversationNotFound The conversation does not exist, or is not reachable.
MessageWritesBlocked The service refused to write a message.
UnsupportedCapability The app does not declare the capability the operation needs.
Protocol The service returned a Teams protocol error.
UnusableResponse The service accepted the request and answered with a body the SDK cannot read.

TeamsError::core returns the shared failure behind an error, when there is one. TeamsError::is_retryable, TeamsError::retry_after and is_authorization_error answer the same questions as their shared counterparts.

The invariant behind the retry decision

Section titled “The invariant behind the retry decision”

A Transport failure with no status means the request never reached the service. The connection was refused, the name did not resolve, or the client could not be built. Nothing was sent, so the call may be made again, and that is what every retry decision in the workspace reads.

The other outcomes have their own variants, so the meaning is never overloaded:

Outcome Variant
The request reached the service and its answer was lost AmbiguousWrite
The request was sent and the deadline passed DeadlineExceeded
The service answered with a body the SDK cannot read TeamsError::UnusableResponse
The service answered with a status the caller cannot use Transport with that status

A request that reached the service and lost its answer is never repeated blindly, because the service may have applied it. A request that never left is repeated whenever the operation is safe to repeat.

What is redacted, and how

Section titled “What is redacted, and how”

Nothing that leaves the workspace as an error message may carry a credential, a token, an address or raw message content. Three mechanisms enforce that, and each one covers a different way a secret can reach an error.

A value that is a secret is never rendered

Section titled “A value that is a secret is never rendered”

muss_core::domain::redaction::Redacted<T> wraps a value that is itself a secret. Its Display form is the placeholder [redacted], and its Debug form is a placeholder too, so neither {} nor {:?} can print the secret. The value is reachable only through Redacted::expose and Redacted::into_inner, both of which name the act of disclosure at the call site.

redact_secret and redact_token build one.

Free text is scrubbed when it is built

Section titled “Free text is scrubbed when it is built”

muss_core::domain::redaction::DiagnosticText is the field type of every free-text field in both taxonomies. It scrubs the text once, when it is constructed, and the scrubbed text is what Display and Debug render.

The pattern rules remove a credential that is recognisable as one:

  • an authentication scheme followed by its credential, such as Authorization: Bearer eyJhbGci... or Basic dXNlcjpwYXNz;
  • a JSON web token, recognised by its three base64url segments;
  • name=value and name: value where the name is a credential-shaped field name, such as client_secret, access_token, password or my_secret;
  • a quoted field of a JSON body, such as {"client_secret":"value"}. Every field of the body is swept, not only the first, so a body that carries several secrets loses all of them.

The rules are conservative on purpose. A diagnostic that over-redacts is a diagnostic that cannot be read, so a word that merely ends in secret, such as notasecret, is left alone.

DiagnosticText::new_redacting additionally removes values the caller knows are secret, wherever they appear in the text. It is the answer for a secret that reached an unexpected field and left no trace of what it was.

An address is masked

Section titled “An address is masked”

redact_personal masks an address to its first character and its domain, so ada.lovelace@example.com becomes a***@example.com. Two masked addresses still correlate, and neither identifies a person.

An identifier that can carry an address keeps its exact value in its Display form, because the exact value is what a request needs, and masks it in its Debug form, because the Debug form is what a log line carries.

The identifiers and their failures

Section titled “The identifiers and their failures”

Every identifier kind is a distinct type, so the common failure - using one kind where another kind belongs - is a compile error rather than a runtime mistake. The types live in muss_teams::domain::identifiers.

Kind Shape Names
EntraUserId GUID a directory user
AppId GUID the app registration of a Teams app
TeamsAppCatalogId GUID an entry in the tenant’s app catalog
TeamId GUID a Graph team
SubscriptionId GUID a Graph change-notification subscription
TeamsUserId opaque token a user inside a Teams conversation
ConnectorConversationId opaque token a conversation as the Connector addresses it
ActivityId opaque token a single inbound activity

A GUID kind accepts exactly the canonical hyphenated form: eight hexadecimal digits, four, four and twelve, separated by hyphens. Upper case input is normalised to lower case. Any other notation, including a truncated GUID and a GUID without hyphens, is rejected.

An opaque kind accepts exactly a non-empty token of printable ASCII of at most 256 bytes, and holds it exactly as it was received. The platform sends conversations as 19:meeting_abc123@thread.tacv2 and users as 29:1abcDEF2ghiJKL_mnoPQRstu, so a parser that demanded a UUID of them would reject every real value.

The two shapes are kept apart deliberately. A Graph chat identifier is a GUID and a Connector conversation identifier is not, which is exactly the mistake that sends a notification to the wrong place. The compile-fail fixtures under crates/muss-teams/tests/ui prove that neither kind can be used where the other belongs.

A rejected identifier reports an IdentifierError, which names the kind that was rejected and the reason it was rejected. The rejected value is never part of the message.

The typed idempotency key

Section titled “The typed idempotency key”

muss_core::domain::idempotency::IdempotencyKey is a version 4 UUID that cannot be forged. It has no constructor that takes a string: new draws one from the operating system’s random source, and parse accepts only the canonical hyphenated form of a version 4 UUID. A key therefore identifies one request and cannot be chosen by a caller who wants to collide with somebody else’s request.

The context a failure carries

Section titled “The context a failure carries”

muss_core::domain::auth_context::AuthContext carries the tenant, the client, the audience the credential was issued for, and the scopes the operation requires. The audience is the piece that makes a credential unreplayable: AuthContext::ensure_audience refuses a credential that was issued for a different audience, before a request leaves the process.
