Supported-surface matrix

This is the surface matrix for muss-teams: the exact Microsoft endpoint, API version, permission, cloud and account type behind every advertised capability. Every row was read from Microsoft Learn on 2026-11-03 and 2026-11-04, and the verification date is the date the cited page was read. Read a row for one capability, or use the pages below to read the matrix surface by surface.

The exact Microsoft surface each advertised capability is allowed to touch.

Every row was read from Microsoft Learn between 2026-11-03 and 2026-11-04 (UTC). The verification date is the date the cited page was read, not the date the page was published. Where a row says not verified, the underlying page could not be retrieved or did not state the value; nothing was inferred from a neighbouring surface.

This matrix exists because permissions are not transitive. ChannelMessage.Read.Group says nothing about TeamsActivity.Send.Chat, and the Bot Connector service says nothing about Microsoft Graph. Each row in these pages stands on its own citation.

Bot Framework surface

Section titled “Bot Framework surface”

The Bot Framework SDK and Bot Framework Emulator were archived on GitHub, and support tickets for the SDK stopped being serviced on 2025-12-31 (What’s new for the Bot Framework SDKs). That archival is about the SDK libraries, not about the Connector REST service: the Connector API reference is still published and still describes the service this SDK talks to (API reference for the Bot Framework Connector service). Separately, Office 365 connectors in Teams, including connector-based Incoming Webhooks, were retired in May 2026 (Create and send messages). Those are two different retirements and muss-teams treats them as such: the Connector REST service is in scope, the connector-based webhook is out.

The Connector service carries no delegated or application permission model and no personal-Microsoft-account support. It authenticates a bot, not a user, so the Cloud and Account type columns for these rows describe the deployment target of the bot, not an OAuth consent model.

The facade’s production wiring

Section titled “The facade’s production wiring”

Recorded 2026-11-04. The facade (TeamsApp, BuiltApp, TeamsClient) adds no protocol surface of its own: it composes the inbound authentication, the router and the Connector rows. This section records the choices it makes for you and what is not verified about them. Cloud: Global only.

Choice Value Basis
Signing keys https://login.botframework.com/v1/.well-known/keys The Bot Framework signing-key row in inbound activity authentication
Issuer, audience, algorithm https://api.botframework.com, the application id, RS256 Inbound activity authentication
Registration shape single tenant, from TEAMS_TENANT_ID A single-tenant registration only ever receives its own tenant’s tokens
Channel msteams The bot is a Teams bot
Reply hosts smba.trafficmanager.net; allow_service_host adds more The service URL row in the Bot Framework surface shows only this host
Messaging path /api/messages The Bot Framework convention; the path registered with the bot must match
Default listener 127.0.0.1:3978 A choice, not a protocol fact
Request body limit 1 MiB, enforced at the host and again at the boundary A chosen bound, not a documented inbound limit. The documented 100 KB limit in outbound Connector messages is for outbound messages

Not verified

Section titled “Not verified”
  • No live tenant has exercised the facade. Every test signs its own tokens with a generated key and writes to a loopback server. That a TeamsApp configured from a real registration receives and answers a Teams message has not been proved.
  • Regional service hosts. The Learn pages show smba.trafficmanager.net only. If Teams delivers an activity whose service URL is on another host, the bot refuses to reply and the fix is allow_service_host. Whether such hosts exist is unconfirmed.
  • The case of the audience claim. A GUID application id is held in lower case and compared exactly with the token’s aud. Entra writes GUIDs in lower case; a token that wrote one in upper case would be refused.
  • Managed-identity bots receiving activities, multi-tenant registrations and sovereign clouds are refused at configuration time. A managed-identity credential can build the outbound TeamsClient; that combination is built and its configuration errors are tested, but no token has been requested through it from the facade.
  • DNS pinning. The Connector send is pinned to the addresses it checked (proved in the outbound Connector messages section). The addresses the inbound boundary approved are still not carried to the send, which checks again; the facade changes nothing about that.
