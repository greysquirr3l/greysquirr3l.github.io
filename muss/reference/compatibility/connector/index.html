Outbound Connector messages

The Bot Connector REST service is how a bot sends a message without calling Microsoft Graph. This page records the endpoints the SDK calls, the body it sends, how it reads the answer, and the destination check applied to every write. No message has been sent to a real tenant.

Verified 2026-11-04 against the pages below. Permission type is Bot credential: the bot authenticates with a token for the audience https://api.botframework.com and no Graph permission is involved. Cloud: Global is the only cloud this section claims; GCC, GCC-High and DoD use other service URLs and are not advertised. Account type: not applicable.

Operation Endpoint (under the conversation’s service URL) Body Answer
Send POST /v3/conversations/{conversationId}/activities an Activity of type message ResourceResponse {"id": ...}
Reply the same POST, with replyToId in the body as above as above
Update PUT /v3/conversations/{conversationId}/activities/{activityId} an Activity of type message ResourceResponse
Delete DELETE /v3/conversations/{conversationId}/activities/{activityId} none status only
Typing the send POST with an activity of type typing an Activity of type typing status only

Sources: Connector API reference (paths, verbs, ResourceResponse, ErrorResponse, Attachment, Mention), Send and receive messages (send to a conversation, throttling note), and Messages in Teams (the reply and update samples, the 100 KB limit, the error table), and Channel and group conversations (the mention entity).

Correction (2026-11-04). The “Update an existing activity” row in the Bot Framework surface table recorded POST. The Connector reference and the Teams page both give PUT, the row now says so, and the SDK sends PUT.

What the SDK sends

Section titled “What the SDK sends”
  • Reply. The Teams page shows a reply as a POST to .../activities with replyToId in the body, and that is what the SDK sends. The Connector also documents POST .../activities/{activityId} (“reply to activity”) and says a channel without nested replies treats it as a plain send. The SDK does not use that endpoint.
  • Body. type, from (the bot), conversation.id, text, replyToId, entities and attachments, each present only when it has a value. An update also repeats id; the Teams sample omits it and the Bot Framework libraries send it, so it is sent (see Not verified).
  • Identifiers in the path. Each identifier is percent-encoded as encodeURIComponent encodes it, so a channel thread identifier such as 19:...@thread.skype;messageid=1481567603816 is one path segment.
  • Mentions. An entity {"type":"mention","mentioned":{"id","name"},"text":"<at>Name</at>"} and the same <at>Name</at> in the text, as the Teams sample shows. Text the caller supplies is escaped (&, <, >), so it cannot forge a mention.
  • Attachments. A link (contentUrl, https only) or inline JSON (content), never both, as the reference says they are mutually exclusive. Inline binary data is not supported.
  • Size. Teams documents a 100 KB limit counted as UTF-16 over the text, link text, mentions and reactions, excluding base64 images, and advises staying under 80 KB. The SDK refuses a serialized activity over 100 KiB measured as UTF-16 before sending, and maps the service’s 413 MessageSizeTooBig the same way.
  • Splitting. Teams splits a message that has both text and an attachment into two activities and returns no identifier. The SDK then returns no handle, and the documentation tells callers to send them separately when they need one.

How an answer is read

Section titled “How an answer is read”

Teams publishes an error table with a code and a retry rule for each status. The SDK reads error.code from the ErrorResponse body when there is one. A code is shown in an error only when it is a short alphanumeric identifier.

Status and code Typed error Repeated by the SDK
400 BadArgument invalid request no
401 BotNotRegistered unauthorized no
403 BotDisabledByAdmin, BotNotInConversationRoster, ConversationBlockedByUser, ForbiddenOperationException MessageWritesBlocked no
403 InvalidBotApiHost, NotEnoughPermissions, other forbidden no
404 ConversationNotFound ConversationNotFound no
404 ActivityNotFoundInConversation MessageNotFound no
405 unsupported capability no
412 PreconditionFailed transport, retryable yes
413 MessageSizeTooBig MessageTooLarge no
429 Throttled rate limited, with Retry-After yes, after the wait
500 transport no
502, 504 send: AmbiguousWrite; update and delete: transport send: no; update and delete: yes
503 transport send: no; update and delete: yes

Deliberate deviation from the table. Teams says to retry 502, 503 and 504 with backoff. A send is a POST and is not idempotent, so after a 502 or 504 the message may already be in the conversation, and the SDK reports an ambiguous outcome instead of posting again. An update (PUT) and a delete (DELETE) are idempotent and are repeated. Only an answer that says the service did not apply the request (429, 412) makes the SDK repeat a send.

  • A Retry-After longer than the policy ceiling (30 seconds by default) is reported to the caller, not waited for.
  • A delete repeated after a lost answer that then finds nothing (404) counts as success, because the first attempt may have removed it. A first-try 404 is MessageNotFound.
  • A request that never connected (a refused connection) is a transport failure with no status and is repeated. A request that was sent and whose answer was lost (a dropped connection, a timeout, an unreadable body) is MussError::AmbiguousWrite, which the SDK does not repeat for a send. muss-core previously classified a connection that dropped mid-exchange as “never reached the service”; that was wrong for a write and is fixed in HttpClient::send_write.

The destination is re-checked and pinned

Section titled “The destination is re-checked and pinned”

A write goes to the conversation’s service URL. The SDK applies the destination policy (https, an allowlisted host, a public address, no credentials in the URL) again at every send, with a fresh resolution, and connects to the addresses that were checked. The client is built with those addresses in place of a lookup, so a name that is repointed after the check cannot redirect the request. The egress test proves the connection: a host name that does not resolve reaches the test server only because the gate approved an address for it. Redirects are not followed, and a test proves a redirected request sends nothing, and the token nothing, to the other server.

This closes the connect half of the DNS-rebinding window recorded under the inbound boundary’s limitations. It does not carry the addresses authenticate() approved to the send: the send resolves again, which is deliberate, since a stored reference can be days old.

Not verified

Section titled “Not verified”
  • No live round trip. Every body and answer above comes from the pages cited; no message was sent to a real tenant. The proof against a live Teams tenant is blocked until a nonproduction tenant, an app registration and a test conversation are supplied.
  • Typing. The Connector reference lists typing as an activity type, and no Learn page found says where Teams shows a typing indicator. The SDK sends one only into a conversation known to be one-to-one, and refuses otherwise.
  • id in an update body. The Teams sample for an update shows only type and text. The Bot Framework libraries repeat the activity id. The SDK sends it; whether the service requires it was not checked.
  • Path encoding. encodeURIComponent encoding follows what the Bot Framework libraries do. The pages do not state how a ; or : in a conversation identifier should be written in the path.
  • Escaping. Text is sent with &, < and > as HTML entities. The pages show <at> tags in the text and do not say how Teams renders an entity in a message’s text. Rendering was not observed.
  • Mention text. The Teams sample’s entity text reads <at>@Pranav Smith</at> while its message text reads <at>Pranav Smith</at>. The SDK writes the same <at>Name</at> in both.
  • Update and delete by scope. The Teams page documents edit and delete for messages the bot sent but only shows personal-chat samples; channel and group chat behaviour was not confirmed.
  • GCC. A 403 InvalidBotApiHost means the conversation belongs to a GCC tenant and the other service URL must be used. The SDK reports it as a refusal and does not switch hosts.
  • Limits of the SDK’s own making. Fifty mentions and ten attachments per message are the SDK’s bounds, not documented Teams limits.
