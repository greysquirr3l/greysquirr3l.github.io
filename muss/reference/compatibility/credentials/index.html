Outbound credentials and token issuance

Every outbound call muss-teams makes needs a token, and each token belongs to one audience. This page records the credentials the SDK can present, the endpoint each one is presented to, and how a managed identity is proved. The certificate and managed-identity credentials have each been exercised against a live service.

muss-teams obtains its own tokens with the OAuth 2.0 client credentials grant. Each row below is a distinct credential, and each is presented to a distinct endpoint. A token issued for one audience is never presented to another: the token cache is keyed by audience as well as by credential.

Item Value Permission type Account type Cloud Source Verified
Token endpoint (client secret) POST https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token, grant_type=client_credentials, scope=https://api.botframework.com/.default Bot credential Single-tenant registration in {tenant} Global OAuth 2.0 client credentials flow 2026-11-03
Token endpoint (certificate) The same endpoint; client_secret is replaced by client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer and a signed client_assertion Bot credential Single-tenant registration in {tenant} Global OAuth 2.0 client credentials flow 2026-11-03
Graph token endpoint POST https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token, scope=https://graph.microsoft.com/.default Application Single-tenant registration in {tenant} Global OAuth 2.0 client credentials flow 2026-11-03
Managed identity endpoint (virtual machine) The host’s instance metadata endpoint, GET {identity_endpoint}/metadata/identity/oauth2/token?api-version=2018-02-01&resource={audience}, with the header Metadata: true Bot credential Managed identity; no registration and no secret Host-provided Managed identities for Azure resources 2026-11-04
Managed identity endpoint (App Service and Azure Functions) The host’s local token service, GET {IDENTITY_ENDPOINT}/MSI/token?resource={audience}, with the header X-IDENTITY-HEADER: {IDENTITY_HEADER} and no query version Bot credential Managed identity; no registration and no secret Host-provided Authentication with the Bot Connector API 2026-11-04

The managed identity rows record a verified round trip. On 2026-11-04 a Linux host in Azure carrying a user-assigned managed identity minted tokens through this SDK’s own managed-identity source: one for the Bot Connector’s audience (https://api.botframework.com) and one for Graph’s (https://graph.microsoft.com). The Connector token was checked for its audience, its issuer and the client identifier of the identity that asked for it; the Graph token was checked for its audience. A third case confirmed that an identity endpoint that cannot answer is refused with a reason rather than minted into an empty token.

That host ran the instance metadata service, which is what a virtual machine runs. The App Service and Azure Functions row was not proved against a live host of that kind, and the matrix says so: its protocol was read from the cited page and proved against a local service that speaks the same shape, but no request has been made to an App Service or Azure Functions host from this repository.

How the managed identity is proved

Section titled “How the managed identity is proved”

Three layers, each answering a different question, and the last one is rare on purpose.

Layer Question it answers Cost When
A local service on the loopback interface Does the SDK ask the identity service the way that service expects? none every commit
The suite in a Linux container Does any of it work on the platform a bot actually runs on? none every commit
A live Azure host Does the platform agree with our model of it? a fraction of a cent before a release

The first layer is the core outbound-auth test and the managed-identity test. Between them they check the path each service serves tokens on, the header each one checks, the query parameters each one takes, and the token that comes back. The second layer is the Linux test script, which runs the whole suite in the container built from the pinned toolchain, so the failures that only appear on Linux are caught here rather than by a customer.

The third layer is the live managed-identity test. It is opt-in, it is not part of the ordinary suite, and it is a release gate rather than a per-commit check. Run it with:

What the live test proves is that the request the SDK makes is one the platform answers, and that the token it receives is one the target service would accept. What it does not prove is that any particular bot registration is entitled to use that identity; that is a directory assignment, and it is outside the SDK.

The provider remains explicit rather than implicit: a deployment that configures a client secret and does not supply one gets an error, never a managed identity instead. The identity service is chosen the same way — the host names it in its environment, and the SDK asks whichever one the host names rather than assuming the virtual machine’s.
