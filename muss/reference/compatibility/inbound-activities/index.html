Inbound bot activities

Once a request is authenticated, the SDK parses the activity body and routes it to a typed handler. This page lists the activity types the SDK recognises, what the published documentation says about when each one is delivered, and how a redelivered activity is handled. Every payload shape here is a documentation sample; none has been received from a live tenant.

What a Teams bot receives after the request is authenticated, and which of it the SDK routes to a typed handler. Every row was read from the cited page on 2026-11-04. Each payload shape the parser is tested against is the sample JSON on that page, kept under the activity fixtures with the tenant and service URL replaced so they pass the test trust policy.

Permission type is Bot credential throughout (the activity arrives over the bot’s own registration), and the cloud is Global: sovereign clouds are not advertised. The account type is the registration’s, as for the rest of the Bot Framework surface.

What the pages say about delivery

Section titled “What the pages say about delivery”
  • Where the tenant is. channelData.tenant.id is “passed in all contexts” (Conversation messages, Teams channel data). conversation.tenantId is present in some payloads and absent in others (the reaction and channel-created samples omit it). That is why the ingress boundary reads both and requires them to agree when both are present.
  • channelData in personal chats. The same page says the channelData object “isn’t included in messages in personal conversations”, while its own personal-message sample carries channelData.tenant. The SDK does not rely on channelData being absent or present; it reads tenant.id when there.
  • Default delivery. In group chats and channels a bot “only receives messages when they’re directly @mentioned” (Channel and group conversations). The resource-specific consent permissions ChannelMessage.Read.Group (channels) and ChatMessage.Read.Chat (group chats) deliver every human message, and Teams “doesn’t deliver messages authored by other agents or bots, including the Workflows (Power Automate) bot … even when these RSC permissions are configured” (Enable an agent to receive all chat messages). The SDK marks each message Direct, BotMentioned or AllHumanMessages so a handler can tell them apart, and never promises other bots’ messages. Adding the permissions needs a reinstall and consent; the SDK does not do either.
  • Reactions are sent “when a user adds or removes reactions to a message, which was sent by your agent”. Reactions to other messages are not delivered.
  • Upgrades. add-upgrade and remove-upgrade are sent when an app upgrade adds or removes the bot from the manifest, and installationUpdate is otherwise not sent on upgrade.
  • Meeting identifiers. The meeting pages say to take the meeting id from channelData and “do not use conversation ID as meeting ID”. The start and end samples carry the id in value.Id instead. The SDK uses channelData.meeting.id only; see meetings and presence.

Inconsistencies in the published pages, and how the SDK reads them

Section titled “Inconsistencies in the published pages, and how the SDK reads them”
Inconsistency Reading
teamRestored in the event table, teamrestored in the sample JSON (and teamarchived in prose) Event types are compared case-insensitively.
groupChat in the manifest, groupchat in a meeting-event sample conversationType is compared case-insensitively.
The meeting start and end sample names begin with a space (" application/vnd.microsoft.meetingStart") Event names are compared exactly. A name with a leading space is an unknown event and goes to the fallback, which fails safe. Believed to be a typo in the page; unverified against a live meeting.
Some samples omit conversation.conversationType A conversation flagged isGroup, or with team data, is read as a group or channel. A conversation that shows nothing is Unspecified, never Personal, so a message in it is not claimed to be addressed to the bot.

Not verified

Section titled “Not verified”
  • Invoke names. The router carries the name of an invoke verbatim and does not interpret it. adaptiveCard/action, task/fetch, task/submit, the composeExtension/* family and the signin/* names belong to the features that answer them and are verified there. The invoke fixture is hand-built from the documented envelope, not copied from a Learn sample, and is marked as such in its test.
  • Live delivery. Every payload above is a documentation sample. No activity from a live Teams tenant has been received by this code. The live round trip has not happened.
  • typing, endOfConversation, contactRelationUpdate and other Bot Framework activity types are not routed; they arrive as Unknown. Teams documents a read-receipt event for bots that opt in, but its payload was not examined, so it is Unknown unless it happens to match a recognised type and event type.
  • Message edit/delete delivery scope. The page lists the edit, undelete and soft-delete activities with scope “All” but shows only personal-chat samples. Delivery in channels and group chats is not confirmed here.

Replay handling

Section titled “Replay handling”

Teams redelivers an activity it did not get a timely answer for, and the SDK does not assume exactly-once delivery. The intake keys a delivery by kind, conversation and activity id, and, for edits, undeletes, deletes and reactions, by the timestamp too, because those activities carry the id of the message they refer to and an id-only key would let the first edit suppress every later one. An activity with no usable key (no id, no timestamp where one is needed, or an invoke) is never deduplicated, because a missed duplicate is safer than a swallowed update. An invoke is handled every time since it expects an answer. The mark is removed when the activity cannot be admitted, so Teams’s retry is accepted instead of being taken for a repeat. Deduplication is not exactly-once processing; see state and the outbox for the outbox pattern.
