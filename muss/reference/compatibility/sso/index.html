Teams user sign-in

Teams sign-in reaches your bot as an invoke: a token to exchange, or a code to verify. This page records the invokes, the token the SDK exchanges on your behalf, and every claim it checks before it keeps anything. Nothing here was run against a tenant, a registration, a bot or a Teams client.

Recorded 2026-11-12. Everything in this section was read from Microsoft Learn that day; nothing was run against a tenant, a registration, a bot or a Teams client. Cloud: Global only. login.microsoftonline.com is the only authority the SDK builds; a sovereign cloud’s authority is not offered. Account type: work or school accounts of the one configured tenant. The SDK requires the token’s tid to be that tenant, so personal Microsoft accounts (tid 9188040d-6c67-4c5b-b112-36a304b66dad) and other tenants are refused. Permission type for the token calls: Delegated. The SDK requests no permission by default: the scopes are the ones the application names, and a .default scope is refused.

What the SDK does about each

Section titled “What the SDK does about each”
  • Typed and parsed once. The primary adapter reads each sign-in value into TokenExchangeRequest, VerifyStateRequest or SignInFailure through newtypes (ExchangeId, ConnectionName, SsoAssertion, VerificationCode). A value that does not parse is answered 400 and nothing else runs. The invoke names are matched exactly.
  • The answer. The HTTP status is the invoke response’s status and the body is the { id, connectionName, failureDetail } object Learn shows. 412 is the SDK’s choice for “not signed in”; Learn says any status other than 200 makes the client show the card. failureDetail is a fixed sentence chosen by the SDK.
  • Person. The tenant is the one the trust model approved for the activity and the user is the sender’s aadObjectId. The token must agree with both.
  • Audience. Learn says a v2.0 token’s aud is the API’s client id and its tokenExchangeResource page says the token’s audience is the resource uri (the application ID URI). The SDK accepts exactly those two values.
  • Version. Only version 2.0 tokens are accepted, because Learn’s setup sets requestedAccessTokenVersion to 2.
  • The authority. Built from the cloud and the configured tenant when the app is built. A hostile iss, tid or aud is refused before any request is made; a test sends a token naming another authority and asserts the token endpoint saw nothing. Redirects from the token endpoint are refused, because the request body carries the secret; a test asserts a redirect target receives nothing.
  • No token passthrough. The SSO token is the assertion of the on-behalf-of request and goes nowhere else. A test asserts Graph never sees it, and that Graph receives the delegated token.
  • Duplicates. Learn is silent. The SDK’s rule: exchanges for one person run one at a time; a finished id is answered again with its first answer (a remembered 200 only while the session exists); three failures in ten minutes make the SDK answer 412 without calling the identity platform or the application’s hook.
  • State, nonce and PKCE. The fallback uses state (256 random bits, single use, ten minutes, tied to the person who started it), a nonce (see “Who signed in” below) and PKCE S256. Learn’s “Authentication flow for bots” requires the state check and a verification code check against a provisional token; the SDK does both.
  • Who signed in. Learn’s flow pages do not say how to tell that the browser’s account is the account in the chat; a code is redeemed whoever signs in. The SDK adds the OpenID Connect check: it asks for openid profile (and offline_access when the application keeps refresh tokens), sends a separate nonce (256 random bits, one per sign-in, kept server side), and before it keeps anything verifies the returned id token: signature against the tenant’s key set, iss built from the token’s tid, tid equal to the configured tenant, aud equal to the client id, nbf and exp with 60 seconds of skew, nonce equal to the one sent, and oid and tid equal to the person who started the sign-in. Any failure stores nothing and answers one fixed sentence (CallbackRefusal::WrongAccount). The /authorize request is still response_type=code (no id_token response type), so no implicit-grant setting is needed.
  • azp is not read. The id token and access token claims references list azp for v2.0 tokens (the client that requested the token). The SDK does not check it: the access token’s azp is the Teams client that acquired it, and Entra already restricts which clients may obtain a token for the application through the “authorized client applications” list in the registration (the setup step in the SSO guide); a second list in the SDK would drift from the registration and add no protection the registration does not give. For the id token the client is the application itself, whose credential redeemed the code. Row “The SSO token’s claims” lists azp as a claim Learn names, not one the SDK enforces.
  • Failure counts are per route. signin/tokenExchange and signin/verifyState each count three failures in ten minutes independently. A shared count let routine consent failures on the silent route (which is why the card offers the fallback) block verifyState for ten minutes. Learn is silent on any of this; the rule is the SDK’s.
  • The hook runs on every use. The authorization hook is asked on every use and renewal of a session, so withdrawing a person’s access takes effect on their next use (see withdrawing access). Learn says nothing of it; it is the SDK’s authorization rule, not a protocol claim.
  • A timed-out exchange is answered 412 with the documented { id, connectionName, failureDetail } body and a fixed sentence.
  • Bounds the SDK chose. See the table in limits and protections. None is a Microsoft limit.

Inconsistencies in the published pages

Section titled “Inconsistencies in the published pages”
  • The current Teams bot SSO pages describe the Bot Framework Token Service route (an OAuth connection on the Azure Bot resource, token.botframework.com in validDomains), in which the bot never sees the token. The SDK instead validates and exchanges the token itself, following the Microsoft Entra on-behalf-of page. Both start from the same signin/tokenExchange invoke.
  • The pages do not state the signin/verifyState payload. The field name state comes from the Teams SDK reference for SignInVerifyStateValue.
  • Learn’s access-token page says a v2.0 token’s aud is the client id, and the Teams pages say the token’s audience matches the tokenExchangeResource.uri (the application ID URI). Both are accepted.
  • The Learn page for the SSO troubleshooting is at the tab authentication path (tabs/how-to/authentication/tab-sso-troubleshooting); the bot SSO pages link to it. Its bot section is where the invoke payloads are.

Not verified

Section titled “Not verified”
  • No live run. Live acceptance (a configured nonproduction tenant, a registration, a Teams client) is blocked; no row above is a measurement.
  • Whether Teams offers its token for an OAuth card the bot sends itself, and how it renders a card that carries tokenExchangeResource without a Token Service sign-in link.
  • Whether Teams answers or retries a 412 to signin/verifyState.
  • The time Teams waits for the exchange answer. The SDK’s ten seconds is a choice.
  • Personal Microsoft accounts, other tenants and sovereign clouds: refused, not tested.
  • Revocation: the SDK deletes its own session on sign-out; it does not call the identity platform to revoke refresh tokens.
  • Whether the id token the token endpoint returns for a plain response_type=code request carries the nonce sent to /authorize. Learn requires nonce for the hybrid flow and says the claim matches the authorize parameter; OpenID Connect Core says it is echoed when sent; no page states it for the code-redemption id token. If it is absent the SDK refuses every fallback sign-in (fail closed).
  • The refresh-token page calls the id token it returns “unsigned” and shows alg: none; the SDK’s fallback reads only the id token from code redemption, expects RS256, and refuses anything else.
  • The exp of the id token is judged with 60 seconds of skew like the SSO token; Learn states no skew.
