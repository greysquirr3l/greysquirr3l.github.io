Cards and card actions

A card is data, and a card action is an HTTP response your bot writes while handling an inbound request. This page holds the card-action surface, the Adaptive Card builders and their version rules, the message-extension models, and the browser-side surfaces the SDK does not implement. No card has been rendered by a Teams client.

Card actions

Section titled “Card actions”

Recorded 2026-11-05. These rows are the bot’s answers to a card: the SDK receives activities Teams sends and writes a response in the HTTP response of the same request. There is no Graph call, no token and no permission involved, so the permission type is none; the request is authenticated by the inbound authentication rows. Cloud: Global only. Account type: single-tenant registration.

What the SDK does about each

Section titled “What the SDK does about each”
  • Authorization is the application’s, and the default is no. Documented guidance asks the bot to treat the data as client-supplied; the SDK goes further and runs no handler without an allow from the application’s hook. Tests: a missing hook, a tampered object id, an identity claimed in the data, a failing hook, a replay and a race.
  • Bounds the SDK chose. Action data is capped at 64 KiB, a verb at 128 characters, an action id at 256, search text at 512, a data set name at 128, skip at 10,000, response text at 1,000 characters. These are the SDK’s, not Teams limits. The 15-choice cap is Teams’s.
  • Deadline. 10 seconds, configurable, applied to the hook and the handler together.
  • Cancellation. The hook and handler run in one task that is aborted when it passes the deadline or when the request is dropped; the task holds its concurrency permit until it is gone. Cancellation happens at an .await, so a handler can stop between two non-atomic effects, and a task or blocking call it spawned is not cancelled.
  • How long a decision is remembered. The idempotent result lives for 7 days (result_ttl), in memory unless the application opts into SQLite, so it is lost on restart and not shared between instances. The key is the verb and an application-chosen string, not the actor: a second authorized person pressing the same decision gets the replay.

Inconsistencies in the published pages

Section titled “Inconsistencies in the published pages”
  • The type of a card-replacement response is spelled application/vnd.microsoft.card.adaptive in the response table and in the Node and Python samples, and application/vnd.microsoft.adaptive.card in the .NET sample on the user-specific-views page. The SDK uses the table’s spelling.
  • The response table’s rows for 401 and 412 still carry “TODO: needs link” for the error object. The SDK sends the error object the server-handler samples show.
  • The Universal Action Model page is the Adaptive Cards site’s, not Teams’s. The Teams page for Action.Execute defers to it for the request and response formats.

Not verified

Section titled “Not verified”
  • The time budget. None of the pages read states how long Teams waits for an adaptiveCard/action response. The SDK’s 10 seconds is a choice.
  • Statuses outside the table. 403 (denied) and 409 (replay with different data) are not in the documented table (400, 401, 412, 500 plus 200). The envelope says statusCode mirrors HTTP status codes in 200-599; how each client displays them is not verified. The Timeout code is the SDK’s own, sent with 500.
  • The search error response. The documented search response is the 200 body. A denied or failed search is answered with the error envelope and the matching HTTP status (400, 403, 500); how Teams shows that is not verified.
  • msteams Submit variants. The pages read describe plain Action.Submit only. imBack, messageBack, invoke and signin are not routed specially, and what invoke name an invoke-typed submit carries is not confirmed.
  • A submit’s text. That a plain Action.Submit message has no text is inferred from the samples; a message that has text is treated as a message.
  • Refresh end to end. The request shapes come from the documentation. No client has refreshed a card against this SDK.
  • Per-user cache limits. Learn says the client caches the 50 latest cards per user and refreshes only if the last invoke is older than a minute. The SDK does nothing about either.
  • Group chats. Dynamic search in a group chat needs the groupChat scope in the manifest (the page says groupchat); not tested.

What the SDK checks, and what it does not

Section titled “What the SDK checks, and what it does not”

It checks structure, https links, identifiers, the version rules above, size and nesting. The walk reaches into ImageSet, RichTextBlock runs, Table rows and cells, every form of backgroundImage and fallback bodies (on elements, columns, table rows and table cells), and an id must be unique across all of them (a fallback may reuse its own element’s id). It does not look inside a Table’s column definitions or an unknown element type. A link with surrounding whitespace or a control character is refused because the URL parser would otherwise trim or encode it silently. The SDK has no element-count limit: the 1 MiB input cap and the 100 KB card cap bound the walk. It keeps every property it does not understand and says so in Card::notices(). It does not render a card, so it makes no claim about how a card looks on desktop, web or mobile.

Inconsistencies in the published pages, and how the SDK reads them

Section titled “Inconsistencies in the published pages, and how the SDK reads them”
  • Microsoft’s samples write the schema address both as http://adaptivecards.io/... and https://adaptivecards.io/.... A built card writes the http form the Teams sample uses; both are accepted.
  • Two Cards format samples write "version": "1.0.0". The SDK reads major.minor and also major.minor.patch, drops the patch for its own decisions, and keeps the text as written.
  • Some samples have no version (an actions-only fragment). The schema requires one, so the SDK refuses them and says what to add.
  • The Universal Action Model sample writes "fallback": "Action.Submit" as a string, while its backward-compatibility sample writes an object. The builder writes the object form; a string fallback in JSON you supply is kept.
  • The Cards format page shows elements newer than 1.6 (CodeBlock, Icon, Rating, CompoundButton) in version 1.5 samples. The SDK keeps them as unknown elements with a notice and does not claim they render.

Not verified

Section titled “Not verified”
  • Rendering on any client. No card was shown in a Teams desktop, web or mobile client. Nothing here is a statement about layout or truncation.
  • Media in Teams. The schema defines it from 1.1; the pages read do not say whether Teams renders it. Cards carry a notice.
  • The UTF-16 byte count of a card inside an activity. The 100 KB figure is documented for a bot message; the SDK applies it to the card alone and the Connector client applies it again to the whole activity.
  • Behaviour of a 1.2-declared card with Action.Execute on current Teams clients. The Universal Action Model page describes it; it was not run.
  • Action.ShowCard inside Teams. The schema defines it; the pages read do not list it for bot cards.
  • Whether an Input.* value comes back under its id for every client.
