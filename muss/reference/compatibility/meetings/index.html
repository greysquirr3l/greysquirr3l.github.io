Meetings and presence

Meeting events arrive over the Bot Connector, and the reads that follow are Connector calls too; presence is Graph. This page records both, and the resource-specific consent permissions that decide what a bot may read in a meeting. No call has been made to a real tenant.

Everything in this section was read from the pages named, on 2026-11-11, in the public cloud with a work or school account. No call was made to a real tenant: every body in the tests and the example is a sample from those pages, served by a loopback server. See meetings and presence for the guide.

The reads have no Graph API version: they are Bot Connector calls under the activity’s service URL, authenticated with the bot’s Connector token, and use the same destination check and pinned addresses as a send. The RSC permission names are in the RSC catalog (read 2026-11-11), which describes OnlineMeeting.ReadBasic.Chat and OnlineMeetingParticipant.Read.Chat as app-only or delegated-or-app-only and ChannelMeeting.ReadBasic.Group as app-only.

Facts the SDK relies on, and how:

  • The meeting id is channelData.meeting.id. The page says “Do not use conversation ID as meeting ID” and “Do not use meeting ID from meeting events payload activity.value”. The start and end samples on the page carry value.Id and no channelData.meeting, so an event built from them names no meeting id and a read from it fails with MeetingIdMissing.
  • Response codes for the participant read: 200 retrieved, 401 invalid token, 403 “Get participant information isn’t shared with the app. If the app isn’t installed in the meeting, it triggers the error response 403. If the admin disables or blocks the app”, 404 “the meeting has either expired or participants aren’t available”. The details section lists none, and the SDK reads the same statuses the same way.
  • Do not cache participant roles: the organizer can change them at any time. The SDK holds none.
  • No retry. A read is not repeated. A 429 returns Throttled with the delay the service asked for.

Inconsistencies in the pages, and how the SDK reads them:

Inconsistency Reading
The start and end sample value uses Pascal case (Title, JoinUrl, MeetingType, StartTime, EndTime); the TypeScript sample on the same page reads camel case Both spellings are accepted.
value.Id of the event versus channelData.meeting.id Only channelData.meeting.id is a meeting id; value.Id is not read.
The one-to-one call sample has the key "organizer " and the participant sample "role ", each with trailing spaces Read as typos and not matched: the organizer or role is absent, never guessed. Unverified against a live answer.
The page describes the join and leave payload value.members[0] only Every member is read, up to 256. A list that is absent, empty or longer is refused.
The bot’s own join event has no aadObjectId (the TypeScript sample skips it for that reason) A member without a directory id is delivered; the handler tells the bot from a person by it.

Transcripts and recordings are not offered. The Graph Get callTranscript page (read 2026-11-11) shows the read needs OnlineMeetingTranscript.Read.All (or OnlineMeetingTranscript.Read.Chat for scheduled private chat meetings, application only), an application access policy that a tenant administrator creates and grants to a user, and two further tenant administrator settings that decide which transcript formats may be read (text/vtt fails with 403 SpeakerAttributionNotAllowed where speaker attribution is disallowed). The SDK cannot check or grant any of these, and a live tenant was not available to prove the reads, so it offers no operation rather than an unverified one. The recording read has its own page, which was not read.

The request rate is 1,500 requests in 30 seconds per application per tenant. The page’s third example, GET /communications/presences/{id}, shows its answer as a value array while the other two show one object; the SDK does not offer that form. POST /communications/getPresencesByUserId (up to 650 ids) is not offered either: the SDK never repeats a POST, which is the wrong rule for a read. The presence status message, work location and the write operations (set, clear) are not modelled.

The availability values the page lists are Available, Away, BeRightBack, Busy, DoNotDisturb, Focusing, InACall, InAMeeting, Offline, Presenting and PresenceUnknown; the activity values are Available, Away, BeRightBack, Busy, DoNotDisturb, Offline, OutOfOffice and PresenceUnknown. The page’s own example shows the activity Presenting, so neither set is closed: a value the SDK does not name is kept as Other.

The get and delete pages carry a presence paragraph (when includeResourceData is true, encryption is required and creation fails without encryptionCertificate and encryptionCertificateId) but no permissions row. The SDK does not borrow Presence.Read.All from the create and update pages for them (re-read 2026-11-11); the delegated client is still required before anything is sent.

Facts from Get change notifications for presence updates and the subscription resource type (read 2026-11-11):

  • Lifetime: 60 minutes. A single user may have one presence subscription per application. A subscription is renewed with the update call before it expires, or created again after it does. The keeper plans a renewal half way through the hour, because its lead time is capped at half the remaining life, and a renewal asks for another 60 minutes.
  • Resource: one user. communications/presences/{id}, where {id} is the user’s GUID. The bulk form communications/presences?$filter=id in (...) (650 users) is not offered.
  • Change type: updated only.
  • Lifecycle URL. The lifecycleNotificationUrl is required for Teams resources when the expiration is more than one hour away. A presence subscription never is, so the URL is optional; set it anyway to hear of a reauthorizationRequired notification. subscriptionRemoved is listed for Outlook and Teams chatMessage only, so the SDK does not expect it for presence; a lapsed presence subscription is found by its expiry or by a 404 on renewal.
  • Resource data: advised, enforced locally. What Learn says, re-read 2026-11-11. The create page’s presence section: “Subscriptions on presence require any resource data included in a change notification to be encrypted. Always specify the encryptionCertificate parameter when creating a subscription to avoid failure.” The update, get and delete pages say, under a presence heading: “In that case [includeResourceData set to true], encryption is required and the subscription creation fails if an encryptionCertificate and encryptionCertificateId aren’t specified.” So the failure Learn states is conditional on includeResourceData: true; the create page’s advice to always specify the certificate is not worded as a rule. The presence notification page documents a basic notification (the user, no state) and says to set includeResourceData to true with both certificate fields “to subscribe to rich notifications”. A basic presence subscription is therefore documented; the SDK still refuses to create one (SubscriptionError::ResourceDataRequired, before anything is sent), because the create page advises always specifying the certificate “to avoid failure” and a wrong guess would only show up against a live tenant. This is the SDK’s conservative choice, not a stated service rule, and no live tenant has tried a basic presence subscription. The SDK creates the subscription with includeResourceData, the certificate and its id; the id is stored on the subscription record and bound when notifications are opened. Rotating means creating the subscription again with the new certificate. Basic presence notifications that arrive are still delivered.
  • Delegated only. A client that is not delegated is refused before anything is sent (UnsupportedCapability). The keeper renews with the delegated client it was built over, so the user’s token has to be available every time a renewal is due. In the facade, give the webhook that token with TeamsApp::graph_delegated_tokens; without it GraphWebhooks::watch refuses a presence subscription (WatchError::DelegatedClientNotConfigured) and a lifecycle notification for one is reported to the recovery hook as blocked.

Not verified

Section titled “Not verified”
  • No call was made to a real tenant, so none of the above is live evidence. The acceptance step that asks for the advertised paths in a configured tenant is blocked: no tenant, bot registration or meeting was available.
  • The percent-encoding of +, / and = in the meeting id path segment. Learn shows the path without one; the SDK encodes the three characters so the id stays one path segment. Not seen against a live service.
  • Whether details.id always equals the requested id. The SDK does not compare them.
  • Whether Developer Portal’s “Meeting event subscriptions” has a manifest equivalent. The SDK cannot check it.
  • The permission the participant read needs.
  • Live delivery of presence notifications: the service was not asked to send one, so the rich payload’s field names beyond the page’s example, whether it ever sends a basic one to a subscription made with a certificate, and whether it sends an identifier are unconfirmed.
  • The permission the get and delete subscription calls need for presence: the pages state none.

Resource-specific consent

Section titled “Resource-specific consent”

Resource-specific consent (RSC) permissions are app-only and consented at the resource, not by a tenant administrator. The scope of a team-scoped RSC permission extends to all of that team’s channels, except private and shared channels, where it extends only to channels where a user has explicitly added the app. Read from Resource-Specific Consent for Teams Agents and Apps on 2026-11-03.

Permission Grants Scope
TeamsActivity.Send.Group Send activity-feed notifications to users in this team Team
TeamsActivity.Send.Chat Send activity-feed notifications to users in this chat Chat
TeamsActivity.Send.User Send activity-feed notifications to the user User
ChannelMessage.Read.Group Read and receive all of this team’s channel messages Team
ChannelMessage.Send.Group Send messages to this team’s channels Team
ChatMessage.Read.Chat Read and receive all of this chat’s messages Chat
TeamMember.Read.Group Read this team’s members Team
TeamsAppInstallation.Read.Chat Read the apps that are installed in this chat Chat

Three details recorded on the same page, read 2026-11-03:

  • TeamsActivity.Send.Group, TeamsActivity.Send.Chat and TeamsActivity.Send.User are the “basic” RSC permissions: any user consents to them simply by installing the app.
  • The TeamsActivity.Send RSC application permission is always enabled at the tenant level; app users do not need administrator consent for it.
  • App-only RSC requires app manifest version 1.6 or later.

The ChannelMessage.Read.Group and ChatMessage.Read.Chat permissions are the ones that let an app receive messages it was not mentioned in. Without them, a bot in a channel sees only the messages that mention it. Read from Configure an Agent to Receive All Messages in Group Chats and Channels on 2026-11-03.
