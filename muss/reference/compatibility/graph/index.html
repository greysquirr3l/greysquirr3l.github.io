Microsoft Graph surface

Microsoft Graph is a separate service from the Bot Connector, with its own permissions, and the two do not imply each other. This page records every Graph endpoint, version and permission the SDK uses: messaging, activity-feed notifications, change notifications, subscriptions, directory reads and app installs. No live Graph endpoint has been called.

Every Graph row below is v1.0. No beta endpoint is advertised in v1.

The pages do not say whether the service checks that a channel belongs to the teamId, so the SDK does not claim to; a wrong channel is the service’s answer.

The entityUrl resources differ per endpoint, and none is inferred from another: a team takes team, channel, chatMessage or teamsTab; a chat takes chat or chatMessage; a user takes teamsAppInstallation or teamsCatalogApp. For a team and a chat the pages say the URL must be the resource in the request path or a child of it, and the app must be installed in it. The SDK enforces the first part before any request: the URL must be https://graph.microsoft.com/v1.0/... (the global host only; no port, credentials, query or fragment; a national cloud is not advertised), and its decoded path segments must begin with teams/{teamId} or chats/{chatId} for the identifier in the call. For a user the pages state no relation to the user in the path, so the SDK requires only the supported shapes, users/{id}/teamwork/installedApps/{id} or appCatalogs/teamsApps/{id}. The installation requirement is the service’s to enforce; the SDK does not install the app or probe for it, and an absent installation reaches the caller as the service’s error. The Graph-level test for that case uses a fixture response written by the test, not a recorded one.

The reserved systemDefault type takes one template parameter, systemDefaultText, which carries the free text shown in the Actor+Reason line (Send Teams activity notifications, example 8 and “Reserved activity types”, verified 2026-11-10). The SDK requires that parameter, non-blank, and refuses any other parameter for this type. The overview page does not state a length limit for the text, so none is invented here beyond the SDK’s own 1024-character value bound.

Not implemented: POST /teamwork/sendActivityNotificationToRecipients, and the beta-only custom iconId path. Both are out of scope for this task.

What the SDK checks before it sends

Section titled “What the SDK checks before it sends”

The manifest is the source of truth for the activity type. An activity type the manifest does not declare is refused before any request goes out, as is a template parameter set that does not match the template the activity type declares. A deep link is refused unless it is an HTTPS address on teams.microsoft.com and has one of the shapes Teams publishes: /l/chat/, /l/message/, /l/channel/, /l/team/, /l/loopthread/ or /l/entity/teamsapp/. The activity-feed page (Send activity feed notifications, fetched in full 2026-11-11) states only that webUrl must start with the Teams domain, and its examples use /l/message/ and /l/loopthread/. The Teams deep-link page (Deep link to a Teams chat, fetched in full 2026-11-11) documents /l/chat/, /l/channel/, /l/team/, /l/message/ and /l/file/. No /l/meeting/ shape appears on either page, and /l/file/ is documented as a file link rather than an activity topic, so neither is accepted.

Subscription lifetimes

Section titled “Subscription lifetimes”

The service gives each resource a maximum lifetime, and refuses to create or renew a subscription beyond it. Read from subscription resource type on 2026-11-10:

Resource Maximum lifetime What the SDK does
Teams chatMessage (/teams/{id}/channels/{id}/messages) 4,320 minutes (three days) The default lifetime, and the ceiling it refuses to go past
Teams chatMessage (/chats/{id}/messages) 4,320 minutes (three days) The default lifetime, and the ceiling it refuses to go past
presence (/communications/presences/{id}) 60 minutes The default lifetime, and the ceiling it refuses to go past; delegated clients only

The SDK subscribes to those two paths and to one user’s presence only. The service documents many more resources (chat, channel, conversationMember, team, onlineMeeting, the tenant-wide getAllMessages paths); each has its own lifetime, permission table and lifecycle behaviour, and the SDK models one only once its contract has been read and tested. A path outside the three is refused before any request goes out, as is a $search or $filter query on them.

Two request rules, from the same page and from Get change notifications for messages in Teams channels and chats (read 2026-11-10):

  • An expiration under 45 minutes after the time of the request is moved up to 45 minutes by the service. The SDK refuses such a request rather than let the answer differ from the request.
  • A Teams subscription whose expiration is more than one hour away requires a lifecycleNotificationUrl, and the service fails the request with “lifecycleNotificationUrl is a required property for subscription creation on this resource when the expirationDateTime value is set to greater than 1 hour”. The SDK refuses it before sending. The URL cannot be added to an existing subscription by an update, so a subscription created without one is renewed for an hour at a time, not for the resource maximum. Exactly 60 minutes needs no lifecycle URL.

What the SDK checks, from the page’s “How to validate” and “Decrypting resource data”:

  • Origin. Every token in validationTokens is read and every one must pass: RS256 only (none, HS*, every other algorithm refused before a key is looked up), the key named by kid fetched from the fixed address above (never from the token: jku, x5u, jwk are ignored, crit refused), signature, exp/nbf (60 s skew) judged at the moment the notification was received, aud equal to this app’s id, the caller identity (appid for ver 1.0, azp for ver 2.0) equal to 0bf30f3b-4a52-48df-9a82-234910c4a086, and iss equal to https://sts.windows.net/{tid}/ or https://login.microsoftonline.com/{tid}/v2.0 for the token’s own tid. One token’s tid must equal the notification’s tenantId. The page says a failing token makes the whole delivery suspicious, so one bad token drops every rich item of the request.
  • Client state first. The page’s step “validate clientState” for basic notifications still runs at intake, before anything is quarantined: a token is a bearer value a stranger could replay with forged items, the client state is the secret that ties an item to a subscription.
  • Certificate. encryptedContent.encryptionCertificateId must equal the id the subscription was created with and name a key the app holds. Several keys can be held at once, which is the documented overlap during rotation.
  • Unwrap, verify, decrypt. dataKey is unwrapped with RSA-OAEP, SHA-1, MGF1-SHA-1 (RSA/ECB/OAEPWithSHA1AndMGF1Padding), must be 32 bytes; the HMAC-SHA256 of data under it is compared in constant time with dataSignature before anything is decrypted; then AES-256-CBC with PKCS#7 and an IV of the first 16 key bytes. The result must be a JSON object whose id and @odata.type agree with resourceData.
  • Bounds. Standard strict base64; data is whole AES blocks and at most 64 KiB (the queue record limit); the wrapped key is 256 to 512 bytes; at most 16 tokens of 8 KiB; cryptography runs on blocking threads, at most as many at once as handler workers.

Live check of the key set on 2026-11-11 (public, unauthenticated GET, no tenant involved): https://login.microsoftonline.com/common/discovery/v2.0/keys returned 8 RSA keys with use: sig, kid, n, e, x5c; the address the discovery document names (.../common/discovery/keys) returned 6, all of which are also in the v2.0 set. The SDK uses the v2.0 address, the superset.

Decisions and gaps, stated rather than hidden:

  • Rotation uses new subscriptions. The rich-notification page says to PATCH encryptionCertificate and encryptionCertificateId; the update page lists only expirationDateTime and notificationUrl as updatable, and its request-body rule says one of those two must be present. The pages disagree, so the SDK does not send a certificate in an update. To rotate: hold both keys, create new subscriptions with the new certificate, and retire the old key once no notification names it.
  • SHA-1. The OAEP parameters are the service’s. Nothing else in the SDK uses SHA-1.
  • Validation tokens are not bound to the body. The page describes a token as proof the request came from the service for this app and tenant; nothing in it names the items it travels with. The clientState check at intake is the only body binder, and the SDK keeps it first. A token replayed inside its lifetime (about one day) cannot be detected, because the SDK keeps no record of tokens seen.
  • One audience. Tokens must name this app’s id. A notificationUrl shared by several apps, each with tokens for itself, is unsupported.
  • Thumbprint. DecryptionKeys::with_thumbprint registers the certificate thumbprint with the key and a notification that reports a different one is refused. The subscription record stores none: the certificate id is the link to the subscription, and the thumbprint is checked against what was registered at key-load time. Not registering one leaves only the id check.
  • Key size. The SDK reads the RSA modulus length from the DER itself, for private keys (PKCS#8) and for certificates, so the bound does not depend on what the crypto library will load. A key of 512 to 2,047 bits is reported as KeySize (certificates: UnsupportedKey); the 2,048-bit minimum is tested at 1,024, 2,047 and 2,048 bits and the 4,096-bit ceiling at 4,096 and 4,608 bits, all with OpenSSL-made fixtures, and the DER reader has synthetic tests for boundary sizes with leading zeros, trailing data, indefinite and over-long lengths, and lengths larger than the buffer. aws-lc then parses the key again, so a reader bug can only give a wrong error or a false refusal, never accept a key the library would not.
  • Size. A rich notification must fit the 64 KiB queue record with its tokens; a larger one is dropped and reported (Refusal::TooLargeToQueue). The real size of a Teams message notification is not measured.
  • Scope. Teams chatMessage on the two watched paths. The typed ChatMessage view covers documented properties of the chatMessage page; everything else is in ResourceContent::json.
  • Token ver and issuer. The Learn samples show a v1.0 issuer (sts.windows.net) in the C# sample and a v2.0 issuer in the example token. Both forms are accepted for the token’s own tenant; which a real token uses for this service is unverified.
  • Not verified against a live tenant. No real rich notification, real validation token or real certificate registration was used. The payload vector was made with the OpenSSL command line; the example tokens are minted locally. Unverified: that appRoleAssignmentRequired handling behaves as the page says; the exact lifetime of a rich chatMessage subscription (the lifetime table gives 4,320 minutes and no separate rich value for Teams); the service’s refusal text for a certificate it rejects; Windows run.

Subscription lifecycle notifications

Section titled “Subscription lifecycle notifications”

Read 2026-11-10 from Reduce missing change notifications and removed subscriptions:

Event Sent for What the SDK does
reauthorizationRequired All resources Renews with one PATCH /subscriptions/{id}, which the page documents as reauthorizing and renewing in one request
subscriptionRemoved Outlook message, event, personal contact, and Teams chatMessage Marks the subscription removed and tells the recovery hook; the SDK does not recreate it
missed Outlook message, event, personal contact only Tells the recovery hook if one arrives; the service does not document it for Teams chatMessage

The page asks that POST /subscriptions/{id}/reauthorize and PATCH /subscriptions/{id} are not both issued for one subscription within ten minutes. The SDK only ever sends the PATCH, and sends no second write to a subscription inside ten minutes of the last accepted one. A reauthorization does not extend the subscription unless the PATCH does, and the SDK’s PATCH always does. The standalone reauthorize action is not implemented.

The page says changes made while delivery was paused are lost, and suggests a delta query. These pages document no delta query for Teams message resources, so the SDK promises no replay or resync: it hands missed and subscriptionRemoved to the application’s recovery hook, which decides how to re-read the resource with the ordinary list calls.

The renewal rules: 429 honours Retry-After (capped at one hour), 401 and other transient failures back off from 30 seconds doubling to 15 minutes with up to 25 percent jitter, five failures stop the schedule and tell the hook, 403 stops it at once as a missing permission, and 404 marks the subscription lapsed because it cannot be renewed. A renewal sets an absolute expiry, so repeating one whose result is unknown is safe.

The delivery contract, read from Receive change notifications through webhooks on 2026-11-03:

  • The service considers a notification delivered once the endpoint returns a 2xx within 3 seconds. A non-2xx or a timeout inside that window starts a retry that continues for up to 4 hours, with the retry request timeout extended to 10 seconds.
  • An endpoint is marked slow when more than 10% of responses exceed the 3-second allowance in a 10-minute window. New notifications are then delayed by 10 minutes.
  • An endpoint is marked drop when more than 15% of responses exceed the 10-second retry allowance in a 10-minute window. Notifications are then dropped for a 10-minute window.
  • Validation-token requests must be answered within 10 seconds.
  • If the access token expires, notifications are not delivered, and this does not count against the endpoint’s throttling state; Graph keeps retrying for up to 4 hours.

Throttling, read 2026-11-10 from Receive change notifications through webhooks: “An endpoint is marked ‘slow’ once more than 10% of responses take longer than the 3-second timeout allowance in a 10-minute window”, after which “any new notifications are sent on after a 10-minute delay”; it is marked “drop” once more than 15% of responses take longer than the 10-second retry timeout, and notifications are then dropped for 10 minutes. Dropped notifications cannot be recovered. This is why the SDK bounds what happens before the answer: the acceptance deadline defaults to 2.5 seconds, at most concurrent_requests (8) requests persist at once and the rest are answered 503 at once, and the body read is cut off at body_timeout (5 seconds, 408). A 503 is a non-2xx answer inside the window, which Graph retries for up to 4 hours; the page does not say whether a 503 counts toward the 10 percent, so the SDK cannot promise it does not. Not tested against a live service.

The same page’s “Firewall configuration” section says: “You can configure the firewall that protects your endpoint to allow inbound connections only from Microsoft Graph, reducing further exposure to invalid change notifications. For a complete list of IP addresses used by Microsoft Graph to deliver change notifications, see additional endpoints for Microsoft 365” (source, which links additional endpoints for Microsoft 365, read in full 2026-11-10). The SDK recommends this allow-list beside concurrent_requests; it does not enforce it, and the ranges themselves were not fetched or checked here. The host has no header-read timeout or connection cap, so an edge limit is expected in front of it.

The ingress adds no permission and no beta resource. It receives what a subscription made under the contracts above delivers.

What the pages say, and what the SDK does with it:

  • Handshake. POST ...?validationToken={opaque}; the endpoint must answer within 10 seconds with 200, text/plain and the URL-decoded token, which must not be encoded; the token is opaque and its format can change; “escaping any HTML or JavaScript is a good practice” but a returned token must be plain. The SDK returns the decoded token verbatim as text/plain; charset=utf-8, with nosniff, and bounds it (2 KiB token, 8 KiB query). Plus-as-space follows form decoding; the page does not say whether Graph encodes a space as + or %20, so both are handled. Not verified against a live Graph.
  • Acknowledgment. A 2xx within 3 seconds is delivery; otherwise retries for up to 4 hours at a 10 second timeout; “validate and persist the notification in a queue … and return 202 Accepted within the 3-second window”; “return a 5xx class code” if it was not processed or queued. The SDK answers 202 after the durable write, 503 plus Retry-After otherwise, and caps persistence at 2.5 seconds by default (never over 2.9).
  • Client state. “Validate the clientState property … If there’s a mismatch, don’t consider the change notification as valid.” The page gives the maximum length as 255 on the notification; the SDK accepts 128 on creation, so an echoed value over 128 cannot match and the item is dropped.
  • Fields. id is optional, tenantId, subscriptionId, resource and subscriptionExpirationDateTime are required, changeType and lifecycleEvent are mutually exclusive, and unknownFutureValue is a sentinel the SDK drops. validationTokens appear only with resource data. The SDK requires tenantId and resource on a change item.
  • Inconsistency. The Teams page’s sample gives subscriptionExpirationDateTime as 2021-02-02T10:30:34.9097561-08:00, with a numeric offset. The SDK reads only the Z form and leaves the field out otherwise rather than refuse the notification or misread the instant.
  • Replies. The pages read show message resources only. The SDK also accepts .../messages('id')/replies('id') under a watched channel; that form is not verified.

Not verified: any live delivery; whether Graph encodes a space in the validation token as + or %20; how Graph treats a 202 that arrives after 3 seconds; the reply resource shape; the size of a real rich notification against the 64 KiB queue record limit (an item over it is dropped and reported, not truncated).

The client’s own rules, which are the SDK’s and not Microsoft’s:

  • Destination. Requests go to the configured root only. A request holds a method, a version, a path and a query, so it cannot name a host. Redirects are refused, and the final URL’s origin is checked again before the token is attached.
  • Escape hatch paths. A path is /-separated segments of A-Z a-z 0-9 . _ ~ - $ @ ( ) ' , =, with no empty segment, no . or .., no %, no :, at most 1024 characters. This is the SDK’s restriction and is stricter than Graph’s: colon-delimited drive-item addressing is not reachable. A query name may not look like a credential (access_token, token, sig, client_secret, and so on); values are percent-encoded so a value cannot end its parameter.
  • No permission contract for raw requests. The SDK does not know what an endpoint sent through request needs. A 403 from one says so, and the caller must read that endpoint’s own page.
  • Authority. The application client presents a token minted from the registration’s credential for the Graph audience. The delegated client presents the token its provider hands in, after checking only that it has not expired. The SDK never decodes a token, never requests consent and never widens a grant.

Not verified (and not relied on):

  • A live Graph answer. Every body here is a sample from the Learn pages, served by a loopback server. Nothing has called graph.microsoft.com.
  • Response headers. The pages fetched do not say that Graph returns request-id or echoes client-request-id as response headers. The SDK takes the request identifier from innerError.request-id and from x-ms-request-id / x-ms-correlation-id when present, and records the client-request-id it sent.
  • A throttle on a write. The throttling page says throttled requests “fail”; the SDK reads that as “not run” and repeats a write after a 429. If that reading is wrong for some service, a write could run twice.
  • A 202 Accepted from GET /users/{id}. The page says the method can return it; whether it carries a user body is not stated. The SDK treats the body as it would a 200’s and reports a body it cannot read as accepted but unusable.
  • Permission names in a token. A delegated token’s scopes are not read, so a missing scope is found out by the service’s 403.
  • DNS pinning. The Graph host is a fixed public name resolved by the system; there is no address vetting to pin, because no request supplies a destination.

What the SDK does about each, and what it leaves out:

  • No bulk enumeration. There is no call that lists every user, team or chat of the tenant. directory.user.by-mail is a $filter equality with $top=2; directory.teams.joined is one named user’s teams; the member and installed-app lists are of one team, channel, chat or scope. Every walk stops at the client’s page and item limits with an error.
  • Users. A user is named by object id or by user principal name, and the caller says which (UserRef); a string is never guessed. A guest’s principal name holds #EXT#, which Learn says needs %23 in a URL; the SDK builds paths from plain segments, so it refuses such a name and points to the object id and to the mail address. A name starting with $ is sent as users('<name>'), the form the page gives. A soft-deleted user is not an active user: GET /users/{id} answers 404, and deleted_user reads /directory/deletedItems/{id} and refuses an item that is not a user. userType is read when present; a response without it and without #EXT# is Unspecified, not Member.
  • Members. roles holds owner and guest as the resource page says. Pages can repeat a membership when it changes mid-walk; the walk drops a membership id it already returned and reports the count. diff_memberships compares two snapshots.
  • Identifiers. Entra application id (AppId), manifest id (ManifestId, Graph’s externalId), catalog id (TeamsAppCatalogId, Graph’s teamsApp.id) and installation id (TeamsAppInstallationId) are four types. The installation id is refused in GUID form. A Graph chat id (19:...@thread.v2, @unq.gbl.spaces) and a Graph channel id (19:...@thread.tacv2) are ChatThreadId and ChannelThreadId, refuse each other, and are not Bot Framework conversation ids.
  • Install and uninstall. Only with an InstallApproval made from the exact request, naming who approved, carrying an idempotency key and consumed by the call. The SDK sends only teamsApp@odata.bind; it never sends consentedPermissionSet, so it cannot grant resource-specific permissions. The write permissions are the least privileged ones the pages list (the Self ones); the pages do not say they are limited to the calling app, and a 403 for another user is the service’s answer, which the SDK reports. A write whose answer is lost is not repeated and its key is refused afterwards. The AppInstalls memory is per client, in process, and holds at most 1,024 keys.
  • Not reachable from notify or doctor. The notifier, the Connector client and the CLI doctor hold no Graph client. Tests read their sources and the doctor’s Azure CLI calls.

Not verified

Section titled “Not verified”
  • No call was made to a live tenant. The response shapes come from the Learn examples; the loopback tests prove the SDK’s requests and parsing, not the service’s behaviour.
  • Learn does not document the error body of an install of an app that is already installed. The SDK reports any 409 as Conflict and says what it does not know.
  • Whether $select=userType is returned with User.ReadBasic.All is not documented, so the lookups send no $select.
  • Learn documents $filter=teamsApp/externalId eq on the user, team and chat installed-apps pages (Example 3), but says externalId is empty for a store app, whose teamsApp.id is the manifest id. The SDK sends no $filter on those lists: it walks them within the page limits and matches externalId or teamsApp.id. The catalog request uses externalId eq ... or id eq ..., because the catalog page lists or among the filter operations. Verified against the pages fetched in full on 2026-11-11 (not truncated).
  • externalId is the manifest id chosen by the app author. A sideloaded or organisational app can declare the manifest id of another app, so an installed-apps match by externalId shows what the app claims, not who published it. The SDK does not check distributionMethod for installations (Learn defines it on the catalog teamsApp). Before trusting a match, verify distributionMethod, the catalog id and the publisher against the catalog entry that was approved; a mismatch means a different app.
  • The team install page says 200 OK; the user and chat pages say 201 Created. The SDK accepts any 2xx.
  • Installation ids with + or / would need percent-encoding the SDK does not do. The ids Learn shows hold letters, digits and =.
  • Upgrading an installed app and consentedPermissionSet are out of scope.
