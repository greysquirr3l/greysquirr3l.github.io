Inbound activity authentication

The Bot Connector service calls your bot, and the bot has to decide whether to believe it. This page records the inbound surfaces muss-teams reads, the seven checks the SDK applies to every inbound token, and the places where the SDK deliberately differs from the reference SDKs. It continues the Bot Framework surface table on the index page.

The direction that matters for a bot: the Bot Connector service calls the bot, and the bot has to decide whether to believe it. The rows below are the inbound surfaces muss-teams reads.

The published key set size was measured from the live endpoint on the verification date rather than read from a Learn page, because no page states it. The figure is what the SDK has to cope with: the cache holds 1,024 keys and the key-set fetch reads up to 4 MiB, so the published set fits with room to grow. The shared response limit for every other call stays at 1 MiB.

The Learn page states seven verification requirements for the inbound token - the Authorization header scheme, the JWT shape, the issuer, the audience, the validity period, the signature and the serviceUrl claim - and adds that “implementers shouldn’t expose a way to disable validation of the JWT token that is sent to the bot”. muss-teams implements all seven and exposes no switch that turns any of them off.

Where the tenant and the request properties come from

Section titled “Where the tenant and the request properties come from”

The Learn page lists only aud, iss, nbf and exp in its example Connector-to-bot token and adds that “actual fields may vary in practice”. It does not document a tid claim. muss-teams therefore does not depend on one:

  • The tenant is read from the activity body, from conversation.tenantId or channelData.tenant.id. Both appear in the activity payloads on the Teams “subscribe to conversation events” page (read 2026-11-04). If both are present they must agree, and an activity that names neither is refused.
  • A tid claim in the token is checked when it is present: it must equal the activity’s tenant, or the request is refused as a tenant mismatch. A token without one is judged on the activity’s tenant alone.
  • The tenant allowlist and the registration’s tenant rule are applied to the activity’s tenant.
  • Unverified: whether real Connector tokens carry tid has not been observed against a live tenant. The behaviour above is correct either way. Also unverified against a live tenant: that every Teams activity carries one of the two tenant fields. Both stay open until the live acceptance task.
  • The body property names are the wire names serviceUrl and channelId. The token claim is read as serviceurl, the spelling the Bot Framework SDKs stamp; the Learn page writes serviceUrl. A token that spells the claim only as serviceUrl is refused rather than guessed at.
  • Claim values are compared exactly. A value with surrounding whitespace is malformed, not trimmed into a match.
  • The body is limited to 1 MiB by default before it is parsed, because it arrives before the sender is authenticated.

Key freshness

Section titled “Key freshness”

The Learn page says “all bot instances should refresh their local cache of the document at least once every 24 hours” (read 2026-11-04). The SDK’s default max_age is one hour, deliberately stricter: a retired key stops being trusted sooner, and a set past its age is never served. A lookup past the age refetches, and if that fetch fails the lookup fails with KeyError::Unavailable and the request is refused; the stale keys are not used as a fallback. A stale set also never counts as the current generation, so a miss against one earns a fetch even when the unknown window is configured longer than the age. The tests are in the key cache and the staleness test.

Known limitations of the inbound boundary

Section titled “Known limitations of the inbound boundary”

  • The tenant can come from the unsigned body. When a token carries no tid, the tenant is the activity’s conversation.tenantId or channelData.tenant.id, and the body is not covered by the token’s signature. A captured valid token could therefore be replayed, for the token’s lifetime, with a different tenant in the body. The tenant allowlist and the registration’s tenant rule still apply to whatever tenant the body names, and a tid claim, when present, must match it. This is a property of the protocol as documented, not something the SDK can close alone.

  • DNS pinning is closed for Connector sends, and only there. The Connector client connects to the addresses its destination gate approved, proved by a test in which the host name does not resolve at all (see outbound Connector messages). authenticate() still returns the addresses it approved, and no consumer uses them: a send resolves and checks again at send time. Any later outbound surface (Graph, file transfer) must pin the same way and prove it; none does today.

  • A key-set outage is not backed off. A failed fetch is not cached, so during an outage each request that needs a key makes one attempt. The single-flight keeps concurrent requests to one fetch.

  • A rejected request reaches no handler, store or outbound call. T10 wired a router, a state store and a queue behind the boundary, and the claim is now proved by tests rather than by absence: the rejection test sends eight kinds of refused request (no token, forged token, wrong channel, wrong tenant, wrong service URL, not JSON, oversized, authentic but not an activity) and asserts that the store was called zero times, nothing was queued, no handler or reply ran and the dispatcher’s counters are untouched.

Deliberate deviations from the reference behaviour

Section titled “Deliberate deviations from the reference behaviour”
Behaviour The reference muss-teams Why
Channel endorsement “The list of channel IDs that require endorsements is configurable within each bot. By default, it will be the list of all published channel IDs” Always required, with no setting to disable it The same page says a way to disable validation should not exist. A configurable list that can be emptied is that way.
Missing endorsement HTTP 403 (Forbidden) HTTP 403 Matches the page. The check is not a credential problem, so it is not a 401.
Channel and tenant allowlists The reference SDKs expose them as per-bot settings Default-deny allowlists, opt in to Any The project posture is default-deny. A bot that has not been told which channels or tenants it serves refuses them all.
Sovereign clouds “Sovereign clouds use separate Azure infrastructure with different service endpoints for authentication, token services, and bot communication”; the Teams SDK configures a different OpenID metadata URL, token issuer and signing keys per cloud Refused at configuration time This SDK has not wired or verified the sovereign OpenID metadata URL, issuer and signing keys. IngressDeployment::new refuses a cloud other than the commercial one rather than accepting traffic it cannot check.
