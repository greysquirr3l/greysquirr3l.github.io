Platform policies and retirements

Four things a team adopting muss-teams needs to know that are not about one capability: what the Microsoft retirements do and do not affect, how cards meet different clients, what the SDK keeps about a tenant and for how long, and how upgrades and migrations are handled.

The Bot Framework retirements, stated exactly

Section titled “The Bot Framework retirements, stated exactly”

Two different things were retired or archived. They are easy to confuse, and the SDK depends on one and not on the other. Both pages below were read in full on 2026-11-12 (neither was truncated).

Item What Microsoft says What it means here
Bot Framework SDK and Bot Framework Emulator Archived on GitHub; “no longer updated or maintained”. Support tickets for the Bot Framework SDK are no longer serviced as of December 31, 2025. The page recommends the Microsoft 365 Agents SDK, the Teams SDK, or Microsoft Copilot Studio for new work. muss-teams does not use the Bot Framework SDK libraries and has no dependency on them. It implements the activity protocol and the Connector calls directly. The Emulator is not part of the workflow: the offline recipes use SimulatedTeams, which signs requests the bot then verifies.
Office 365 connectors in Teams, including connector-based Incoming Webhooks “Retired in May 2026.” To receive webhook requests and post messages, “use the Workflows app”. muss-teams never posted through an Incoming Webhook URL. It sends with the bot’s own credential through the Connector. Nothing in the SDK needs migrating off connector webhooks.
Bot Framework Connector REST service Not retired. The Connector API reference is still published (its page was last updated on 2026-11-05) and says the REST API “isn’t equivalent to the SDK” and is provided for standard REST communication. The only retirement it mentions is the Bot Framework State service, in 2018. This is the service muss-teams talks to for replies, updates, deletes, conversations and members. It is in scope.

Sources:

  • What’s new for the Bot Framework SDKs, verified 2026-11-12.
  • Create and send messages, verified 2026-11-12.
  • Bot Framework Connector service REST API reference, verified 2026-11-12.

The matrix rows with these facts, from 2026-11-03, are in the compatibility matrix.

Workflows is a different product

Section titled “Workflows is a different product”

The Workflows app (Power Automate) is Microsoft’s replacement for connector webhooks: a flow with the “When a Teams webhook request is received” trigger posts a message to a chat or channel. Microsoft’s page notes that a workflow is linked to its owners, not to a team or channel, that it can become orphaned if its owner leaves, that it supports private channels, and that a MessageCard payload renders but cannot carry interactive HTTP POST buttons.

It is not the SDK’s bot transport and muss-teams does not call it. Use Workflows when a system that cannot hold a bot credential needs to post one message; use muss-teams when you need a bot identity, interactive cards that call back into your code, conversations that persist, or the other capabilities in the offline recipes. The same page suggests proactive bot messages as the path for an app that already has a Teams app. That is the standalone-notify recipe.

Client and card compatibility

Section titled “Client and card compatibility”

The SDK builds and checks Adaptive Card JSON. It does not render, and Microsoft’s pages do not give a per-client support table for every element.

  • The builder declares the lowest card version that carries what the card uses: 1.0 for text only, 1.3 once a label is added, 1.4 for an execute action. The highest version it lets a bot card declare is 1.6 (see Adaptive Cards).
  • To keep an older client working, declare a lower version and give newer elements a fallback. build() names the JSON path of anything that needs a newer version than the card declares.
  • A card over 100 KB, nested deeper than 32 levels, or declaring a version Teams does not render for a bot is refused before it is sent.
  • Action.Execute is answered in the HTTP response of the same request. Action.Submit arrives as a message, with no response channel. See Card actions.
  • Not verified: how each Teams client shows a 403, 409 or timeout error from a card action. Microsoft’s table covers only 400, 401, 412 and 500. No press in any test came from a real client.
  • Not verified: rendering on desktop, web and mobile. Test every card on the clients you support. Adaptive Cards in link unfurling are limited to 1.3, per the compatibility matrix.
  • Windows is a supported host for the SDK and the command-line tool; the CI workflows that would run the Windows build have not run on a runner yet. See the CI runbook.

Tenant retention

Section titled “Tenant retention”

Nothing is kept forever by default, and every stored row is keyed by tenant.

Data Kept for Holds Removed by
Conversation references and per-tenant records The store’s default of 24 hours, at most 30 days (a longer request is shortened) Identifiers needed to message again Expiry, sweep_expired, purge_tenant
Idempotent results 7 days replayable The recorded result of a state-changing request Expiry, purge_tenant
Notification attempt records The store’s default Identifiers and a digest, never message content Expiry, purge_tenant
Outbox entries Until sent or abandoned The message itself, because it must be sent later Delivery, purge_tenant
Graph poison records 7 days (poison_retention) The failed notification’s identity Expiry
Graph rich notifications awaiting verification 24 hours (quarantine_retention) The item, held unverified Verification, then expiry
Subscription records The subscription’s remaining lifetime plus a short grace period The resource, its plan and the client state, which is a secret Expiry, purge_tenant

An uninstall or a privacy request is Retention::purge_tenant, which deletes every row held for that tenant and returns the count. The in-memory store is lost when the process ends. The SQLite store persists until you delete the file or run the sweep; it is bounded by expiry and not by a row count, so run SqliteState::sweep_all_expired on a schedule.

Payloads are stored in the clear. Never put tokens, client secrets or keys in the state store; use a secret store. The client state in a subscription record is a secret and the store holding it must be protected like a credential. Details in tenant-scoped state.

The SDK does not control the tenant’s own retention. Messages that people post in Teams are governed by the organisation’s Microsoft Purview retention policies, which the SDK neither reads nor changes.

Upgrade and migration policy

Section titled “Upgrade and migration policy”

The workspace is at version 0.1.0. No crate has been published, so no upgrade path has been exercised by a user yet. The policy below is what the code is built to honour.

  • Toolchain. Rust 1.99.1, edition 2024, pinned in rust-toolchain.toml with rust-version set in the manifest. A change of the baseline is a deliberate, recorded change and is never done by an unpinned update.
  • Before 1.0. A minor version may change the public API. Each such change is listed with the reason in the commit that makes it, and the examples and the locked v1 contract change in the same commit.
  • From 1.0. The facade follows semantic versioning. Feature names and the names in the locked v1 contract are the contract; a rename is a breaking change. MussError and TeamsError are #[non_exhaustive], so a new variant is not breaking for a caller who matches with a wildcard arm.
  • Stored state. The SQLite schema version is in PRAGMA user_version. Migrations apply in order, each in a transaction. A shipped migration is never edited; one is appended. A database written by a newer library is refused with SchemaTooNew, so a rollback cannot silently corrupt it. Keep a copy of the file before you upgrade.
  • Subscriptions. A subscription record written by an older version keeps its client state and plan. An upgrade does not recreate subscriptions; restart the process and the next sweep renews what is due.
  • Manifest. The SDK validates against manifest schema 1.29. muss-teams manifest validate reports a field the schema does not know. Re-run it after upgrading before you upload a package.
  • Microsoft’s side. Each row in the compatibility matrix has a verification date. A release that changes a row re-reads its source page and updates the date in the same commit. A page that drops a cloud or adds a beta marker is a breaking change to the SDK’s promise.
  • Migrating from the Bot Framework SDK. The activity protocol is shared. A message handler becomes on_message, a card action becomes on_card_action, and a proactive message uses a stored ConversationReference; the handler bodies still have to be rewritten against the typed contexts. Dialogs, extensions and meeting events have typed handlers in the offline recipes. State that the old SDK kept in its own storage has to move to your store; the Bot Framework State service was retired in 2018 and the SDK does not read from it.
