The locked v1 contract

This is the locked v1 contract for muss-teams. It is the surface a developer writes against; everything below the facade is an implementation detail they should never need to name.

The contract is derived from docs/dev/API-DESIGN.md and the capability contracts, and the exact Microsoft endpoints each capability may touch are recorded in the compatibility matrix. Where this document and compatibility.md disagree about a protocol detail, compatibility.md wins, because it is the one that was read from Microsoft Learn on a dated basis.

One dependency

Section titled “One dependency”

A normal application depends on muss-teams, plus Tokio and whatever domain crates the application already has.

muss-core is an ordinary transitive dependency. Its types stay behind the facade unless they are deliberately re-exported, so an application normally never names it.

The root of muss_teams re-exports the concrete values a Graph, meetings or directory app builds with, so those apps name only muss_teams:: paths:

Re-export Feature Why an app names it
TenantId, ClientId, Audience, AuthContext none The subscription keeper, the stores and the recovery hook take an AuthContext, built from the tenant, the app registration and the token audience.
MemoryState, MemoryLimits, MemoryLimitsError none The in-memory store for development, and the bounds TeamsApp::memory_limits takes: rows, bytes and a per-tenant share; docs/state.md.
SqliteState sqlite The durable store that survives a restart.
StateTime none The “now” the stores and the keeper take.
Manifest, ManifestId, read_manifest none The activity-feed publisher checks an activity type against the manifest; the app-install request names a manifest id.
TeamId, TeamsAppCatalogId none Directory lookups and app installs address a team and a catalog entry.

Store traits, the transport and the adapters, application and domain modules are not re-exported for this purpose: an application that implements its own store or transport is writing a lower-layer integration and says so.

Feature names

Section titled “Feature names”

Feature names are part of the contract. A rename is a breaking change.

Feature Default Effect
bot-runtime on Inbound bot activities, handlers, and the Connector transport.
cards on Adaptive Card builders, actions, and card responses. Builders compiled in, not gated (T13).
auth on Safe authentication: credential providers, token acquisition, audience separation.
http-host on The built-in HTTP host: run(), run_until(), BuiltApp::router() and serve(). Declared.
dev-storage on In-memory storage for local development.
graph off Microsoft Graph: ApplicationGraph and DelegatedGraph, bounded paging, throttle and OData-error handling, and a path-only request escape hatch. Typed operations arrive with the task that needs each one (today: read a user, list users, read the signed-in user, publish an activity-feed notification, and create, read, renew and delete change-notification subscriptions). Adds no dependency. Declared (T16). See docs/graph.md. T24 adds directory() (read-only lookups of users, teams, channels, chats, members, the app catalog and installed apps) and app_installs() (install and uninstall, each needing an InstallApproval made for that request); see docs/directory.md.
sqlite off Persistent SQLite storage instead of in-memory. Declared.
test-utils off muss_teams::testing: a test supplies its own signing keys, clock and Connector destination. Authentication still runs in full. Never enabled in a production build. Declared (T12).
sso off Teams sign-in: silent SSO (signin/tokenExchange), a sign-in fallback with state and PKCE, sealed per-person sessions, and the delegated token feed for UserSession::graph() (which also needs graph). Adds no dependency. Declared (T22). See docs/sso.md.
files off File listing and upload flows.
tracing-exporters off Exporter wiring for tracing telemetry.
cli off The optional muss-teams setup binary as a library feature.

Only http-host, sqlite, graph, sso and test-utils are declared in the manifest today. The bot runtime, the card builders, safe authentication and in-memory storage are always compiled in (the builders add no dependency, so there is nothing to gate; a cards feature would only exist to switch off the card responses of a later task), and the other features arrive with the tasks that own them (scripts/ci/feature-matrix.sh gaps lists them). The lean, outbound-only combination is --no-default-features, which leaves out the HTTP host: Cargo features only add, so it is a combination and not a feature of its own.

The default set is the bot runtime, card builders, safe authentication, HTTP hosting, and in-memory development storage. Everything that needs a Graph permission, a real database, or a tenant consent step is opt-in, so that cargo add muss-teams does not imply a permission grant the developer has not asked for.

The optional CLI is a separate binary crate, muss-teams-cli. It must never be required at runtime.

The builder and the running app are different types

Section titled “The builder and the running app are different types”

The single most important ownership rule: a client handle never starts a server, and dropping a client never stops a running app.

Type Owns Clone? What happens when it is dropped
TeamsApp Configuration and registered handlers. No Nothing. Nothing was started.
BuiltApp The authenticated pipeline and its worker pool. No The workers are aborted. Call shutdown to let them finish.
TeamsClient A handle to the outbound pipeline. Yes, and cloning is cheap and inert. Nothing. The running app is unaffected.

Change from the first draft of this contract (T12). The draft named a RunningApp that owned the bound listener. There is no such type. run and BuiltApp::serve own the listener for exactly as long as the server runs and shut the app down when it stops, so a long-lived listener handle would only be another thing to forget to drop. What an application can hold is a BuiltApp: it owns the worker pool and no socket, which is what an existing host needs.

Because TeamsClient is a separate type from BuiltApp, a developer cannot accidentally shut down their bot by dropping a client, and cannot accidentally start a server by handing a client to a function. BuiltApp::shutdown(grace) is the explicit way to stop, and it returns only after in-flight work has drained or been aborted at the grace limit. If a router from router() is still alive it returns Error::StillInUse instead of hanging.

A notification-only client never needs to start a web server. It still needs credentials and a valid installed destination or conversation reference.

The two entry paths

Section titled “The two entry paths”

build() starts the worker pool on the current Tokio runtime and nothing else. run() builds the same pipeline and then binds the configured address and serves until Ctrl-C. Both paths use the same handlers and the same client. A host that is not Axum calls BuiltApp::handle(authorization, body). See facade.md.

Hello world

Section titled “Hello world”

No required custom traits, no required procedural macros, no required unsafe code. examples/hello.rs is 11 nonblank lines including the entry point and its doc comment (9 without the comment), against a budget of 25; a test enforces the budget and another keeps this number true. A line counts when it holds anything but whitespace, and comment lines count.

from_env() loads and validates configuration. It does not disable authentication and it does not grant any permission. A missing or misspelled secret is an error, never a silent fallback to a weaker credential.

Configuration

Section titled “Configuration”
Variable Required Meaning
TEAMS_APP_ID yes The application (client) id of the bot’s Entra registration, a GUID.
TEAMS_TENANT_ID yes The Entra tenant id, a GUID. A domain name is refused, because an activity names its tenant by GUID.
TEAMS_CLIENT_SECRET yes The client secret. from_env reads the client-secret credential; a missing secret is an error, never another credential.
TEAMS_CREDENTIAL no client-secret, the default. certificate and managed-identity are refused with a pointer to with_credentials.
TEAMS_BIND_ADDR no The address to bind. Defaults to 127.0.0.1:3978: a bot is reached through an HTTPS front end, and listening on every interface by default would publish a plain-HTTP endpoint nobody asked for.

Credentials are an explicit choice, never inferred:

A misspelled or omitted secret does not cause the SDK to reach for managed identity. It produces a configuration error that says which variable is wrong.

The managed identity credential asks whichever identity service the host runs, and the host names it: a virtual machine runs the instance metadata service, while App Service and Azure Functions run a local token service and publish its address in IDENTITY_ENDPOINT. The application does not choose, and does not have to know which host it is on.

Typed contexts

Section titled “Typed contexts”

Every handler receives a typed context. The context carries the identity of who did what, and it never exposes the raw JSON envelope.

Context Handler Carries
MessageContext on_message The conversation, the sender, the tenant, the message text and attachments.
CardActionContext on_card_action The actor, the card the action came from, and the payload, read with ctx.data_as::<T>().
InstallationContext on_installation_update The scope the app was installed into.
ConversationUpdateContext on_conversation_update What changed in the conversation, and who caused it.
MeetingSummaryContext on_meeting_start / on_meeting_end The meeting’s title, type, join link and actual start or end, and meeting_target() for reads.
MeetingParticipantsContext on_meeting_participants_joined / on_meeting_participants_left The participants, their roles and whether they are in the meeting.
MeetingContext on_meeting Any meeting event with no handler of its own, as MeetingEvent.
GraphChangeContext on_graph_change The changed resource, its version, and its tenant.

The context types are distinct on purpose. A GraphChangeContext is not a MessageContext and cannot be used where one is expected, because a Graph change event is not a reply-capable bot context. See Notification APIs for why that distinction matters.

Cards

Section titled “Cards”

Card::builder(), ctx.reply(card) and .execute(..) are implemented (T13; see cards.md), and so are the button-press types above (T14; see card-actions.md).

Registration is .on_card_action("approve", approve), and a bot that registers card handlers must also register .authorize_card_actions(..): without it every action is denied, because the data on a card is the client’s. The SDK cannot decide who owns an approval, so it asks.

Changes from the draft this section first held, recorded because the contract was locked:

  • CardActionContext is not generic. The draft’s CardActionContext<Approval> would have made the context type depend on the handler, which is the generic parameter stack the contract forbids. The data is typed at the call that needs it: ctx.data_as::<Approval>()?.
  • The handler returns Result<CardResponse, E> for any error type, like every other handler, and CardResponse::replace takes &Card.
  • The authorization hook is a required step, not a comment. It defaults to deny.
  • ctx.once(..) is the idempotency step. The key is derived from the verb and a string the application chooses, not a UUID the application mints, because a button press carries no identifier of its own.

.execute() uses the documented Action.Execute and adaptiveCard/action transport internally, so the developer never writes an invoke envelope or handles the invoke timeout rules. The library resolves the transport; the developer handles the business authorization and the business transaction.

Hidden card fields are client-controlled. They are not permissions. A payload on a card proves only that the client sent it. Every production handler must re-authorize the actor against the server’s own state.

CardResponse::replace(&card), CardResponse::message(text) and typed protocol errors replace hand-written statusCode/type/value JSON. Card builders cover common layouts and inputs with autocomplete. Validation errors name the offending field, for example body[1].id, and say what the fix is. Raw Adaptive Card JSON and unknown properties are supported for forward compatibility.

The four notification APIs

Section titled “The four notification APIs”

This is the part a developer must not have to read protocol documentation to get right. There are four different things, they come from three different Microsoft services, and they are reached through four different Rust methods.

You want to… Use Rust call Microsoft service Delivery
Post a message into a conversation your bot is in Bot messaging client.notify(target, card) Bot Connector service A message in the chat or channel
React to something that happened inside a conversation Inbound bot events app.on_message(handler) Bot Connector service, inbound A handler runs on your server
Notice that a resource changed outside a conversation Graph resource changes app.watch_channel_messages(target, handler) Microsoft Graph change notifications A handler runs on your server
Raise an alert in the Teams activity feed Activity-feed alerts client.activity_feed().send(...) Microsoft Graph activity feed A feed item, not a chat message

The rule behind the table: a reply, an event, a change and an alert are four different things. Two of them arrive at your server; two of them leave it.

1. Bot messaging — outbound

Section titled “1. Bot messaging — outbound”

notify means a bot conversation message. It resolves a stored conversation reference, or opens one only where Teams allows it (a one-to-one chat with a person who has the app installed, a new thread in a channel of a team that has it), and returns a [Notified] with the message’s handle. It returns actionable NoConversationReference, AppNotInstalled or MessageWritesBlocked errors rather than silently escalating permissions or claiming a delivery that did not happen. A bot with no authorize_notifications hook refuses every notification, and a send whose answer is lost is reported as ambiguous and never repeated for you. See notifications.md.

Changes from the draft this section first showed (T15): the tenant is the app’s own, so Target does not carry one; the arguments are borrowed (&target, &message); an update is client.update(&handle, &bot, &message) using the handle in sent, not a method on the result; and the constructors are Target::conversation (an existing chat, group chat or channel thread), Target::user / Target::user_by_object_id and Target::channel_post. An email address or a UPN is not interchangeable with a Teams id or an Entra id, and notify does not resolve a human-readable name.

2. Inbound bot events — inbound handlers

Section titled “2. Inbound bot events — inbound handlers”

These handlers run when the Teams client or platform sends your app an activity. They arrive over the Bot Connector service, and the same authentication covers them.

By default, bots do not receive every group or channel message. An explicit receive-all-human-messages preset declares the RSC permissions it needs and explains the reinstallation and consent steps. Messages authored by other bots are not delivered by that setting. Reading other bots’ messages is a separate Graph path, and only where it is authorized.

3. Graph resource changes — inbound handlers over Graph

Section titled “3. Graph resource changes — inbound handlers over Graph”

A Graph subscription reads like that. This differs from the first draft (app.watch_channel_messages(target, handler)): a handler is registered once with on_graph_change, and what to watch is a SubscriptionRequest that declares the resource and its lifetime, so the permission each resource needs stays in the typed contracts rather than in a second spelling of them. It is an opt-in feature, and it never subscribes to all tenant messages by default.

The subscription API itself is shipped: SubscriptionKeeper::watch creates a subscription and records it in one call (the happy path), and graph.subscriptions() creates, reads, renews and deletes one without recording it, for two resources (one channel’s messages, one chat’s messages). A watch whose record write fails returns WatchError::NotRemembered, which names the subscription that now exists at the service. SubscriptionOwner keeps what was created and the plan for it in tenant-keyed durable state (the client state in it is a secret: protect the store like a credential), and SubscriptionKeeper renews what is due under a version-checked lease and passes what it cannot repair to an application RecoveryHook. The SDK starts no renewal timer: the application calls sweep on its own timer.

The inbound handler is shipped. TeamsApp::on_graph_change registers it and turns on two URLs, GRAPH_NOTIFICATION_PATH and GRAPH_LIFECYCLE_PATH, which answer the validation handshake and accept notifications. A handler gets a GraphChangeContext (a GraphChange and the attempt number) only after the item matched a subscription this app created: client state (constant time), tenant, application and resource. The request is answered 202 after the item is in a bounded durable queue, and 503 with Retry-After when it is not. A handler that fails is retried and then set aside as poison; lifecycle items go to SubscriptionKeeper::handle_lifecycle; rich items (encrypted content) are quarantined unverified and reach only the on_graph_resource handler, after their validation tokens, certificate and data signature check out (graph_decryption_keys, DecryptionKeys, RichChangeContext, SubscriptionRequest::with_resource_data). The worker is owned by the BuiltApp and joined by shutdown. on_subscription_recovery, on_graph_fault and graph_webhook_limits configure it; see graph.md.

A Graph change event is not a reply-capable bot context. It carries the resource, its tenant, its resource identity, the delivery identity where the platform provides one, and resource version metadata. It does not invent a cross-source event id, and it does not promise exactly-once delivery. A notification with an id is deduplicated; one without is delivered each time and the handler must be safe to run twice (documented in graph.md).

4. Activity-feed alerts — outbound

Section titled “4. Activity-feed alerts — outbound”

An activity-feed notification is a separate builder with a manifest-declared notification type and a Teams deep link. It appears in the Teams activity feed. It does not post a message into a conversation, and it does not arrive as a handler call.

Decision (T17, 2026-11-10): the shipped spelling is graph.activity().to_team, .to_chat and .to_user, not client.activity_feed().send(...). The sketch above is the design intent; the shipped form differs for three reasons. A feed notification needs Graph credentials, and the graph feature is where those live (ApplicationGraph and DelegatedGraph), so the entry point sits on the Graph client rather than on the bot client. The three endpoints differ in permission, topic and recipient rules, so one send would hide the choice the caller must make, and the SDK refuses a mismatch by target instead of guessing. And a card is not an input: the service renders the notification from the manifest template, so the body is an ActivityNotification, not a card. The separation from client.notify(...) holds: they are different clients, so no call can deliver both. docs/graph.md shows the shipped form.

The SDK never silently sends both a chat card and a feed alert. If you want both, you make two calls and you own the consequence. The SDK also does not promise a banner, a sound, or a read receipt: client settings and platform behavior govern what the user actually sees.

Picking the wrong one

Section titled “Picking the wrong one”
Symptom Probably the wrong API
You want to appear in the conversation the user is looking at Bot messaging, not activity feed
You want a red entry in the activity feed Activity feed, not bot messaging
You want to know when someone edited a document in a channel Graph change, not an inbound bot event
You want to know what a user typed in a channel Inbound bot event (mentions) or Graph change (all messages)

Setup that fails helpfully

Section titled “Setup that fails helpfully”

The optional CLI provides five commands:

Command What it does What it must never do
muss-teams setup Walks the operator through creating the Entra registration, the bot service principal, the credential, the Graph permissions and the app manifest. It shows the whole plan first and changes nothing without --apply. Run without --apply, publish a multi-tenant bot to the Partner Center, install the app in a tenant, or send a test message.
muss-teams init Writes a minimal example, .env.example, a manifest template, and an exact setup checklist. Create cloud resources, grant consent, install apps, or post test messages.
muss-teams manifest validate Validates an app manifest against the documented schema. Change the manifest.
muss-teams package Assembles the app package. Publish or submit anything.
muss-teams doctor Read-only diagnosis of the local setup. Mutate anything.

setup is the one command that changes a cloud resource, and it is the one that has to be asked twice: once to show the plan, once with --apply to run it. Every step it would take is printed before any of them is taken, and the steps that a tenant administrator has to agree to say so in the plan rather than in a failure later.

doctor is read-only by default, redacts credentials, and distinguishes a wrong app id, a tenant mismatch, an expired secret, an unconfigured messaging endpoint, a missing installation, and missing Graph permissions where the service exposes enough evidence. Where it cannot verify something, it says so rather than reporting a guess.

Anything that mutates a cloud resource is a separate explicit operation, never a side effect of init. setup is that operation, and it is opt-in twice over: no --apply, no change, and a plan the operator can read first.

Glossary

Section titled “Glossary”
Term What it is Where to get it
Teams app id The id of the Microsoft 365 app package. The app manifest, or muss-teams doctor.
Entra client id The application (client) id of the Entra registration. The Entra app registration.
Tenant id The Entra tenant. The Entra app registration overview, or the domain’s Get-TenantId.

These identifiers are not interchangeable. A Connector conversation id is not a Graph chat id, and an Entra client id is not a Teams app id. The SDK uses distinct types for them so that a mix-up is a compile error rather than a runtime 404.

Boundaries of “full integration”

Section titled “Boundaries of “full integration””

v1 covers the Teams server-side application surfaces: bot messaging and events, proactive notifications, interactive cards, Graph subscriptions and the activity feed, dialogs, message extensions, authentication, directory and install helpers, meeting metadata and events, and presence.

It does not claim that every Microsoft Graph endpoint is implemented.

Not in v1 Why
File upload, download and consent No file flow is implemented. A card may carry a link to a file, and an attachment may name one, but the SDK neither uploads nor downloads bytes and it does not answer a fileConsent activity.
TeamsJS and other browser-side APIs A tab or meeting side-panel frontend runs in the browser and uses TeamsJS. The SDK is the server side: it authenticates the activity, answers the invoke, and keeps the state. The frontend is the application’s own work.
Graph beta endpoints Only v1.0 is advertised.
Sovereign clouds Advertised only after their own compatibility tests pass.
Cross-tenant operation v1 is single-tenant.
