Performance and resource bounds

Master-list IDs followed: PERF-01, 02, 03, 08, 11, 12; LEAK-01 to 05; MEM-13. Everything here was measured on one machine (below). Nothing is a throughput claim for other hardware, and no number is a Microsoft service latency: every downstream in these runs is a loopback stand-in that answers after a delay the run chose.

Builds

Section titled “Builds”
  • cargo bench uses [profile.bench]: release code generation, thin LTO, one codegen unit, full debug info, strip = "none". (bench inherits release, which strips; without the explicit strip = "none" the symbols would be thrown away at link time.)
  • cargo build --profile profiling builds the same code for a profiler.
  • The library sets no global allocator, passes no target-cpu, and keeps panic = "unwind". The only counting allocator (dhat) is installed by the alloc_budget test binary for itself.

Where things live

Section titled “Where things live”
What Path
Shared harness (mock downstream, signed bot, percentiles, metadata) crates/muss-teams/perf_support/
Criterion benches crates/muss-teams/benches/workloads.rs, surfaces.rs
Open-loop latency percentiles crates/muss-teams/benches/latency.rs
Allocation-count gate and live-block check crates/muss-teams/tests/alloc_budget.rs
Overload, retention, rotation, capacity crates/muss-teams/tests/perf/
Live descriptor and task gauges (soak, webhook flood) crates/muss-teams/tests/perf_gauge/
Structural rules (hasher, leak APIs, spawn sites) tests/hash_policy.rs, tests/leak_policy.rs
Stored baselines crates/muss-teams/perf_baselines/*.json

cargo test --workspace --all-features --locked runs the allocation gate and the perf, perf_gauge_soak, perf_gauge_metric and perf_gauge_webhook tests; they take a few seconds. MUSS_SOAK_SECONDS=600 lengthens the cancel-and-restart soak.

Each gauge test lives in a binary of its own because the descriptor gauge counts the whole process’s descriptor table. A budget taken from one test only holds while no other test in the same process is holding a socket, and cargo runs the tests inside a binary in parallel. A sibling test’s runtime is created before its body runs, so it exists while the gauge holds its lock and moves the count the gauge asserts on; one binary per gauge is what keeps that from happening. Measured on a busy machine with eight busy threads: the earlier layout, with both gauge tests beside ten others in one binary, failed 17 runs out of 40; split into their own binaries, they failed none.

Profiling without Unix-only tools

Section titled “Profiling without Unix-only tools”
  • macOS and Linux: samply record target/profiling/<binary> (install with cargo install samply), or Instruments on macOS. Build with --profile profiling; for a bench, cargo bench --no-run leaves a binary with symbols under target/release/deps/.
  • Windows: the same profile builds a .pdb next to the binary. Record with Windows Performance Recorder / ETW, open in WPA, and load the .pdb. samply also runs on Windows. Do not rely on perf.
  • Allocation sources: dhat (see alloc_budget.rs for the pattern). The standard library ships without debug info, so a profile that ends inside std is the floor.
  • Nothing here has been run on Windows or Linux yet; the commands are the documented route, not a result.

Measured baseline

Section titled “Measured baseline”

Only the allocation counts are a gate. alloc_counts.json is read by tests/alloc_budget.rs, so a regression in allocation blocks the build. The Criterion and latency files are reference data: no test reads them, so a performance regression in them is visible only when a person compares them. Treat the tables below as a record of one machine on one day, not as a threshold the build enforces.

Machine for every number below: Apple M3 Pro, 11 logical CPUs, 36 GiB, macOS, rustc 1.99.1, bench profile, features graph test-utils sqlite http-host. The machine was shared and busy (one-minute load average 10 to 16 on 11 CPUs while measuring; it is stored in each file). Repeat runs of the same benchmark differed by up to 2x (rich-notification open: 363 to 562 microseconds), so treat each figure as an order of magnitude and re-baseline on a quiet machine before using any as a gate. The stored files hold means, confidence intervals and medians.

Budgets

Section titled “Budgets”

Chosen from the observed data, for this machine class, as limits a regression should not cross without review:

  • Acknowledgement p99 under 5 ms at 400 per second with an instant downstream (observed 5.8 ms on a loaded machine; the target is a quiet one).
  • No allocation count above its stored baseline plus tolerance.
  • Live resources after cancel and restart: tasks and descriptors at or below the starting level, every cycle.
  • Shutdown within its grace period plus 3 seconds.

Capacity of the default in-memory state

Section titled “Capacity of the default in-memory state”

Each delivery leaves a de-duplication mark for the replay window (1 hour). The memory store holds 10,000 rows and one tenant may hold 90 per cent of them (9,000), so the default bot admits about 9,000 deliveries in a window and refuses the rest. That is a sustained rate of about 2.5 deliveries per second per hour; measured, 8,999 were admitted (one other row is a conversation reference) and the rest were refused. The refusal is 503 with Retry-After: 30, because the marks expire and the same delivery succeeds later; it was a 500 before this task.

A busier bot raises the bound with TeamsApp::memory_limits:

The bounds are checked when the app is built: rows 16 to 1,000,000, bytes 64 KiB to 1 GiB, tenant share 1 to 100 per cent. A store that is full still refuses and never evicts a live row. The limits apply to the memory store; asking for them together with sqlite is a configuration error, because SQLite is bounded by expiry and not by count (sweep it on a schedule).

The tenant share is what keeps one tenant from starving the others: a tenant at its share is refused while the other tenants still write, and the store as a whole stays under its cap. Rows of every kind count: records, queued outbox entries and idempotent results, against both rows and bytes. At 100 per cent the tenants compete for the whole store. Pinned in tests/perf/capacity.rs, tests/perf/retention.rs and tests/state_memory.rs.

Leak audit

Section titled “Leak audit”
ID Finding
LEAK-01 cycles No Weak back-references exist and none were needed. Arc cycles are tested end to end by the live-block check across three bot lives.
LEAK-02 leak APIs None in library code; leak_policy.rs bans forget, Box::leak, ManuallyDrop, into_raw.
LEAK-03 caches Token cache (32, LRU), key cache (1,024 keys, 1,024 unknown ids with expiry), pinned clients (cleared at cap), install memory (1,024), state stores (entry and byte caps), dispatcher and webhook queues (configured depth). Defects fixed below.
LEAK-04 channels All mpsc channels are bounded; unbounded_channel is banned by test.
LEAK-05 tasks Every spawn site is pinned in leak_policy.rs with its owner. One defect fixed below.

Defects found and fixed, each with a failing-first test:

  1. Memory state kept expired rows until the store filled (LEAK-03). A write now releases expired rows at most once a minute, so a dead row can hold its place in memory for up to one full sweep interval after it expires. The store still refuses a write when the table is full rather than evicting a live row.
  2. CollectingSink (telemetry) grew without bound (LEAK-03). Bounded to 1,024 reports by default, counting what it drops.
  3. FairScheduler kept a slot for every tenant ever seen (LEAK-03) and scanned them linearly. It was fixed, then deleted with the rest of muss-core’s fair queue, which nothing in the tree used.
  4. The meeting authorization hook was a detached task if the caller stopped waiting (LEAK-05). It now lives in a JoinSet, which aborts on drop.
  5. A full state store answered 500 (see Capacity above).

Also noted: muss-core::adapters::secondary::queue (FairQueue, FairScheduler, QueueHandle) had no consumer in the library, the tests, the benches, the examples or perf_support. The project rule is to delete such primitives, so the module and its tests were removed.

Hashing audit (MEM-13)

Section titled “Hashing audit (MEM-13)”

Every HashMap and HashSet in library code uses the standard RandomState (keyed SipHash 1-3); BTreeMap is used for key-id maps. No FxHash, ahash, fnv or fixed-key DefaultHasher exists in source or in a manifest, and tests/hash_policy.rs keeps it that way. rustc-hash appears in Cargo.lock only through a target-specific dependency that cargo tree does not reach. dhat (a test-only dependency) uses its own hasher internally; that is the profiler, not the SDK.
