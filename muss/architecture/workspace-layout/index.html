Workspace layout

The repository is the Cargo workspace. There is no umbrella crate and no separate workspace root manifest elsewhere in the tree.

Package Kind Path In-tree consumer Depends on
muss-core library crates/muss-core muss-teams, the only consumer —
muss-teams library crates/muss-teams muss-teams-cli, the workspace examples and the integration tests muss-core
muss-teams-cli binary crates/muss-teams-cli the operator muss-teams, so muss-core transitively

The list is exhaustive. Adding a member requires a new ADR.

muss-core — shared M365 primitives

Section titled “muss-core — shared M365 primitives”

Infrastructure only, and only what muss-teams calls today:

  • tenant identity and AuthContext;
  • credential providers and audience-separated token clients;
  • pooled bounded HTTP transport with a retry policy;
  • the shared error taxonomy;
  • UUID-v4 IdempotencyKey;
  • secret redaction;
  • telemetry hooks.

Nothing in that list is Teams-specific. A Teams identifier, an endpoint, a scope, a payload shape, a card model or an adapter does not belong here. A primitive with no in-tree caller is deleted rather than kept for a hypothetical second crate: “a future muss-* crate might want it” is not a caller.

muss-teams — the product

Section titled “muss-teams — the product”

Everything an application programs against: the Teams identifiers, the protocol contracts, the Adaptive Card models, the bot runtime, the Graph surfaces, and the public facade.

This is the crate an application depends on. muss-core arrives as an ordinary transitive dependency, and its types stay behind the facade unless they are deliberately re-exported — and a deliberate re-export is documented as public API.

muss-teams-cli — an optional binary

Section titled “muss-teams-cli — an optional binary”

init, manifest validate, package, setup and doctor. A developer convenience, never an application dependency: no library in the workspace depends on it, and no application should. It is also not required at runtime.

The crate on a registry would be muss-teams-cli; the installed command is muss-teams. The two are different things, and neither is a crate name to put in a Cargo.toml.

muss-core is infrastructure, not a ports module

Section titled “muss-core is infrastructure, not a ports module”

This is the rule most likely to be got wrong, so it is worth stating precisely.

muss-core holds shared infrastructure. It does not hold port traits. The application use cases in muss-teams keep owning their own narrow inline port traits. No use-case trait ever moves into muss-core, and there is no shared trait registry.

The distinction matters because a shared ports crate is where a framework grows. Once the ports of every use case sit in one crate, they can be re-exported, extended, and made to satisfy each other, and the crate becomes the API that every application must learn — which is exactly what the one-dependency promise forbids.

There is no top-level ports module in any package either. A use case that owns several ports may group them in a file beside itself, and the Graph client does that in application/graph/ports.rs, but the file belongs to that use case alone.

Three rules follow from it:

  • A muss-teams use case keeps its port trait where the use case lives.
  • muss-core gains a primitive only when a named in-tree caller in muss-teams needs it.
  • A primitive whose caller disappears is deleted, not relocated and not kept “for later”.

Naming

Section titled “Naming”

Crate names follow muss-<item>, where <item> is the Microsoft 365 item the crate serves. muss is the workspace name and the project name; it is not a published crate name, and there is no crate for an M365 item that has not been implemented.

Module names follow the same discipline. utils, helpers, common and shared are not permitted, and ports is reserved against.

The reasoning is recorded in ADR 0003, and the internal layout each package uses is described in the architecture overview.
