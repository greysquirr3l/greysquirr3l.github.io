Architecture overview

Every package in the workspace has the same internal shape:

The dependency rule is that the arrows point inward. A primary adapter calls into the application layer, the application layer calls into the domain, and the domain calls nothing. Secondary adapters implement the ports the application layer declares.

Collapsed hexagonal, with DDD-lite inside it

Section titled “Collapsed hexagonal, with DDD-lite inside it”

The design is a hexagon with the walls taken out, and a DDD-lite domain inside it.

Collapsed hexagonal means there is no abstract “port and adapter” split applied to the whole system. Each use case declares the one or two ports it actually needs, as a trait local to the module that consumes it, and the adapter that implements it lives in the same crate. There is no shared ports module, no shared trait registry, and no interface that exists only because a diagram wanted it. The ports are where the use case is, and the adapters are what the platform looks like.

DDD-lite means the domain is a real domain layer with real invariants, held to a stricter rule than a typical DDD codebase: the domain has no traits of its own. Not “no repository traits” — no traits at all, with one deliberate exception noted below.

The tension this resolves: a plain hexagonal architecture invites a large interface surface that every adapter must implement and every test must mock. Collapsing it keeps the abstraction at the size of the use case.

The one exception

Section titled “The one exception”

muss-teams’s domain holds exactly one trait: TokenProvider, the seam an application implements when its credential lives somewhere the SDK cannot see — a vault, a certificate store, a token broker. The SDK asks for a token for an audience and never learns where the token came from.

It is there because it is public API rather than an internal port. An application that keeps its credential in a secret store has no other way to hand it over, and hiding the trait behind a module the application cannot name would push the seam into a closure or a boxed future, which is harder to read and harder to implement. Everything else the domain needs is a value.

The four directories

Section titled “The four directories”
Directory Holds Does not hold
src/domain Pure values and policy. Identifier newtypes that carry their invariants, the card model, the activity and reference types, the error taxonomy, the state and notification domain. Traits of its own, I/O, repository abstractions, an ambient clock. TokenProvider is the one public seam and is described below.
src/application Use cases, and the narrow inline port traits they own. The router, the connector sends, the card-action authorization hook, the state ports, the Graph use cases. Transport plumbing, concrete HTTP types, storage backends.
src/adapters/primary The inbound side: verify a request, parse it, translate it into a typed command, and hand it to a use case. The facade, the ingress pipeline, the Graph webhook endpoint, the manifest reader. Business decisions that belong to a use case.
src/adapters/secondary The outbound side: obtain a token, call an endpoint, store state, write a file. The Connector client, the Graph client, the key set, the state stores. Policy about when to retry or whether an outcome is ambiguous.

The split that matters is between application and adapters/secondary. The retry policy and the rule that decides whether a lost answer is an ambiguous write are pure functions, so they live in application where they can be tested without a network. The socket pool, the timeouts and the size limit live in the adapter. HttpClient is what applies the bounds, so a use case cannot forget them.

The rules that keep it

Section titled “The rules that keep it”

These are enforced, not aspirations. A change that violates one is a violation of ADR 0003.

The domain has no traits of its own, no I/O, no repository abstractions and no ambient clock. Time enters the system at one explicit place and nowhere else. A use case that needs the current time owns a narrow port for it, in the crate where the use case lives, and passes the time down. A clock trait in muss-core would have had no user: nothing in that crate asks for the time. The single exception is TokenProvider, a public seam rather than an internal port.

There is no shared ports module. A use case declares the one or two ports it needs as a trait local to the module that consumes it. Ports are never pooled into a shared abstraction layer that every use case and every adapter has to satisfy, and no crate collects them. A use case that owns several ports may group them in a file beside the use case — the Graph client keeps GraphEgress and BearerSource together in application/graph/ports.rs — but the file belongs to that use case, and nothing else depends on its existence.

Each use case owns its own port traits. The traits are narrow: one to three methods, declared where they are consumed, implemented by the adapter that satisfies them.

Untrusted input is parsed once, at the adapter boundary. A primary adapter takes the DTO and produces an invariant-carrying domain value through TryFrom or FromStr. A value that cannot be parsed is refused at the edge rather than carried inward. Outbound conversion is explicit, not a Display impl in disguise.

Stateful calls require an AuthContext, and tenant identity is mandatory in a storage key. AuthContext carries the tenant, the app identity, the audience and the scope set the operation requires. Authorization is default-deny: a bot that has not been told which channels or tenants it serves refuses them all, and the card-action pipeline runs an action only when an authorization hook allows it.

State-changing use cases have an atomic boundary. A typed UUID-v4 IdempotencyKey guards check, execute, persist and result. The SDK’s replay handling does not make an external business operation atomic; that is the application’s boundary, and the SDK exposes the hooks and the outbox pattern for it.

The module names utils, helpers, common and shared are not permitted. They are dumping grounds that hide exactly the ownership questions the boundary exists to answer.

Why it is shaped this way

Section titled “Why it is shaped this way”

The alternative was a split by layer across crates: a ports crate, a domain crate, an adapters crate. That produces a forest of crates with no in-tree consumer, speculative semver obligations, and a public API spread across packages a hello-world author has to learn at once. Splitting too little is worse still: every crate carries its own half-built copy of auth, HTTP and error handling, and Teams protocol churn fuses to shared primitives.

The current split keeps the shared parts shared and everything else in the crate that owns it. The workspace layout page says which crate owns what. The decisions page records why each boundary was drawn.
