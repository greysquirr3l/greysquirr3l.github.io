Continuous integration

This is the runbook for the workflows in .github/workflows/. It says what each check proves, how to run the same check on a developer machine, what the setup costs, and what has not been verified yet.

The workflows

Section titled “The workflows”
Workflow What it is for
ci.yml The build, the lint policy, the tests, the documentation, the feature matrix, the dependency policy and the coverage ratchet.
security.yml CodeQL for the source, the dependency review for a pull request, and a secret scan of the history.
dependabot.yml Weekly updates for the Cargo dependencies and for the pinned actions.

Neither workflow can write to the repository. The token permission is contents: read, plus security-events: write on the CodeQL job alone, because uploading a scan result is the only thing that needs it.

The checks, and what each one proves

Section titled “The checks, and what each one proves”
Check Command Proves
Formatting cargo f -- --check The tree is formatted the way rustfmt formats it.
Lint policy cargo l The whole Clippy profile holds: the warn groups, the six documented allowances, the specific denies and -D warnings.
Tests cargo t The suite passes on Linux x64, Linux arm64, macOS arm64 and Windows x64.
Documentation examples cargo test --workspace --all-features --locked --doc The examples in the rustdoc compile and run.
Reference documentation cargo dc The rustdoc builds with RUSTDOCFLAGS="-D warnings", so a broken intra-doc link fails the build.
Markdown style scripts/ci/install-markdownlint.sh then markdownlint-cli2 The markdown in the repository follows the rules in .markdownlint-cli2.jsonc, so a heading, list or fence mistake fails the build.
Published pages scripts/ci/check-docs-sync.sh The pages the site publishes are the pages the repository’s documents produce, so a change under docs/ that was never published fails the build.
Commit message hook scripts/ci/check-commit-msg-hook.sh The hook refuses a commit message carrying an agent/tool attribution trailer, and the installer keeps a hook that was already on the machine and lets it refuse the commit first.
Feature matrix scripts/ci/feature-matrix.sh run Every declared feature compiles on its own, the workspace compiles with no features at all, and each combination is tested with and without the Axum host.
Dependency policy cargo deny --all-features check No advisory, no banned crate, no disallowed licence, no unexpected source.
Advisory audit cargo audit The RustSec advisory database has nothing new against the lockfile.
Coverage ratchet scripts/ci/coverage.sh The owned domain and application code has not lost coverage.
Newest stable Rust cargo l on stable The project still builds and lints on a compiler newer than the pinned one.
CodeQL the CodeQL action The source has no known-dangerous pattern.
Dependency review the dependency review action A pull request does not bring in a vulnerable or unmaintained crate.
Secret scan scripts/ci/install-gitleaks.sh then gitleaks detect No secret was committed, anywhere in the history.

The commit message hook

Section titled “The commit message hook”

The repository’s git hooks live in scripts/hooks/ and are tracked, so every clone installs the same ones:

commit-msg refuses a commit message carrying an agent/tool attribution trailer – Co-authored-by: Copilot, and the same for Claude, ChatGPT, Gemini and the rest. The history belongs to the person who made the changes; the explanation belongs in the body of the message, where it is read. Remove the trailer rather than bypass the check: git commit --no-verify skips this hook and every other check the repository enforces, so it is not a way to get a commit in.

Installing over a hook that was already there does not discard it. The existing script moves to .git/hooks/<name>.pre-muss and runs first, so it can still refuse a commit before the repository’s own check runs. A second run of the installer changes nothing.

scripts/ci/check-commit-msg-hook.sh proves all of that: it runs the hook against a set of messages and asserts what it does with each one, and it runs the installer against a scratch repository to check the chaining. A hook that quietly stopped refusing anything would fail the build instead of sitting in .git/hooks where nothing looks at it.

./scripts/test-linux.sh is the local answer to “does this work on the shape Azure runs”. On an Apple Silicon machine it produces an arm64 Linux container, which is the same architecture and the same operating system as the Azure Linux hosts. It costs nothing.

Where the jobs run

Section titled “Where the jobs run”

The Linux jobs run on the organisation’s self-hosted runner, drinkme. The macOS, Windows and Linux arm64 jobs run on GitHub-hosted runners.

drinkme is a 32-core Linux x64 box with 75 GB of free disk, and it carries the whole dependency graph warm in the Cargo registry cache. A build of the whole workspace takes about a minute on it.

The label set every Linux job targets is:

Labels are AND-matched: a runner must carry every label listed. self-hosted is spelled out rather than relying on a bare custom label so that a workflow cannot accidentally land on this host when it meant a hosted runner, and just as importantly so that a hosted-runner workflow never lands here. linux and x64 pin the operating system and the architecture. docker is the custom label the runner was registered with, and it is the one that says the runner can host the container job the dependency policy needs.

actionlint only knows the standard GitHub label set, so .github/actionlint.yaml declares docker for it. Without that file the lint job reports a label that does not exist.

The hosted legs are gated

Section titled “The hosted legs are gated”

The hosted legs are billed, and the account they would draw on cannot pay: GitHub refuses to schedule the job at all, with “The job was not started because recent account payments have failed or your spending limit needs to be increased”. The job fails within seconds of being queued, with no steps executed and no runner ever assigned, so the run is red for a reason that has nothing to do with the code under test.

A skipped job never asks for a runner, so it never reaches the billing check. The hosted legs therefore carry a job-level gate:

The variable holds a label rather than a boolean, so the state is legible where it is read, in the workflow list and in the repository settings, instead of being an opaque true. An unset variable also skips, so a deleted variable cannot turn the hosted jobs back on by accident.

Value Effect
billing-ok The hosted jobs run.
billing-suspended The hosted jobs are skipped.
unset The hosted jobs are skipped.

What the runner does not carry

Section titled “What the runner does not carry”

The runner is a plain Linux box, so a job that needs a tool the box does not have installs it, the same way a developer machine would. Three of them needed an installer script:

  • shellcheck. actionlint checks the run: blocks of a workflow with shellcheck, and it skips that check when shellcheck is not on the machine. A linter that silently checks less than it appears to is worse than no linter, so scripts/ci/install-shellcheck.sh installs it.
  • yamllint. The runner has no pipx, so scripts/ci/install-yamllint.sh installs the tool into a virtual environment and checks every wheel against the hash the package index publishes for it.
  • Node.js. The runner’s tool cache has no Node until actions/setup-node puts one there, which the markdown style job does before it installs markdownlint-cli2.

The descriptor limit

Section titled “The descriptor limit”

The runner’s login sessions get a soft limit of 65536 open files, which is what the test suite needs: install_writes holds about a thousand sockets open at once, and under the default limit of 1024 the last of them fails to connect. The limit is set for the runner account in /etc/security/limits.d/99-actions-runner.conf.

The feature matrix

Section titled “The feature matrix”

cargo test --all-features does not prove a minimal build works. A feature can pull in a dependency, a module or a permission that no other build compiles, and the combined build hides the break. The matrix walks each declared feature on its own, so a feature that is broken in isolation fails before it is combined with everything else.

The features the project intends to ship are listed in scripts/ci/feature-matrix.sh together with the task that owns each one. A feature that no manifest declares yet is reported in the job summary rather than skipped in silence:

Feature Owned by State
outbound-only T07 Not declared
graph T16 Not declared
sqlite T09 Not declared
sso T22 Declared
files T23 Not declared

The list is the honest one. The workspace declares no features today, because none of the five surfaces is finished. The matrix job is not a no-op: it builds the workspace with no features at all and with every feature, and it picks up each feature automatically on the day its task lands.

What the matrix costs in disk

Section titled “What the matrix costs in disk”

The matrix walks six feature sets, and each one links its own binaries. A runner that keeps all of them runs out of disk before it reaches the last step: the target directory reached 8.5 GiB on a runner with 14 GiB, and the job failed with No space left on device.

scripts/ci/feature-matrix.sh run spends less, in three ways.

The workspace’s own artifacts are removed between combinations. Cargo keeps every build of a crate it has made, so the matrix was leaving one copy of muss-teams per feature set behind. That was 6.4 GiB of the 8.5 GiB. The dependencies stay, because every combination needs the same ones, so they are built once and reused.

The incremental cache is off. It exists to make the next build of the same crate cheap, and the matrix builds each crate once for each of six feature sets. The cache is paid for six times over and never read, which was 1.2 GiB of the peak for nothing. A developer who runs cargo build outside the script keeps the cache, because the setting is in the script rather than in the workspace manifest.

The debuginfo is stripped from the linked artifacts, and the debug information that reaches them is reduced to line tables. Cargo’s default for the development profile is the full form, and that is the largest part of an unstripped binary. Stripping it costs a reader nothing on a runner: a panic message names the file and the line from a constant compiled into the binary, not from the debug information, so a failing test still says which line raised it. What is lost is a debugger’s view of the variables, which a runner has no use for, and a backtrace’s line numbers, which the panic message has already named. The coverage measurement is unaffected: it uses its own instrumentation rather than the debug information, and it stands at 87% with the line tables alone.

The peak is about 2.8 GiB, measured with the same environment the runner has. The peak is the final build with every feature, where the shared dependencies and the three workspace crates are all present at once; it is the floor for a job that links every combination in one target directory.

The measurements were taken on a Linux container rather than on a runner, because a runner cannot be measured while it is the thing being measured. The container has the same toolchain and the same target directory layout, and the runner’s disk is the constraint the number has to fit in.

The coverage ratchet

Section titled “The coverage ratchet”

scripts/ci/coverage.sh measures line coverage of the pure domain and application layers and fails when it drops below the floor in scripts/ci/coverage-floor.txt.

The floor is a ratchet, not a target: it moves up and never down. The project target is 90%. The floor currently sits at 69%, which is where coverage actually stood when it was measured. The gap is concentrated in crates/muss-teams/src/domain/manifest/, the app manifest model that the manifest task owns, and in the serialisation paths of the newtypes.

The adapters are excluded on purpose. They hold the I/O, and what matters in them is proved by the behaviour tests that surround them rather than by a line count. The security decisions they make are covered by their own negative tests, which assert the decision rather than the line.

What this costs

Section titled “What this costs”

This repository is private, so the hosted runners are billed per minute against the account’s included compute usage.

The Linux jobs run on the organisation’s self-hosted runner, so they draw no minutes at all. That is most of the workflow: the build, the lint policy, the tests, the documentation, the feature matrix, the dependency policy, the coverage ratchet and the newest-stable check all run there.

The hosted legs that remain are the macOS, Windows and Linux arm64 test jobs, and they are gated on HOSTED_CI_BILLING_LABEL so that an account with no minutes does not turn every pull request red. See “The hosted legs are gated” above.

Two hosted-runner features are paid add-ons on a private repository:

  • CodeQL uploads results only where code scanning is enabled. On a private repository that is the GitHub Code Security add-on, which is paid. The workflow runs the analysis either way, but the results are not uploaded without the add-on.
  • Dependency review on a pull request needs the same add-on. The job detects a private repository and skips itself with an explicit warning rather than failing against a repository that cannot answer.

Two repository settings are worth turning on by hand, and neither is a workflow: GitHub’s own secret scanning and push protection. They catch a secret at the moment it is pushed, which is earlier than any workflow can, and they cost nothing on a public repository.

The cheapest way to run this project is what it already does: the container harness on a developer machine costs nothing and covers the Linux shape.

Pinned actions

Section titled “Pinned actions”

Every third-party action is pinned to a commit SHA, and the comment beside the SHA records the tag it points at:

EmbarkStudios/cargo-deny-action v2.1.1 3c6349835b2b7b196a839186cb8b78e02f7b5f25
github/codeql-action v4 1fc58d04a4d4374f921bdac573c3811c240f9c26
actions/dependency-review-action v5 a1d282b36b6f3519aa1f3fc636f609c47dddb294

A moving tag is remote code execution that changes without a commit in this repository, and a reviewer cannot review what they cannot see. Dependabot updates the SHA and the comment together, so the comment stays a truthful record.

To move one by hand, resolve the tag to a commit and update both:

The gitleaks and actionlint binaries are not actions, so they are installed by a script instead. Each script downloads the release and checks it against the checksum the release publishes, because the upstream actionlint install script does not check one, and a scanner for the pipeline should not be the weakest link in it.

markdownlint-cli2 is a Node package rather than a release binary, so its script reads the npm registry’s metadata for the pinned version and checks the tarball against the sha512 the registry publishes for it. npm then checks the integrity of every dependency below it.

What is deliberately absent

Section titled “What is deliberately absent”
  • No release pipeline. It belongs to the release task, and it must be one protected pipeline with a verified tag trigger. A chain of workflows that trust each other’s artefacts is the pattern that gets repositories compromised.
  • No pull_request_target. It runs the base branch’s code with a write token, which is remote code execution for anyone who can open a pull request.
  • No workflow_run artifact promotion. An artefact from one workflow is not trusted input for another.
  • No publish step. Nothing here pushes a tag, publishes a crate or creates a release.

The state of verification

Section titled “The state of verification”

The workflows run on the organisation’s self-hosted runner. The Linux jobs have executed there and passed; the hosted legs are skipped while the billing label says so.

What has been checked by running it:

  • The whole ci.yml workflow ran on drinkme: the formatting, the lint policy, the tests, the documentation, the feature matrix, the dependency policy, the advisory audit and the coverage ratchet all passed.
  • The whole security.yml workflow ran on drinkme: CodeQL analysed the source, the dependency review ran and the secret scan reported nothing.
  • The commit-msg job ran on drinkme and passed, so the hook and the installer have been checked on the runner and not only on a developer machine.
  • The macOS, Windows and Linux arm64 legs were skipped, which is the designed behaviour while the billing label says so. They are the part of the matrix that is still unproven on a runner.
  • actionlint reports no problem with either workflow file, and it checks the run: blocks with shellcheck.
  • yamllint reports no problem with any file under .github/, which covers dependabot.yml as well as the two workflows.
  • The shell scripts pass shellcheck.
  • scripts/ci/feature-matrix.sh runs and reports the feature list.
  • scripts/ci/install-gitleaks.sh installs a verified binary and the scan reports no secret in this repository’s history.
  • scripts/ci/install-markdownlint.sh installs a verified markdownlint-cli2 and it reports no problem with any of the markdown files it checks.
  • scripts/ci/coverage.sh runs and measures the floor it enforces.
  • scripts/ci/check-commit-msg-hook.sh runs and reports that the hook refuses every trailer it claims to refuse, that it accepts the messages it claims to accept, and that the installer keeps a hook that was already on the machine and lets it refuse the commit first.

What has not been checked: the three hosted legs. They have never had a runner to start on, and they stay unproven until the billing label is set to billing-ok and they run.
