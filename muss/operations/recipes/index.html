Offline recipes

One compiled recipe for each capability muss-teams ships today. Each runs on your machine with no cloud account, no tenant and no network, and each has a negative path: the way it fails, and where to read what to do about it.

A recipe that says “simulation” on its first line is one. Nothing leaves the process. A SimulatedTeams signs the requests with a key it generated, and the bot judges them with the production trust policy, so authentication is not bypassed; only the key source, the clock and the Connector address are replaced, through the test-utils feature that no production build enables. What a simulation prints is evidence about the SDK, not about how a tenant behaves. the compatibility matrix lists what no live tenant has confirmed.

T29 is incomplete. The single sign-on and file recipes are owed and are listed under Planned, not yet shipped.

Recipes

Section titled “Recipes”

The columns after the capability are the recipe file, the command that runs it, the test that runs or compiles it in CI, the explanation of how it fails, and whether the recipe imports only the public muss_teams:: paths (yes) or says which lower-layer type it still needs (no). A test reads this table: a row with a missing file, a missing test or no negative-path link fails the build.

ID Capability Recipe Run Tested by Negative path Facade only

approval-card An interactive approval card, a replay and a denied press crates/muss-teams/examples/approval.rs, crates/muss-teams/examples/per_user_view.rs cargo run -p muss-teams --example approval --features test-utils crates/muss-teams/tests/example_approval.rs, crates/muss-teams/tests/example_per_user_view.rs Card mismatch yes
standalone-notify A proactive message with no bot running crates/muss-teams/examples/notify.rs, crates/muss-teams/examples/proactive.rs cargo run -p muss-teams --example proactive --features test-utils crates/muss-teams/tests/example_proactive.rs App not installed and ambiguous writes yes

How to read it:

  • hello-bot is hello.rs in 11 nonblank lines, under the budget of 25. It needs real credentials to run, so CI compiles it and the offline round trip in offline.rs runs the same handler.
  • approval-card keeps the card action within 60 nonblank lines of bot code. per_user_view.rs is longer on purpose because it adds the refresh.
  • standalone-notify is two recipes. notify.rs is the 14-line sender that needs credentials and a saved conversation reference; proactive.rs runs the whole flow against the simulation, including a repeat that sends nothing and a denied target.
  • existing-host has two spellings. BuiltApp::handle(authorization, body) takes the header value and the body bytes and works with any web framework. BuiltApp::router() returns an Axum router to merge into your own, and tests/facade/host.rs serves it beside an unrelated route over real TCP.
  • The Facade only column is checked from both sides. A yes row fails if the example names muss_core or a muss_teams::adapters, muss_teams::application or muss_teams::domain path. A no row fails if it stops needing one, so the note cannot go stale.

Run them all

Section titled “Run them all”

PowerShell needs the quotes around a comma-separated feature list. The other examples follow the same two shapes.

cargo test --workspace --all-features --locked builds every example, runs each one that is listed above and checks what it prints, and runs the checks on this page.

Lower-layer examples

Section titled “Lower-layer examples”

These document a layer under the facade and say so in their first lines. They are not recipes for a capability, and an application does not need them.

Example Layer
crates/muss-teams/examples/connector.rs The Connector wiring TeamsClient is built from.
crates/muss-teams/examples/state.rs The state ports: deduplication, an idempotent approval and an outbox.
crates/muss-teams/examples/render.rs The manifest model the muss-teams tool is built on.

crates/muss-teams/examples/credential.rs Choosing a credential explicitly.

Planned, not yet shipped

Section titled “Planned, not yet shipped”

These capabilities are in the public contract but have no recipe, because the code behind them is not merged. Each has a row here so the contract and this page stay in step, and the build fails if a capability is listed in one and not the other. No recipe will be written until the capability itself is shipped and tested; a recipe over unimplemented code would be a pretend success.

ID Capability Waiting on
sso User single sign-on and delegated token exchange (the sso feature) The single sign-on task (T22). The 401 login and 412 SSO responses described in Card actions belong to it.
files File listing, upload flows and the consent they need (the files feature) The files and consent task (T23). Its Graph rows in the compatibility matrix are read from Learn but no code uses them.

When both land, T29 is reopened for two recipes: one for sso (a token exchange, and the refusal when consent is missing) and one for files (a listing and an upload session, and the refusal when the file permission is missing). Until then T29 is incomplete.
