Installation

An application depends on muss-teams and nothing else from this workspace, plus Tokio and whatever domain crates it already has.

muss-core is an ordinary transitive dependency. Its types stay behind the facade unless they are deliberately re-exported, so an application normally never names it. See the public API reference for the full list of deliberate re-exports.

The crate is not on crates.io yet

Section titled “The crate is not on crates.io yet”

As of 2026-11-13, muss-teams, muss-core and muss-teams-cli are not published to crates.io; the names are free but unclaimed. The version above is the contract the SDK documents, and it is the line to write when the crate is published. Until then, use one of the two forms below.

Feature flags

Section titled “Feature flags”

Feature names are part of the contract: a rename is a breaking change. Only http-host, sqlite, graph, sso and test-utils are declared in the manifest today. The bot runtime, the Adaptive Card builders, safe authentication and the in-memory store are always compiled in — the builders add no dependency, so there is nothing to gate.

Feature Default What it turns on
http-host on The Axum host: TeamsApp::run, TeamsApp::run_until, BuiltApp::router and BuiltApp::serve. It pulls in axum and Tokio’s net and signal features. A hello-world bot needs somewhere to listen, so it is on by default.
sqlite off TeamsApp::sqlite_state and the SqliteState store: durable state in a SQLite file instead of the in-memory store. Off by default because the in-memory store needs nothing and bundling SQLite adds a C compile.
graph off The Microsoft Graph clients: ApplicationGraph and DelegatedGraph, bounded paging, throttle and OData-error handling, and the path-only request escape hatch. It adds no dependency — the client is written over the shared transport — so the gate keeps Graph out of an application that never calls it.
sso off Teams sign-in: silent SSO (signin/tokenExchange), the sign-in fallback with state and PKCE, sealed per-person sessions, and the delegated token feed that UserSession::graph draws on. UserSession::graph also needs graph.
test-utils off muss_teams::testing: a test supplies its own signing keys, clock and Connector destination. Authentication still runs in full — the token is parsed, its signature checked and its claims judged by the production policy. Never enable it in a production build.

Turning features on is ordinary Cargo:

Cargo features only add. The lean, outbound-only build is --no-default-features, which leaves out the HTTP host and has no web server dependency. Use it for an application that only sends messages, or that hosts the bot on another framework through BuiltApp::handle.

The public contract also names bot-runtime, cards, auth, dev-storage, files, tracing-exporters and cli. Those are not declared in the manifest yet: the four always-on capabilities have nothing to gate, and the others arrive with the tasks that own them.

The toolchain

Section titled “The toolchain”

The workspace pins Rust 1.99.1 (stable) in rust-toolchain.toml, so rustup installs the exact compiler on first build. The workspace manifest declares edition 2024, resolver 3 and rust-version = "1.99".

Installing the command-line tool

Section titled “Installing the command-line tool”

The tool is optional. It scaffolds a project, validates and packages an app manifest, walks the operator through the Entra registration, and diagnoses a configuration. No library in the workspace depends on it, and no application should.

The installed program is called muss-teams. The crate on the registry would be muss-teams-cli; the two names are different things and neither is a crate name you put in a Cargo.toml.

The commands are init, manifest validate, package, setup and doctor. doctor is read-only by construction. setup prints its whole plan and changes nothing until --apply is given and the operator confirms. the CLI reference covers each command and what it writes.
