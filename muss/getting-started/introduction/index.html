What muss is

muss is a Cargo workspace of Rust crates for Microsoft 365. Its first product crate, muss-teams, is a framework-neutral Microsoft Teams SDK: it gives an application one facade over authenticated bot activities, Adaptive Cards, proactive messages, Graph notifications, dialogs, extensions and sign-in.

File listing and upload flows are named in the public contract and are not implemented yet. The contract and the implementation are kept in step: a capability is not advertised until it is built and tested.

An application that uses it declares one dependency and writes ordinary async functions. A handler receives a typed context. There is no connector client to build, no token cache to wire, no activity adapter to register and no dispatcher to start.

The full contract is in the public API reference; the facade itself is described in the facade guide.

The three crates

Section titled “The three crates”

The workspace has exactly three members. There is no umbrella muss crate.

Crate What it is Who depends on it
muss-core Shared M365 primitives: tenant identity and AuthContext, credential providers and audience-separated token clients, pooled bounded transport with a retry policy, the shared error taxonomy, UUID-v4 IdempotencyKey, secret redaction and telemetry hooks. muss-teams, transitively. An application normally never names it.
muss-teams The product: Teams protocol contracts, identifiers, Adaptive Card models, the bot runtime, the Graph surfaces and the public facade. Your application.
muss-teams-cli An optional command-line tool: init, manifest validate, package, setup and doctor. An operator. Never an application dependency, and never required at runtime.

muss-core holds only M365-generic primitives that muss-teams calls today. It is infrastructure, not a framework: a primitive with no in-tree caller is deleted rather than kept for a hypothetical second crate. The rule and its reasoning are in the workspace layout page.

The one-dependency promise

Section titled “The one-dependency promise”

muss-teams is the only dependency an application declares, plus Tokio and whatever domain crates the application already has.

muss-core arrives as an ordinary transitive dependency. Its types stay behind the facade unless they are deliberately re-exported, so an application that only sends messages never has to learn about the token cache, the transport pool or the credential adapters.

The SDK does not hand you transport plumbing, storage traits, generic parameter stacks or lifetime gymnastics. Those are the crate’s problem. What you get is a handler function and a typed context.

What the SDK does not do

Section titled “What the SDK does not do”

These are decisions, not gaps that are still being worked on. Each is recorded with its reason in ADR 0001.

  • It does not replace TeamsJS. A tab or meeting side-panel frontend runs in the browser and uses TeamsJS. v1 provides a documented bridge and a Rust backend contract, not a replacement for the browser SDK.
  • It does not advertise Graph beta endpoints. Only v1.0 is supported.
  • It does not support sovereign clouds. A non-global cloud is advertised only after its own compatibility run.
  • It does not do cross-tenant operation. v1 is single-tenant: one tenant per app registration.
  • It does not implement every Graph endpoint. It implements a named set of surfaces, each recorded in the compatibility matrix with its endpoint, API version, permission and the date the Microsoft Learn page was read.
  • It does not do Office 365 connector-based Incoming Webhooks. That mechanism was retired in Teams in May 2026. Inbound activities arrive over the Bot Connector service.
  • It does not implement API-based message extensions. v1 implements the bot-based model.
  • It does not capture native media. Application-hosted real-time audio and video is a different Microsoft platform with its own .NET and Windows requirements.

Two more boundaries are worth stating plainly.

No live tenant has been involved. Every test in the repository signs its own tokens and writes to a loopback server. What the SDK does against a real Microsoft 365 tenant is not yet confirmed, and the compatibility matrix says so row by row. Where a surface is unverified, the SDK does not claim it.

Windows is a first-class host, and it is not yet confirmed. The CI test matrix declares a Windows runner, and the Windows-specific path and name rules are tested on every platform, but the repository’s own record says Windows has not run any of this. What is explicitly unverified on Windows is the PowerShell instructions and the Azure CLI launcher lookup: the CLI installs az.cmd on Windows and the tool resolves it by walking PATH and PATHEXT itself. That lookup is tested with a supplied file system, but nothing has confirmed the resolved az.cmd starts.
