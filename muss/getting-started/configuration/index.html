Configuration

TeamsApp::from_env() reads five variables. Three are required, two are optional. The environment is read in one place, parsed into typed values, and every failure names the variable that is wrong.

The variables

Section titled “The variables”
Variable Required What it means
TEAMS_APP_ID yes The application (client) id of the bot’s Entra registration, a GUID. It is also the audience every inbound token is checked against.
TEAMS_TENANT_ID yes The id of the directory the registration lives in, a GUID. A domain name is refused: an activity names its tenant by GUID, so a bot configured with a domain would refuse every activity without saying why.
TEAMS_CLIENT_SECRET yes A client secret of the registration.
TEAMS_CREDENTIAL no Names the credential. client-secret is the default and the only value the environment can select. certificate and managed-identity are refused with a pointer to TeamsApp::with_credentials.
TEAMS_BIND_ADDR no The host:port that run binds. Defaults to 127.0.0.1:3978.

The default address is the loopback interface on purpose. A bot is reached through an HTTPS front end or a tunnel, and listening on every interface by default would publish a plain-HTTP endpoint nobody asked for.

TeamsClient::from_env() reads the same variables. It binds nothing and starts no task, so TEAMS_BIND_ADDR does not change where it listens — there is no listener.

Credential sources

Section titled “Credential sources”

The credential is a choice, never a guess. A missing secret is an error that names TEAMS_CLIENT_SECRET; it never turns into a managed identity.

The Credentials enum has four shapes:

Shape What it is How you configure it
Credentials::ClientSecret { id, secret } A client secret registered with the application. The simplest, and the least safe. TEAMS_CLIENT_SECRET, or TeamsApp::with_credentials.
Credentials::Certificate { id, private_key, thumbprint } A certificate registered with the application. The private key is in PKCS#8 PEM form; the thumbprint is the certificate’s SHA-1 thumbprint in standard base64. TeamsApp::with_credentials only.
Credentials::ManagedIdentity { client_id } An identity the host owns. client_id of None asks for the host’s system-assigned identity. TeamsApp::with_credentials only.
Credentials::Provider(Arc<dyn TokenProvider>) A seam for a credential that lives somewhere the SDK cannot see: a vault, a certificate store, a token broker. TeamsApp::with_credentials only.

The managed identity and the host

Section titled “The managed identity and the host”

Which identity service is asked is a fact about the host, not a choice the application makes. A virtual machine runs the instance metadata service; App Service and Azure Functions run a local token service and publish its address in IDENTITY_ENDPOINT and the value it wants in IDENTITY_HEADER. The SDK asks whichever one the host names, and the application does not have to know which host it is on.

Secrets are never printed

Section titled “Secrets are never printed”

A configuration error names the setting, says what to do about it, and never prints the value. The rule is the same for every setting, so no error has to be audited for which value it may show. The Debug rendering of a credential shows [redacted] where the secret or the private key would be.

What happens when a variable is missing

Section titled “What happens when a variable is missing”

Each failure names its variable and gives the next action. The messages are fixed text:

A variable that holds bytes that are not text is reported as not usable, with the reason “it is not valid text”, and not as not set: telling an operator that a variable is not set would send them looking for a variable that is there. A tenant id that is not a GUID is reported as not usable, with the reason “it is not a tenant id (a GUID)”. A secret that is present but empty is reported as not usable, with the reason “it is empty”.

TEAMS_CREDENTIAL gets its own wording. certificate and managed-identity are refused with “it is not supported here: only client-secret can be chosen from the environment”, and an unrecognised value is refused with “it is not a known credential”.

The same text is what a program sees when its main returns the error. fn main() -> Result<()> prints Error: TEAMS_APP_ID is not set. ..., because Error’s Debug rendering is its Display text. The variant is still there to match on. A test runs a failing start in a child process and checks the output.

TLS

Section titled “TLS”

The SDK does not terminate TLS. run binds a plain HTTP listener on the configured address, and the endpoint Teams reaches is HTTPS, so TLS is terminated in front of the bot — by a reverse proxy, an ingress controller or a development tunnel. There is no certificate file, private key path or port setting for the inbound side, because the inbound side is not the SDK’s to serve.

What the SDK does hold is the certificate credential: a private key and a thumbprint it signs a client assertion with when it authenticates outbound. That is a credential like any other, and it is configured in code through Credentials::Certificate.

Two related variables exist for the tooling rather than for the library: TEAMS_CERTIFICATE_PATH and TEAMS_CERTIFICATE_THUMBPRINT. The muss-teams setup command writes them into the environment file it generates for a certificate credential, and muss-teams doctor reads them to check that both are set and that they belong together. The library itself does not read them.

For outbound requests the TLS stack is rustls only. reqwest is built with default-features = false, so native-tls and openssl never enter the dependency tree.

Variables the host sets for you

Section titled “Variables the host sets for you”

Two more variables are read, but by the credential source rather than by the facade, and they are set by the Azure host rather than by you:

Variable Set by What it is
IDENTITY_ENDPOINT App Service and Azure Functions The address of the host’s local managed-identity token service.
IDENTITY_HEADER App Service and Azure Functions The value that service wants in its identity header.

If the host sets one and not the other, the credential source refuses to guess and says why.

Two APIs take a variable name you choose rather than reading a fixed one: ClientAuth::secret_from_env(variable) reads a client secret for the on-behalf-of exchange, and SealingKey::from_env(variable) reads the base64 key that seals a per-person sign-in session. The name is yours; nothing is implied about it. Both need the sso feature.

Configuration in code

Section titled “Configuration in code”

TeamsApp::with_credentials(app_id, tenant_id, credentials) configures a bot for a credential the environment cannot describe. It returns a ConfigError that names the argument that is wrong — app_id or tenant_id rather than a variable name — when the value is not usable.

TeamsApp::bind_addr(address) replaces TEAMS_BIND_ADDR. It takes a SocketAddr and cannot fail, because the address is already parsed by the time it is a SocketAddr.

See the facade guide for the rest of the builder, and the public API reference for the contract.
